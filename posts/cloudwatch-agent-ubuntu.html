Install and Configure the CloudWatch Agent on Ubuntu 22.04 & 24.04

A complete walkthrough for getting the Amazon CloudWatch Agent running on Jammy and Noble — IAM setup, package install, the configuration wizard, custom metrics and log collection, systemd management, and the troubleshooting steps that actually matter.

1. Why the CloudWatch Agent

By default, an EC2 instance reports a small set of metrics to CloudWatch — CPU utilization, network in/out, disk read/write bytes — collected from the hypervisor. What it does not report is anything the hypervisor cannot see: memory usage, disk space (as opposed to disk I/O), per-process metrics, or the contents of any log file on the instance.

The CloudWatch Agent fills that gap. It runs as a systemd service on the instance, reads metrics from /proc and /sys, tails arbitrary log files, and ships everything to CloudWatch Metrics and CloudWatch Logs. It is the supported AWS-native way to get memory utilization, disk usage, swap, and application logs into the same place as your other observability data.

What You Get

  • System metrics — memory, disk, swap, network at much finer granularity than the default EC2 metrics.
  • Process metrics — per-process CPU, memory, and file-descriptor counts via procstat.
  • Log shipping — tail any file on disk and stream lines into a CloudWatch log group, with timestamp parsing and multi-line message support.
  • Custom metrics from StatsD or collectd — push application-defined metrics through the agent without writing AWS SDK code.
Note: The agent is open-source (aws/amazon-cloudwatch-agent on GitHub) and the binary is the same across Amazon Linux, Ubuntu, RHEL, and SUSE. What changes between distros is the package format and the systemd unit path. This guide focuses on the .deb install for Ubuntu 22.04 (Jammy) and 24.04 LTS (Noble).

2. Prerequisites

Confirm each item below before installing. Most of the install issues people hit are actually IAM or networking issues that surface as confusing agent log messages.

  • An EC2 instance running Ubuntu Server 22.04 LTS or 24.04 LTS (the latest LTS), amd64 or arm64. The agent works on both architectures and the install steps are identical apart from the package URL.
  • Outbound HTTPS (443) from the instance to the regional CloudWatch endpoints (monitoring.<region>.amazonaws.com, logs.<region>.amazonaws.com). If you are inside a private subnet without a NAT gateway, you need VPC endpoints for both services.
  • An IAM role attached to the instance with permissions to publish metrics and write logs. Local AWS credentials work too, but a role is the only sensible choice on EC2.
  • Sudo access on the instance.
  • The wget or curl package installed for downloading the .deb. Both ship by default on Ubuntu Server.
Confirm the OS version and architecture
lsb_release -a
# Distributor ID: Ubuntu
# Release:        24.04
# Codename:       noble

dpkg --print-architecture
# amd64  (or arm64 on Graviton)

3. IAM Setup — Role or User

The agent needs permission to write metrics, write log events, and (optionally) read its configuration from SSM Parameter Store. AWS publishes a managed policy that covers all of this — CloudWatchAgentServerPolicy — and you should attach it to a role rather than reinventing the wheel.

Create an IAM role and attach the managed policy (one-time, from your workstation)
# Trust policy that lets EC2 assume the role
cat > trust-policy.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
EOF

aws iam create-role \
  --role-name CloudWatchAgentServerRole \
  --assume-role-policy-document file://trust-policy.json

aws iam attach-role-policy \
  --role-name CloudWatchAgentServerRole \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

# Wrap the role in an instance profile and attach to the EC2 instance
aws iam create-instance-profile \
  --instance-profile-name CloudWatchAgentServerRole

aws iam add-role-to-instance-profile \
  --instance-profile-name CloudWatchAgentServerRole \
  --role-name CloudWatchAgentServerRole

aws ec2 associate-iam-instance-profile \
  --instance-id i-0123456789abcdef0 \
  --iam-instance-profile Name=CloudWatchAgentServerRole
Verify the role is visible from inside the instance
# From the EC2 instance — IMDSv2 token first
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/
# CloudWatchAgentServerRole
Important: The agent will silently fail to publish if the role is missing or the policy is wrong. The error shows up in the agent log as a 403 from the CloudWatch API — easy to miss. Test the role before installing the agent.

4. Install the Agent on Ubuntu

The agent ships as a .deb package directly from AWS. There is no need to add an apt repository for the install itself, though you can if you want apt-managed upgrades. The same package works on both Ubuntu 22.04 and 24.04.

Download and install — amd64
cd /tmp

wget https://s3.amazonaws.com/amazoncloudwatch-agent/ubuntu/amd64/latest/amazon-cloudwatch-agent.deb

sudo dpkg -i -E ./amazon-cloudwatch-agent.deb

# Confirm the install
dpkg -l | grep amazon-cloudwatch-agent
Download and install — arm64 (Graviton)
cd /tmp

wget https://s3.amazonaws.com/amazoncloudwatch-agent/ubuntu/arm64/latest/amazon-cloudwatch-agent.deb

sudo dpkg -i -E ./amazon-cloudwatch-agent.deb

The package installs the binary at /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent, drops a systemd unit at /etc/systemd/system/amazon-cloudwatch-agent.service, and creates the runtime directories under /opt/aws/amazon-cloudwatch-agent/. The service is installed but not started — that comes after you supply a config.

Where the agent lives on disk
# Binary
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent

# Wrapper CLI (start/stop/fetch-config)
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl

# Wizard
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-config-wizard

# Configuration files
/opt/aws/amazon-cloudwatch-agent/etc/

# Logs
/opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log
Tip: On Ubuntu 24.04 the package may pull in a couple of additional shared library dependencies the first time. If dpkg -i complains about unmet dependencies, run sudo apt-get install -f immediately after to resolve them.

5. Generate a Config With the Wizard

The fastest way to get a working configuration is the interactive wizard. It walks through a series of questions about which metrics and logs you want, then writes a JSON config to /opt/aws/amazon-cloudwatch-agent/bin/config.json.

Launch the wizard
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-config-wizard

The wizard asks roughly the following questions, in order. Answer them based on your environment.

  • OS — pick Linux.
  • Hosting environment — EC2 (or on-premises if not on AWS).
  • Which user to run as — accept the default cwagent; the package created this user during install.
  • Collect StatsD metrics? — only say yes if your application actually sends StatsD.
  • Collect CollectD metrics? — same — only if collectd is actually running.
  • Monitor host metrics? — yes. Choose a default level (Basic, Standard, Advanced). Standard is a sensible starting point.
  • Metric collection interval — 60 seconds is the safe default. Anything below 60 puts you on high-resolution metrics, which cost more.
  • Monitor log files? — yes. Provide the file path, log group name, log stream name, and timestamp format for each file you want shipped.
  • Save config to SSM Parameter Store? — yes if you want to deploy the same config to a fleet. Otherwise, no.

When the wizard exits, the generated config is at /opt/aws/amazon-cloudwatch-agent/bin/config.json. Read it, version-control it, and treat it as the source of truth for that instance class.

Note: The wizard is convenient for the first install. For everything after that — fleets, infrastructure-as-code, environment-specific configs — hand-write the config and ship it via SSM, S3, or your config management tool. Section 6 shows what the file actually looks like.

6. Hand-Write a Config File

The agent config is plain JSON with three top-level sections: agent (global settings), metrics (what to collect from the host), and logs (what files to tail). The example below is a sensible production starting point — memory, disk, swap, network, and a couple of common log files.

/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
{
  "agent": {
    "metrics_collection_interval": 60,
    "run_as_user": "cwagent",
    "logfile": "/opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log"
  },
  "metrics": {
    "namespace": "CWAgent/Linux",
    "append_dimensions": {
      "InstanceId": "${aws:InstanceId}",
      "AutoScalingGroupName": "${aws:AutoScalingGroupName}"
    },
    "aggregation_dimensions": [["AutoScalingGroupName"], ["InstanceId"]],
    "metrics_collected": {
      "mem": {
        "measurement": ["mem_used_percent", "mem_available_percent"]
      },
      "disk": {
        "resources": ["/"],
        "measurement": ["used_percent", "inodes_used"],
        "ignore_file_system_types": ["sysfs", "devtmpfs", "tmpfs"]
      },
      "swap": {
        "measurement": ["swap_used_percent"]
      },
      "netstat": {
        "measurement": ["tcp_established", "tcp_time_wait"]
      }
    }
  },
  "logs": {
    "logs_collected": {
      "files": {
        "collect_list": [
          {
            "file_path": "/var/log/syslog",
            "log_group_name": "/ubuntu/syslog",
            "log_stream_name": "{instance_id}",
            "timestamp_format": "%b %d %H:%M:%S",
            "retention_in_days": 30
          },
          {
            "file_path": "/var/log/nginx/access.log",
            "log_group_name": "/nginx/access",
            "log_stream_name": "{instance_id}",
            "retention_in_days": 14
          }
        ]
      }
    }
  }
}

A few decisions worth understanding before you copy this verbatim.

  • namespace — every metric the agent publishes lands here. Pick a name you can search by; CWAgent is the AWS default but a project- or team-specific namespace makes filtering easier.
  • append_dimensions — these dimensions are added to every metric. ${aws:InstanceId} and ${aws:AutoScalingGroupName} are resolved at runtime from instance metadata.
  • aggregation_dimensions — tells CloudWatch to also publish aggregated views (e.g., the whole ASG together) so you can alarm on a single line per ASG instead of per instance.
  • retention_in_days — sets log retention on first write. Without this, log groups default to Never expire, which is the most expensive setting.
  • {instance_id} — a token the agent expands. You can use {hostname}, {ip_address}, or any environment variable.

7. Start, Stop, and Reload the Agent

The agent is managed through its own wrapper script, amazon-cloudwatch-agent-ctl. It is a thin layer over systemctl that also handles the “fetch and apply this config” step. You can call systemctl directly too — both work.

Apply a local config file and start the agent
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
  -a fetch-config \
  -m ec2 \
  -c file:/opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json \
  -s
Apply a config stored in SSM Parameter Store
# Replace the parameter name with your own
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
  -a fetch-config \
  -m ec2 \
  -c ssm:AmazonCloudWatch-linux-prod \
  -s
Service control through systemd
# Status
sudo systemctl status amazon-cloudwatch-agent

# Stop and start
sudo systemctl stop amazon-cloudwatch-agent
sudo systemctl start amazon-cloudwatch-agent

# Restart after editing the config file directly
sudo systemctl restart amazon-cloudwatch-agent

# Enable on boot (the package usually does this for you)
sudo systemctl enable amazon-cloudwatch-agent
Tip: After editing amazon-cloudwatch-agent.json, always re-run the fetch-config -s command rather than just restarting the service. fetch-config validates the JSON, translates it into the agent's internal TOML format, and only then restarts. A plain restart will load the previous translated config.

8. Collect Application Log Files

The most common reason to install the agent is log shipping. The pattern is the same for every file: add an entry to logs.logs_collected.files.collect_list, give it a log group, set retention, re-apply the config.

Add an application log to the existing config
{
  "file_path": "/var/log/myapp/app.log",
  "log_group_name": "/myapp/application",
  "log_stream_name": "{instance_id}",
  "timestamp_format": "%Y-%m-%d %H:%M:%S",
  "timezone": "UTC",
  "multi_line_start_pattern": "^\\d{4}-\\d{2}-\\d{2}",
  "retention_in_days": 14
}

A few of those fields are worth calling out:

  • timestamp_format — uses Go's strftime-style placeholders. If the agent cannot match the timestamp, it stamps each line with the time it was read instead of the time it was logged. Set this for any log where ordering matters.
  • multi_line_start_pattern — a regex marking the first line of a new event. Without it, multi-line stack traces are split into one CloudWatch event per line, making them very hard to read.
  • timezone — defaults to local. Set to UTC for any log that does not include a timezone in its timestamp.
  • File permissions — the cwagent user must be able to read the log file. Add it to the relevant group (e.g., adm for syslog, nginx for nginx logs) rather than chmodding files world-readable.
Grant cwagent read access via group membership
# Add cwagent to the adm group (lets it read /var/log/syslog and friends)
sudo usermod -aG adm cwagent

# For nginx logs
sudo usermod -aG adm cwagent  # nginx access/error logs are usually adm-readable on Ubuntu

# Restart so the new group membership takes effect
sudo systemctl restart amazon-cloudwatch-agent

9. Verify Metrics and Logs in CloudWatch

Within roughly one collection interval (60 seconds in the example config) you should see metrics arriving in the CloudWatch console under your chosen namespace, and log events under each log group.

Check from the CLI without leaving the instance
# List recent metrics in your namespace
aws cloudwatch list-metrics \
  --namespace "CWAgent/Linux" \
  --region "us-east-1"

# Pull a single data point for mem_used_percent
aws cloudwatch get-metric-statistics \
  --namespace "CWAgent/Linux" \
  --metric-name "mem_used_percent" \
  --dimensions "Name=InstanceId,Value=i-0123456789abcdef0" \
  --start-time "$(date -u -d '5 minutes ago' +%FT%TZ)" \
  --end-time "$(date -u +%FT%TZ)" \
  --period 60 \
  --statistics Average

# List log groups created by the agent
aws logs describe-log-groups \
  --log-group-name-prefix "/ubuntu"
Tail the agent's own log to confirm it is publishing
sudo tail -f /opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log

# What you want to see:
# Successfully built the agent runtime
# Got Home directory: /root
# I! Starting AmazonCloudWatchAgent CWAgent/
# I! Loaded inputs: cpu disk diskio mem net netstat swap
# I! Loaded outputs: cloudwatch cloudwatchlogs

10. Troubleshooting

The agent is generally well-behaved, but four issues account for almost every failed install.

403 from the CloudWatch API

The agent log shows AccessDenied when calling PutMetricData or PutLogEvents. Either the IAM role is not attached, or the policy is missing one of the required actions. Re-run the IAM verification from section 3 and confirm CloudWatchAgentServerPolicy is attached.

Agent starts then immediately exits

Check journalctl -u amazon-cloudwatch-agent -n 50. The most common cause is a malformed JSON config — a trailing comma, a missing brace, or a wrong key name. The wrapper script does validate, but only at fetch-config time, so a directly-edited file with a syntax error will fail at boot.

Validate the JSON before applying
jq . /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.json
# If jq prints the parsed JSON, syntax is fine.
# If it errors, fix the file before restarting.

Logs are flowing but timestamps look wrong

The timestamp_format in your config does not match the actual format in the file. CloudWatch then stamps each line with the time it was read, which clusters everything around restart times. Open the log file, copy a real timestamp, and translate it character-by-character into the strftime placeholders.

Metrics are publishing but disk usage is missing

By default the agent only collects disk metrics for filesystems whose mount type is in its allowlist. Containerized or LVM setups often miss /. Either add resources with explicit mount points (as in the section 6 example) or adjust ignore_file_system_types.

Important: Never set metrics_collection_interval below 60 unless you actually need high-resolution metrics. Anything under 60 seconds is billed as a high-resolution metric and the cost can climb very fast on a fleet of any size.

11. Best Practices

The patterns below are what I have seen actually hold up across fleets running this agent.

  • Store the config in SSM Parameter Store, one parameter per role. Keep AmazonCloudWatch-web, AmazonCloudWatch-worker, etc. as separate parameters and have each instance fetch the one matching its role tag. This is the cleanest path to a fleet-wide rollout.
  • Always set retention_in_days on every log group. The default is Never expire, which silently grows your CloudWatch Logs bill forever. Pick a retention that matches your actual investigation window.
  • Tag log groups the same way you tag the instances writing to them. Cost allocation reports become useful only when log groups carry the team / environment / service tags.
  • Run the wizard once, version-control the JSON forever. The wizard is a starting point; the config belongs in the same repo as the rest of your infrastructure code.
  • Bake the agent into your AMIs rather than installing it on first boot. The package install itself is fast, but doing it inline with cloud-init pushes the “instance is ready” checkpoint out by 30+ seconds.
  • Use append_dimensions, not custom dimensions per metric. ${aws:InstanceId} and ${aws:AutoScalingGroupName} are resolved by the agent and stay correct across instance replacements.
  • Watch amazon-cloudwatch-agent.log itself. The agent will keep running even when CloudWatch calls are failing — symptoms only show up when you go looking for the metric or log later. Add the agent's own log file to its collect_list so it ships its own logs.
  • Upgrade quarterly. AWS publishes regular fixes and metric additions; apt-get install --only-upgrade amazon-cloudwatch-agent if you added the apt source, or just re-download the latest .deb.
Wrap-up: Once installed, the CloudWatch Agent is one of those services you set up once and barely think about again. The hard parts are getting IAM right and committing to a sensible config that you actually maintain. Do those two things well and the rest — metrics, logs, alarms, dashboards — is just a matter of pointing CloudWatch at the data the agent is already shipping.
