Migrating Secrets from Azure Key Vault to AWS Secrets Manager

A practical, hands-on guide to bulk-migrating secrets between cloud-native secret management services — using Python, Azure CLI, and AWS SDK with encryption handling and validation.

1. Why Migrate Between Cloud Secret Managers

Organizations migrate secrets between cloud providers for a variety of compelling reasons. The most common scenario is a full cloud migration — moving workloads from Azure to AWS (or vice versa) means your secrets need to follow your applications. Multi-cloud consolidation is another driver: teams that once ran services across both clouds may decide to standardize on a single provider to reduce operational overhead.

Other motivations include cost optimization (AWS Secrets Manager charges $0.40/secret/month plus $0.05 per 10,000 API calls, while Azure Key Vault uses a per-transaction model at $0.03 per 10,000 operations for standard tier), vendor lock-in reduction, and alignment with organizational security policies that mandate a specific secrets platform.

Key Differences at a Glance

Feature Azure Key Vault AWS Secrets Manager
Pricing Per-transaction ($0.03/10K ops) Per-secret ($0.40/mo) + API calls
Encryption Azure-managed or CMK (HSM-backed) AWS KMS (default or custom CMK)
Secret Types Secrets, Keys, Certificates String or Binary values
Rotation Event Grid + Azure Functions Native Lambda-based rotation
API Style REST API with Azure AD auth AWS SDK with IAM/STS auth

2. Prerequisites

Before starting the migration, ensure the following tools and permissions are in place on your workstation or CI/CD runner:

  • Azure CLI (v2.50+) — authenticated with az login
  • AWS CLI (v2) — configured via aws configure with a profile that has Secrets Manager write access
  • Python 3.8+ with pip
  • Required Python packages: boto3, azure-identity, azure-keyvault-secrets
  • Azure RBAC: At minimum, the Key Vault Secrets User role on the source vault
  • AWS IAM: Permissions for secretsmanager:CreateSecret, secretsmanager:TagResource, and kms:Encrypt if using a custom KMS key
Install Python dependencies
pip install boto3 azure-identity azure-keyvault-secrets
Security Note: Never run migration scripts on a shared or public machine. Secret values will briefly exist in memory during transfer. Use a hardened bastion host or a short-lived CI runner with encrypted swap disabled.

3. Understanding the Data Model Differences

Azure Key Vault and AWS Secrets Manager use fundamentally different data models. Understanding these differences is critical for a clean migration.

Azure Key Vault Model

Azure Key Vault separates its storage into three distinct entity types:

  • Secrets — arbitrary string values (passwords, API keys, connection strings)
  • Keys — cryptographic keys used for sign/verify/encrypt/decrypt operations (RSA, EC)
  • Certificates — X.509 certificates with optional private key material and renewal policies

Each secret in Azure Key Vault has a unique name, a value, optional tags (key-value metadata), a content type field, and activation/expiration dates. Secrets are versioned automatically — every update creates a new version while preserving the history.

AWS Secrets Manager Model

AWS Secrets Manager stores all data as either a SecretString (UTF-8 text, commonly JSON) or a SecretBinary (binary blob up to 64 KB). There is no built-in separation between secrets, keys, and certificates — everything is a "secret." Rotation is handled via Lambda functions attached directly to the secret resource.

Mapping Strategy

Recommended mapping between services
# Azure Key Vault          -->  AWS Secrets Manager
# ─────────────────────────────────────────────────────
# Secret Name              -->  Secret Name (sanitized)
# Secret Value             -->  SecretString
# Content Type             -->  Tag: "ContentType"
# Tags                     -->  Tags (direct mapping)
# Activation Date          -->  Tag: "ActivationDate"
# Expiration Date          -->  Tag: "ExpirationDate"
# Vault Name               -->  Tag: "SourceVault"
# Key Vault Keys           -->  AWS KMS (separate migration)
# Key Vault Certificates   -->  AWS ACM or Secrets Manager
Name Sanitization: Azure Key Vault allows only alphanumerics and hyphens in secret names. AWS Secrets Manager also accepts underscores, forward slashes, and dots. Generally, Azure names are directly compatible — but always validate with a regex check: /^[a-zA-Z0-9\-]+$/.

4. Method 1: Azure CLI + AWS CLI (Quick & Simple)

For small vaults with fewer than 50 secrets, a Bash script combining both CLIs is the fastest approach. This method requires no Python and works directly from any terminal with both CLIs installed.

migrate-secrets-cli.sh
#!/bin/bash
# Migration script: Azure Key Vault --> AWS Secrets Manager
# Usage: ./migrate-secrets-cli.sh <vault-name> [aws-region]

set -euo pipefail

VAULT_NAME="${1:?Usage: $0 <vault-name> [aws-region]}"
AWS_REGION="${2:-us-east-1}"
SUCCESS_COUNT=0
FAIL_COUNT=0
LOG_FILE="migration-$(date +%Y%m%d-%H%M%S).log"

log() { echo "[$(date '+%H:%M:%S')] $*" | tee -a "$LOG_FILE"; }

log "Starting migration from Azure Key Vault: $VAULT_NAME"
log "Target AWS region: $AWS_REGION"

# Fetch all secret names from Azure Key Vault
SECRET_NAMES=$(az keyvault secret list \
  --vault-name "$VAULT_NAME" \
  --query "[?attributes.enabled].name" \
  -o tsv)

TOTAL=$(echo "$SECRET_NAMES" | wc -l | tr -d ' ')
log "Found $TOTAL enabled secrets to migrate"

for SECRET_NAME in $SECRET_NAMES; do
  log "Processing: $SECRET_NAME"

  # Retrieve secret value from Azure
  SECRET_VALUE=$(az keyvault secret show \
    --vault-name "$VAULT_NAME" \
    --name "$SECRET_NAME" \
    --query "value" -o tsv) || {
    log "ERROR: Failed to read $SECRET_NAME from Azure"
    ((FAIL_COUNT++))
    continue
  }

  # Create secret in AWS Secrets Manager
  if aws secretsmanager create-secret \
    --name "$SECRET_NAME" \
    --secret-string "$SECRET_VALUE" \
    --region "$AWS_REGION" \
    --tags "Key=SourceVault,Value=$VAULT_NAME" \
           "Key=MigratedAt,Value=$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
    2>>"$LOG_FILE"; then
    log "  OK: $SECRET_NAME migrated successfully"
    ((SUCCESS_COUNT++))
  else
    log "  FAIL: $SECRET_NAME — check log for details"
    ((FAIL_COUNT++))
  fi

  # Clear the variable immediately
  unset SECRET_VALUE
done

log "Migration complete: $SUCCESS_COUNT succeeded, $FAIL_COUNT failed (of $TOTAL)"
Tip: If a secret already exists in AWS, create-secret will fail. Use aws secretsmanager put-secret-value instead to update existing secrets, or add a --force-overwrite-replica-secret flag in your error-handling branch.

5. Method 2: Python Script (Recommended)

For production migrations with hundreds or thousands of secrets, a Python script provides better error handling, dry-run support, progress tracking, and metadata preservation. This is the recommended approach.

migrate_secrets.py
#!/usr/bin/env python3
"""Migrate secrets from Azure Key Vault to AWS Secrets Manager."""

import argparse
import hashlib
import json
import logging
import sys
from datetime import datetime, timezone

import boto3
from botocore.exceptions import ClientError
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    handlers=[
        logging.StreamHandler(sys.stdout),
        logging.FileHandler("migration.log"),
    ],
)
logger = logging.getLogger(__name__)


def get_azure_secrets(vault_url: str) -> list[dict]:
    """Retrieve all enabled secrets from Azure Key Vault."""
    credential = DefaultAzureCredential()
    client = SecretClient(vault_url=vault_url, credential=credential)
    secrets = []

    for prop in client.list_properties_of_secrets():
        if not prop.enabled:
            logger.info(f"Skipping disabled secret: {prop.name}")
            continue

        secret = client.get_secret(prop.name)
        secrets.append({
            "name": secret.name,
            "value": secret.value,
            "content_type": prop.content_type or "",
            "tags": prop.tags or {},
            "expires_on": prop.expires_on.isoformat() if prop.expires_on else "",
            "not_before": prop.not_before.isoformat() if prop.not_before else "",
        })
        logger.info(f"Read secret: {secret.name}")

    return secrets


def create_aws_secret(
    sm_client,
    name: str,
    value: str,
    tags: dict,
    kms_key_id: str = "",
) -> bool:
    """Create a secret in AWS Secrets Manager."""
    aws_tags = [
        {"Key": k, "Value": v} for k, v in tags.items()
    ]

    create_kwargs = {
        "Name": name,
        "SecretString": value,
        "Tags": aws_tags,
    }
    if kms_key_id:
        create_kwargs["KmsKeyId"] = kms_key_id

    try:
        sm_client.create_secret(**create_kwargs)
        return True
    except ClientError as e:
        if e.response["Error"]["Code"] == "ResourceExistsException":
            logger.warning(f"Secret '{name}' already exists — updating value")
            sm_client.put_secret_value(SecretId=name, SecretString=value)
            return True
        logger.error(f"Failed to create '{name}': {e}")
        return False


def migrate(args):
    """Main migration orchestration."""
    vault_url = f"https://{args.vault_name}.vault.azure.net"
    logger.info(f"Source: {vault_url}")
    logger.info(f"Target: AWS Secrets Manager ({args.aws_region})")
    logger.info(f"Dry run: {args.dry_run}")

    # Step 1: Read all secrets from Azure
    secrets = get_azure_secrets(vault_url)
    logger.info(f"Retrieved {len(secrets)} secrets from Azure Key Vault")

    if args.dry_run:
        logger.info("DRY RUN — listing secrets that would be migrated:")
        for s in secrets:
            logger.info(f"  {s['name']} (content_type={s['content_type']})")
        return

    # Step 2: Create each secret in AWS
    sm_client = boto3.client(
        "secretsmanager", region_name=args.aws_region
    )
    success, failed = 0, 0

    for i, secret in enumerate(secrets, 1):
        logger.info(f"[{i}/{len(secrets)}] Migrating: {secret['name']}")

        # Build tags including Azure metadata
        tags = {**secret["tags"]}
        tags["SourceVault"] = args.vault_name
        tags["MigratedAt"] = datetime.now(timezone.utc).isoformat()
        if secret["content_type"]:
            tags["ContentType"] = secret["content_type"]
        if secret["expires_on"]:
            tags["ExpirationDate"] = secret["expires_on"]
        if secret["not_before"]:
            tags["ActivationDate"] = secret["not_before"]

        ok = create_aws_secret(
            sm_client,
            name=secret["name"],
            value=secret["value"],
            tags=tags,
            kms_key_id=args.kms_key_id,
        )
        if ok:
            success += 1
        else:
            failed += 1

    logger.info(f"Migration complete: {success} OK, {failed} failed")


if __name__ == "__main__":
    parser = argparse.ArgumentParser(
        description="Migrate Azure Key Vault secrets to AWS"
    )
    parser.add_argument("--vault-name", required=True)
    parser.add_argument("--aws-region", default="us-east-1")
    parser.add_argument("--kms-key-id", default="",
        help="Custom KMS key ARN for encryption")
    parser.add_argument("--dry-run", action="store_true",
        help="List secrets without migrating")
    migrate(parser.parse_args())
Run the migration
# Dry run first — always!
python migrate_secrets.py --vault-name my-prod-vault --dry-run

# Execute the migration
python migrate_secrets.py \
  --vault-name my-prod-vault \
  --aws-region us-east-1 \
  --kms-key-id arn:aws:kms:us-east-1:123456789:key/abc-def-123

6. Handling Secret Types

Not all secrets are simple strings. Your migration logic needs to account for different content types stored in Azure Key Vault.

Plain Text Secrets

API keys, passwords, and tokens migrate directly as SecretString values. No transformation needed.

JSON Secrets

If your Azure Key Vault secret has content_type: application/json, the value is typically a JSON object (e.g., database credentials). AWS Secrets Manager natively supports JSON in SecretString — just pass it through directly. The AWS console will even render individual key-value pairs for easy inspection.

Certificates

Azure Key Vault certificates combine the certificate chain and private key. When migrating to AWS, you have two options: store the PEM content in Secrets Manager as a SecretString, or import the certificate into AWS Certificate Manager (ACM) instead.

Connection Strings

Azure services often store connection strings as single semicolon-delimited values. Consider converting these to structured JSON for better compatibility with AWS SDK patterns:

Converting Azure connection strings to JSON
def parse_connection_string(conn_str: str) -> dict:
    """Convert Azure-style connection strings to JSON."""
    parts = {}
    for segment in conn_str.split(";"):
        if "=" in segment:
            key, value = segment.split("=", 1)
            parts[key.strip()] = value.strip()
    return parts

# Example usage during migration
azure_value = "Server=mydb.database.windows.net;Database=prod;User=admin;Password=s3cret"
aws_value = json.dumps(parse_connection_string(azure_value))
# Result: {"Server":"mydb.database.windows.net","Database":"prod","User":"admin","Password":"s3cret"}

Preserving Tags and Metadata

Azure Key Vault tags map directly to AWS Secrets Manager tags. The Python script above handles this automatically, carrying over all custom tags plus adding migration-specific metadata like SourceVault, MigratedAt, and ContentType.

Tag Limits: AWS Secrets Manager supports a maximum of 50 tags per secret with keys up to 128 characters and values up to 256 characters. Azure Key Vault supports 15 tags with keys up to 256 characters. If your Azure secrets use long tag values, you may need to truncate them.

7. Handling Encryption

Both services encrypt secrets at rest, but with different encryption stacks. Understanding how each handles encryption is critical during migration.

Azure Key Vault Encryption

Azure Key Vault encrypts all secrets using either Azure-managed keys (service-managed, no configuration needed) or customer-managed keys (CMK) backed by Azure Key Vault HSM or Managed HSM. When you read a secret via the API, Azure transparently decrypts it — you always receive the plaintext value.

AWS Secrets Manager Encryption

AWS Secrets Manager encrypts every secret version using an AWS KMS key. By default, it uses the AWS-managed key aws/secretsmanager. For tighter control, specify a customer-managed KMS key (CMK).

Creating a secret with a custom KMS key
# Using AWS CLI
aws secretsmanager create-secret \
  --name "db-credentials" \
  --secret-string '{"username":"admin","password":"s3cret"}' \
  --kms-key-id "arn:aws:kms:us-east-1:123456789012:key/abcd-1234-efgh-5678"

# Using boto3
sm_client.create_secret(
    Name="db-credentials",
    SecretString='{"username":"admin","password":"s3cret"}',
    KmsKeyId="arn:aws:kms:us-east-1:123456789012:key/abcd-1234-efgh-5678",
)
Encryption in Transit: Both services enforce TLS for all API calls. During migration, secret values are decrypted on the client side (your script), held briefly in memory, then re-encrypted by AWS KMS when stored. The secret value never touches disk unless you explicitly log it (do not log secret values).

Cross-Account KMS Considerations

If your AWS Secrets Manager lives in a different account from the KMS key, ensure the KMS key policy grants kms:Encrypt, kms:Decrypt, and kms:GenerateDataKey to the Secrets Manager service principal in the target account.

8. Terraform Approach

If you manage your infrastructure with Terraform, you can use data sources to read from Azure Key Vault and resources to create in AWS Secrets Manager. This approach provides declarative, version-controlled migration with built-in plan/apply workflow.

main.tf — Terraform migration configuration
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.80"
    }
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.30"
    }
  }
}

provider "azurerm" {
  features {}
}

provider "aws" {
  region = var.aws_region
}

variable "vault_id" {
  description = "Azure Key Vault resource ID"
  type        = string
}

variable "aws_region" {
  default = "us-east-1"
}

variable "secret_names" {
  description = "List of secret names to migrate"
  type        = list(string)
}

variable "kms_key_arn" {
  description = "Custom KMS key ARN (optional)"
  type        = string
  default     = ""
}

# Read each secret from Azure Key Vault
data "azurerm_key_vault_secret" "source" {
  for_each     = toset(var.secret_names)
  name         = each.value
  key_vault_id = var.vault_id
}

# Create the secret container in AWS
resource "aws_secretsmanager_secret" "migrated" {
  for_each = data.azurerm_key_vault_secret.source

  name       = each.value.name
  kms_key_id = var.kms_key_arn != "" ? var.kms_key_arn : null

  tags = {
    SourceVault = var.vault_id
    MigratedAt  = timestamp()
    ContentType = each.value.content_type
  }
}

# Store the actual secret value
resource "aws_secretsmanager_secret_version" "migrated" {
  for_each = data.azurerm_key_vault_secret.source

  secret_id     = aws_secretsmanager_secret.migrated[each.key].id
  secret_string = each.value.value
}
State File Security: Terraform stores secret values in plain text within the state file. Use a remote backend with encryption (S3 + KMS, or Terraform Cloud) and restrict access to the state file. Consider using sensitive = true on all secret-related outputs.
Run the Terraform migration
terraform init
terraform plan -var-file="migration.tfvars"
terraform apply -var-file="migration.tfvars" -auto-approve

9. Validation & Rollback

After migration, you must verify that every secret was transferred correctly — without exposing the actual values. The approach: compare SHA-256 hashes of the source and target values.

validate_migration.py
#!/usr/bin/env python3
"""Validate migrated secrets by comparing hashes."""

import hashlib
import boto3
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

def sha256(value: str) -> str:
    return hashlib.sha256(value.encode()).hexdigest()

def validate(vault_name: str, aws_region: str):
    # Azure client
    az_client = SecretClient(
        vault_url=f"https://{vault_name}.vault.azure.net",
        credential=DefaultAzureCredential(),
    )
    # AWS client
    sm_client = boto3.client("secretsmanager", region_name=aws_region)

    mismatches = []
    missing = []
    matched = 0

    for prop in az_client.list_properties_of_secrets():
        if not prop.enabled:
            continue

        azure_secret = az_client.get_secret(prop.name)
        azure_hash = sha256(azure_secret.value)

        try:
            aws_resp = sm_client.get_secret_value(SecretId=prop.name)
            aws_hash = sha256(aws_resp["SecretString"])

            if azure_hash == aws_hash:
                matched += 1
            else:
                mismatches.append(prop.name)
        except sm_client.exceptions.ResourceNotFoundException:
            missing.append(prop.name)

    print(f"\nValidation Results:")
    print(f"  Matched:    {matched}")
    print(f"  Mismatches: {len(mismatches)}  {mismatches}")
    print(f"  Missing:    {len(missing)}  {missing}")

    return len(mismatches) == 0 and len(missing) == 0

validate("my-prod-vault", "us-east-1")

Rollback Strategy

The safest rollback approach is to keep Azure Key Vault as a read-only backup during the transition period:

  1. Do not delete Azure Key Vault secrets immediately after migration
  2. Set Azure Key Vault access policies to read-only for application identities
  3. Monitor AWS Secrets Manager access patterns for 2-4 weeks
  4. Once all applications are confirmed using AWS, soft-delete Azure Key Vault secrets
  5. Azure retains soft-deleted secrets for 7-90 days (configurable), giving you a final safety net
Tip: Tag migrated Azure secrets with MigrationStatus: completed and MigratedTo: aws so that other teams know these secrets have been moved.

10. Post-Migration Checklist

Migration is not complete when the secrets land in AWS. Use this checklist to ensure a production-safe transition:

Application Configuration

  • Update all application code and config files to use AWS Secrets Manager SDK calls instead of Azure Key Vault
  • Replace azure-keyvault-secrets references with boto3 or the AWS Secrets Manager caching client
  • Update Kubernetes ExternalSecrets or CSI driver manifests to point to AWS Secrets Manager
  • Update any CI/CD pipeline variables that reference Azure Key Vault URIs

Enable Rotation

  • For database credentials, set up automatic rotation using AWS-provided Lambda templates
  • Configure rotation intervals (minimum 1 day, recommended 30-90 days for most secrets)
  • Test rotation in a staging environment before enabling in production

Monitoring and Alerting

  • Create CloudWatch alarms for secretsmanager:GetSecretValue failures
  • Set up CloudTrail logging for all Secrets Manager API calls
  • Configure SNS notifications for rotation failures
  • Monitor cost using AWS Cost Explorer — track per-secret and per-API-call charges

Decommission Azure Key Vault

  • Revoke write access to the Azure Key Vault (keep read-only for rollback)
  • After the validation period (2-4 weeks), soft-delete all migrated secrets
  • Update Azure RBAC policies — remove service principal access
  • If the vault is empty and no longer needed, schedule it for deletion
  • Remove the Azure Key Vault provider from your Terraform state if applicable

IAM and Security

  • Apply least-privilege IAM policies — grant only secretsmanager:GetSecretValue to application roles
  • Use resource-based policies to restrict which secrets each service can access
  • Enable VPC endpoints for Secrets Manager to avoid secrets traversing the public internet
  • Review KMS key policies to ensure only authorized principals can decrypt
Cost Monitoring: AWS Secrets Manager charges $0.40 per secret per month. If you are migrating hundreds of secrets, consider consolidating related values into single JSON secrets (e.g., all database credentials for one service as one secret) to reduce costs. A vault with 500 individual secrets would cost $200/month — consolidating into 50 JSON secrets brings that down to $20/month.
