Transferring HashiCorp Vault Secrets from Azure VM to AWS

A step-by-step guide to migrating secrets between two HashiCorp Vault instances across cloud providers — from an Azure VM to an AWS EC2 instance — with zero downtime and full audit trail.

1. Why Migrate Vault Secrets Cross-Cloud

There are several common scenarios where organizations need to transfer their entire secrets estate from one cloud to another. Understanding your reason helps determine which migration method is appropriate and how much effort to invest in automation.

Common Scenarios

  • Full Cloud Migration — Your company is moving its entire infrastructure from Azure to AWS. Every workload, database, and supporting service (including secrets management) must follow. The Vault on your Azure VM is the source of truth, and you need an identical copy running on EC2.
  • Multi-Cloud Strategy — You are adopting a multi-cloud architecture where workloads in AWS need local access to secrets without cross-cloud API latency. Both Vault instances will coexist, with periodic synchronization.
  • Disaster Recovery — The AWS Vault serves as a warm standby. If the Azure region goes down, your applications failover to AWS and need immediate access to the same secrets, policies, and auth configurations.
  • Cost Optimization — Reserved instance pricing, data transfer costs, or licensing changes make AWS more economical. You need to migrate without losing any secrets or version history.

Key Challenges

Cross-cloud secret migration introduces risks that do not exist in a single-provider environment:

  • Network Security — Secrets must never travel over the public internet in plaintext. You need VPN tunnels, VPC peering, or at minimum TLS-encrypted API calls with certificate pinning.
  • Encryption in Transit — Even with TLS, consider double-encrypting the payload using Vault's transit secrets engine. If a TLS termination proxy is misconfigured, your secrets remain protected.
  • Secret Versioning — KV v2 secrets carry version metadata, creation timestamps, and custom metadata. Decide early whether you need the full version history or only the latest version on the destination.
  • Audit Compliance — Regulatory frameworks like SOC 2, HIPAA, and PCI-DSS require a complete audit trail for secret access. Enable audit devices on both Vaults before the migration begins so every read and write is logged.
Note: This guide covers both HashiCorp Vault OSS and Enterprise editions. Enterprise-specific features like performance replication and DR replication are called out explicitly in Method 3.

2. Prerequisites

Before you begin the migration, verify that every item on this checklist is in place. Missing a prerequisite mid-migration can leave secrets in an inconsistent state.

  • Source Vault (Azure VM) — A running, initialized, and unsealed HashiCorp Vault instance on an Azure Virtual Machine. Record the address as VAULT_ADDR (e.g., https://azure-vault.example.com:8200).
  • Destination Vault (AWS EC2) — A running, initialized, and unsealed HashiCorp Vault instance on an AWS EC2 instance. Record the address (e.g., https://aws-vault.example.com:8200). Ensure the KV v2 secrets engine is enabled at the same mount path as the source.
  • Vault CLI (v1.15+) — Installed on your workstation or a bastion host that can reach both Vault instances over the network.
  • Authentication Tokens — Root or admin-level tokens for both Vaults. Ideally, create purpose-built tokens with a short TTL and scoped policies (read-only on source, write-only on destination).
  • Network Connectivity — A secure network path between your workstation and both Vault endpoints. Options include Azure VPN Gateway to AWS Site-to-Site VPN, AWS Transit Gateway, or public endpoints with TLS and IP allowlisting.
  • jq (v1.6+) — The command-line JSON processor, used to parse Vault API responses and extract secret data.
  • Audit Logging Enabled — On both Vault instances, to capture a tamper-evident log of every operation performed during the migration.
Verify Vault CLI and jq are installed
vault version
# Vault v1.15.4 (or later)

jq --version
# jq-1.7
Enable audit logging on both Vault instances
# On the source Vault (Azure VM)
vault audit enable file file_path=/var/log/vault/audit-source.log

# On the destination Vault (AWS EC2)
vault audit enable file file_path=/var/log/vault/audit-dest.log
Tip: Test connectivity from your workstation to both Vaults before proceeding: vault status -address=https://azure-vault.example.com:8200 and vault status -address=https://aws-vault.example.com:8200. Both should return Sealed: false.

3. Architecture Overview

Regardless of the method you choose, the migration follows a three-stage pipeline: export from source, secure transfer, and import to destination. Your workstation (or a bastion host) acts as the orchestrator.

High-level migration architecture

│    Azure VM              │    TLS / VPN         │    AWS EC2               │
│    ┌──────────────────┐  │  ────────────────►    │  ┌──────────────────┐    │
│    │  HashiCorp Vault │  │  vault kv get/put     │  │  HashiCorp Vault │    │
│    │  (Source)        │  │  or HTTP API          │  │  (Destination)   │    │
│    │                  │  │                       │  │                  │    │
│    │  KV v2 Secrets   │  │                       │  │  KV v2 Secrets   │    │
│    │  Policies        │  │                       │  │  Policies        │    │
│    │  Auth Methods    │  │                       │  │  Auth Methods    │    │
│    └──────────────────┘  │                       │  └──────────────────┘    │

Two Approaches

This guide covers three methods, each suited to a different scale and set of constraints:

  • Method 1 — Manual CLI Export/Import: Best for small secret stores (fewer than 50 paths). You run vault kv get and vault kv put commands one at a time. Transparent, easy to audit, but tedious at scale.
  • Method 2 — Automated Bash Script: Best for medium to large stores. A script recursively discovers every secret path, exports each one to JSON, and imports it to the destination with full logging.
  • Method 3 — Transit Engine & Enterprise Replication: Best for Enterprise customers who need real-time sync, or OSS users who want encrypted-at-rest staging files during the transfer.
Important: All three methods transfer only the latest version of each secret by default. If you need full version history, you must iterate over each version number using the KV v2 API endpoint /v1/secret/data/:path?version=N.

4. Method 1: CLI-Based Export/Import

This is the most straightforward approach. You manually list secrets on the source Vault, export each one as JSON, and write it to the destination Vault. It is ideal for small migrations or when you want to inspect each secret before importing.

Step 1: Set environment variables

Define source and destination Vault addresses and tokens
# Source Vault (Azure VM)
export SOURCE_VAULT_ADDR="https://azure-vault.example.com:8200"
export SOURCE_VAULT_TOKEN="hvs.CAESIJz...azure-token"

# Destination Vault (AWS EC2)
export DEST_VAULT_ADDR="https://aws-vault.example.com:8200"
export DEST_VAULT_TOKEN="hvs.CAESIKx...aws-token"

Step 2: List all secret paths on the source

List top-level keys under the secret/ mount
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault kv list -format=json secret/

# Example output:
# [
#   "app/",
#   "database/",
#   "api-keys",
#   "tls-certs/"
# ]

Paths ending with / are directories. You will need to list them recursively to discover leaf secrets within.

Step 3: Export a single secret to JSON

Read a secret and extract only the data payload
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault kv get -format=json secret/database/postgres \
  | jq '.data.data' > /tmp/secret-database-postgres.json

# Inspect the exported data
cat /tmp/secret-database-postgres.json
# {
#   "username": "db_admin",
#   "password": "s3cur3-P@ssw0rd!",
#   "host": "postgres.internal.azure.com",
#   "port": "5432"
# }

Step 4: Import the secret to the destination

Write the JSON payload to the same path on the AWS Vault
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault kv put secret/database/postgres @/tmp/secret-database-postgres.json

# Verify the write succeeded
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault kv get secret/database/postgres
Warning: The file /tmp/secret-database-postgres.json contains plaintext secrets. Delete it immediately after import using shred -u /tmp/secret-database-postgres.json. Never leave plaintext secret files on disk.

Step 5: Repeat for every secret path

For each key returned by vault kv list, repeat the export and import steps. If a key ends with /, list it to discover nested secrets. This works for small stores, but becomes impractical beyond a few dozen secrets — that is where Method 2 comes in.

5. Method 2: Automated Bash Script

For larger secret stores, manual export/import is tedious and error-prone. The following script automates the full process: it recursively walks every path in the source KV store, exports each secret, and writes it to the destination Vault. Every operation is logged with a timestamp for auditability.

vault-migrate.sh — Complete migration script
#!/usr/bin/env bash
# ──────────────────────────────────────────────────────────────
# vault-migrate.sh
# Recursively migrate all KV v2 secrets from source to destination Vault
# Usage: chmod +x vault-migrate.sh && ./vault-migrate.sh
# ──────────────────────────────────────────────────────────────

set -euo pipefail

# ── Configuration ─────────────────────────────────────────────
SOURCE_VAULT_ADDR="https://azure-vault.example.com:8200"
SOURCE_VAULT_TOKEN="hvs.CAESIJz...azure-token"
DEST_VAULT_ADDR="https://aws-vault.example.com:8200"
DEST_VAULT_TOKEN="hvs.CAESIKx...aws-token"
KV_MOUNT="secret"
LOG_FILE="vault-migration-$(date +%Y%m%d-%H%M%S).log"

# Counters
SUCCESS_COUNT=0
FAIL_COUNT=0
SKIP_COUNT=0

# ── Logging helper ────────────────────────────────────────────
log() {
  local msg="[$(date '+%Y-%m-%d %H:%M:%S')] $1"
  echo "$msg" | tee -a "$LOG_FILE"
}

# ── Recursive migration function ──────────────────────────────
migrate_path() {
  local path="$1"

  # List all keys at the current path on the source Vault
  local keys
  keys=$(VAULT_ADDR="$SOURCE_VAULT_ADDR" \
    VAULT_TOKEN="$SOURCE_VAULT_TOKEN" \
    vault kv list -format=json "${KV_MOUNT}/${path}" 2>/dev/null) || {
    log "WARN: Could not list path: ${KV_MOUNT}/${path} — skipping"
    (( SKIP_COUNT++ )) || true
    return
  }

  # Iterate over each key returned
  for key in $(echo "$keys" | jq -r '.[]'); do
    if [[ "$key" == */ ]]; then
      # Key is a directory — recurse into it
      log "Entering directory: ${KV_MOUNT}/${path}${key}"
      migrate_path "${path}${key}"
    else
      # Key is a leaf secret — export from source, import to destination
      local full_path="${KV_MOUNT}/${path}${key}"
      log "Migrating secret: $full_path"

      # Read secret data from source Vault
      local secret_data
      secret_data=$(VAULT_ADDR="$SOURCE_VAULT_ADDR" \
        VAULT_TOKEN="$SOURCE_VAULT_TOKEN" \
        vault kv get -format=json "$full_path" \
        | jq -c '.data.data') || {
        log "  ERROR: Failed to read $full_path from source"
        (( FAIL_COUNT++ )) || true
        continue
      }

      # Write secret data to destination Vault
      echo "$secret_data" | \
        VAULT_ADDR="$DEST_VAULT_ADDR" \
        VAULT_TOKEN="$DEST_VAULT_TOKEN" \
        vault kv put "$full_path" - &>/dev/null && {
        log "  OK: $full_path migrated successfully"
        (( SUCCESS_COUNT++ )) || true
      } || {
        log "  ERROR: Failed to write $full_path to destination"
        (( FAIL_COUNT++ )) || true
      }
    fi
  done
}

# ── Main execution ────────────────────────────────────────────
log "============================================="
log "  Vault Secret Migration — Starting"
log "============================================="
log "Source:      $SOURCE_VAULT_ADDR"
log "Destination: $DEST_VAULT_ADDR"
log "KV Mount:    $KV_MOUNT"
log ""

# Verify connectivity to both Vault instances
VAULT_ADDR="$SOURCE_VAULT_ADDR" VAULT_TOKEN="$SOURCE_VAULT_TOKEN" \
  vault status &>/dev/null || {
  log "FATAL: Cannot reach source Vault at $SOURCE_VAULT_ADDR"
  exit 1
}

VAULT_ADDR="$DEST_VAULT_ADDR" VAULT_TOKEN="$DEST_VAULT_TOKEN" \
  vault status &>/dev/null || {
  log "FATAL: Cannot reach destination Vault at $DEST_VAULT_ADDR"
  exit 1
}

log "Connectivity verified. Beginning migration..."
log ""

# Start recursive migration from the root of the KV mount
migrate_path ""

# Print summary
log ""
log "============================================="
log "  Migration Complete"
log "============================================="
log "Secrets migrated successfully: $SUCCESS_COUNT"
log "Secrets failed:               $FAIL_COUNT"
log "Paths skipped:                $SKIP_COUNT"
log "Full log available at:        $LOG_FILE"
Tip: Run this script from a bastion host that has network access to both Vault instances. The timestamped log file provides a complete audit trail. Pipe it through tee to watch progress in real time while also saving to disk.
Warning: This script stores secret data in shell variables temporarily. Ensure the bastion host has encrypted swap and restricted access. Clear your shell history after the migration: history -c && history -w.

6. Method 3: Using Vault's Transit & Replication

For organizations with stricter security requirements or Vault Enterprise licenses, there are more robust options than shell scripts.

Enterprise: Performance and DR Replication

Vault Enterprise includes built-in replication that synchronizes data between a primary and one or more secondary clusters automatically. This is the gold standard for cross-cloud secret migration.

  • Performance Replication — Secondaries serve read requests locally, reducing latency. Writes are forwarded to the primary. Ideal for multi-cloud active/active setups.
  • DR Replication — The secondary is a hot standby that mirrors the primary. It cannot serve requests until promoted. Ideal for disaster recovery.
Enable DR replication (Enterprise only)
# On the source Vault (Azure VM) — enable as DR primary
vault write -f sys/replication/dr/primary/enable

# Generate a secondary activation token
vault write -format=json \
  sys/replication/dr/primary/secondary-token \
  id="aws-ec2-dr" | jq -r '.wrap_info.token'
# Save this wrapping token securely

# On the destination Vault (AWS EC2) — activate as DR secondary
vault write sys/replication/dr/secondary/enable \
  token="<wrapping-token-from-primary>"

OSS: Transit Secrets Engine for Encrypted Transfer

If you are using Vault OSS and need to stage exported secrets on disk (for example, on an intermediate jump box), you can encrypt them using the transit secrets engine. This ensures that even if the staging files are compromised, the secrets remain protected.

Enable and configure the transit engine on the source
# Enable the transit secrets engine on the source Vault
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault secrets enable transit

# Create a dedicated encryption key for the migration
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault write -f transit/keys/migration-key \
  type="aes256-gcm96"
Export, encrypt, then decrypt and import
# Step 1: Read secret from source and base64-encode it
SECRET_JSON=$(VAULT_ADDR=$SOURCE_VAULT_ADDR \
  VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault kv get -format=json secret/database/postgres \
  | jq -c '.data.data')

B64_ENCODED=$(echo -n "$SECRET_JSON" | base64)

# Step 2: Encrypt with transit engine
CIPHERTEXT=$(VAULT_ADDR=$SOURCE_VAULT_ADDR \
  VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault write -format=json transit/encrypt/migration-key \
  plaintext="$B64_ENCODED" \
  | jq -r '.data.ciphertext')

# Step 3: Store the ciphertext — safe to write to disk
echo "$CIPHERTEXT" > /tmp/secret-postgres-encrypted.dat

# Step 4: Decrypt using the transit engine
PLAINTEXT=$(VAULT_ADDR=$SOURCE_VAULT_ADDR \
  VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault write -format=json transit/decrypt/migration-key \
  ciphertext="$(cat /tmp/secret-postgres-encrypted.dat)" \
  | jq -r '.data.plaintext' | base64 -d)

# Step 5: Write the decrypted secret to the destination Vault
echo "$PLAINTEXT" | \
  VAULT_ADDR=$DEST_VAULT_ADDR \
  VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault kv put secret/database/postgres -

# Step 6: Securely remove the encrypted staging file
shred -u /tmp/secret-postgres-encrypted.dat
When to use Transit: Use this method when secrets must be staged on an intermediate host (like a jump box) before being pushed to the destination. The ciphertext file is useless without access to the transit key, providing defense in depth beyond TLS.

7. Handling Auth Methods

Secrets are only half the story. Your applications authenticate to Vault using auth methods such as AppRole, Token-based auth, and Kubernetes auth. These configurations must be recreated on the destination Vault so that applications can authenticate after the migration.

Migrating AppRole Auth

List and export AppRole roles from the source Vault
# List all AppRole roles on the source
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault list -format=json auth/approle/role \
  | jq -r '.[]'

# Export a specific role's configuration
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault read -format=json auth/approle/role/web-app \
  | jq '.data' > /tmp/approle-web-app.json

# View the exported configuration
cat /tmp/approle-web-app.json
# {
#   "token_ttl": 3600,
#   "token_max_ttl": 14400,
#   "token_policies": ["web-app-policy"],
#   "secret_id_ttl": 86400,
#   "secret_id_num_uses": 0
# }
Recreate the AppRole on the destination Vault
# Enable AppRole auth method on the destination
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault auth enable approle

# Recreate the role with the same configuration
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault write auth/approle/role/web-app \
  token_ttl="1h" \
  token_max_ttl="4h" \
  token_policies="web-app-policy" \
  secret_id_ttl="24h" \
  secret_id_num_uses="0"

Migrating Token Auth Configuration

Recreate token roles on the destination
# Export token role from source
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault read -format=json auth/token/roles/ci-runner \
  | jq '.data' > /tmp/token-role-ci-runner.json

# Create the same token role on the destination
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault write auth/token/roles/ci-runner \
  allowed_policies="ci-read-only" \
  orphan="true" \
  token_period="768h" \
  renewable="true"

Migrating Kubernetes Auth

Configure Kubernetes auth for AWS EKS on the destination
# Enable Kubernetes auth on the destination
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault auth enable kubernetes

# Configure with the AWS EKS cluster details
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault write auth/kubernetes/config \
  kubernetes_host="https://ABCDEF1234.gr7.us-east-1.eks.amazonaws.com" \
  kubernetes_ca_cert=@/tmp/eks-ca-cert.pem \
  token_reviewer_jwt=@/tmp/eks-reviewer-token.jwt

# Recreate Kubernetes auth roles
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault write auth/kubernetes/role/web-app \
  bound_service_account_names="web-app-sa" \
  bound_service_account_namespaces="production" \
  policies="web-app-policy" \
  ttl="1h"
Important: AppRole role_id values are deterministic and tied to the role name, but secret_id values are unique to each Vault instance. After recreating roles on the destination, you must generate new secret_id values and distribute them to your applications through your deployment pipeline.

8. Handling Policies

Vault policies control which paths a token can access and what operations it can perform. Migrate every custom policy from the source to the destination before applications attempt to authenticate — otherwise, tokens will be issued with no permissions.

Export All Custom Policies

List and export policies from the source Vault
# List all policies (exclude built-in default and root)
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault policy list | grep -v -E '^(default|root)$'

# Export each custom policy to an HCL file
for policy in $(VAULT_ADDR=$SOURCE_VAULT_ADDR \
  VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault policy list | grep -v -E '^(default|root)$'); do

  VAULT_ADDR=$SOURCE_VAULT_ADDR \
  VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
    vault policy read "$policy" > "/tmp/policy-${policy}.hcl"

  echo "Exported: $policy -> /tmp/policy-${policy}.hcl"
done
Example exported policy: web-app-policy.hcl
# Allow read access to application secrets
path "secret/data/app/*" {
  capabilities = ["read", "list"]
}

# Allow the app to manage its own token
path "auth/token/renew-self" {
  capabilities = ["update"]
}

# Deny access to admin secrets
path "secret/data/admin/*" {
  capabilities = ["deny"]
}

Import Policies to the Destination

Write all exported policies to the AWS Vault
# Import each policy file to the destination Vault
for policy_file in /tmp/policy-*.hcl; do
  # Extract the policy name from the filename
  policy_name=$(basename "$policy_file" .hcl | sed 's/^policy-//')

  VAULT_ADDR=$DEST_VAULT_ADDR \
  VAULT_TOKEN=$DEST_VAULT_TOKEN \
    vault policy write "$policy_name" "$policy_file"

  echo "Imported: $policy_name"
done

# Verify all policies exist on the destination
VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault policy list
Tip: Review each policy before importing. Some may reference Azure-specific auth paths (e.g., auth/azure/login) or resource IDs that must be updated for AWS. For example, replace Azure Managed Identity references with AWS IAM role ARNs in the relevant auth method configuration.

9. Validation & Verification

Never assume a migration succeeded. Validate every aspect: secret counts, individual values, policies, and auth methods. This section provides scripts and techniques for thorough verification.

Compare Secret Counts

Count top-level keys on source and destination
# Count keys on source
SRC_COUNT=$(VAULT_ADDR=$SOURCE_VAULT_ADDR \
  VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault kv list -format=json secret/ | jq 'length')

# Count keys on destination
DST_COUNT=$(VAULT_ADDR=$DEST_VAULT_ADDR \
  VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault kv list -format=json secret/ | jq 'length')

echo "Source count:      $SRC_COUNT"
echo "Destination count: $DST_COUNT"

if [ "$SRC_COUNT" -eq "$DST_COUNT" ]; then
  echo "Counts match."
else
  echo "WARNING: Count mismatch! Investigate before proceeding."
fi

Spot-Check Individual Secret Values

Compare a specific secret between source and destination
# Read from source and destination, then compare
SRC_VAL=$(VAULT_ADDR=$SOURCE_VAULT_ADDR \
  VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault kv get -format=json secret/database/postgres \
  | jq -Sc '.data.data')

DST_VAL=$(VAULT_ADDR=$DEST_VAULT_ADDR \
  VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault kv get -format=json secret/database/postgres \
  | jq -Sc '.data.data')

if [ "$SRC_VAL" = "$DST_VAL" ]; then
  echo "secret/database/postgres: MATCH"
else
  echo "secret/database/postgres: MISMATCH"
  echo "Source: $SRC_VAL"
  echo "Dest:   $DST_VAL"
fi

Full Recursive Validation Script

vault-validate.sh — Compare all secrets between source and destination
#!/usr/bin/env bash
# vault-validate.sh — Verify all secrets match post-migration

set -euo pipefail

MATCH=0
MISMATCH=0
MISSING=0

validate_path() {
  local path="$1"
  local keys
  keys=$(VAULT_ADDR="$SOURCE_VAULT_ADDR" \
    VAULT_TOKEN="$SOURCE_VAULT_TOKEN" \
    vault kv list -format=json "secret/${path}" 2>/dev/null) || return

  for key in $(echo "$keys" | jq -r '.[]'); do
    if [[ "$key" == */ ]]; then
      validate_path "${path}${key}"
    else
      local full="secret/${path}${key}"
      local src dst

      src=$(VAULT_ADDR="$SOURCE_VAULT_ADDR" \
        VAULT_TOKEN="$SOURCE_VAULT_TOKEN" \
        vault kv get -format=json "$full" \
        | jq -Sc '.data.data')

      dst=$(VAULT_ADDR="$DEST_VAULT_ADDR" \
        VAULT_TOKEN="$DEST_VAULT_TOKEN" \
        vault kv get -format=json "$full" \
        | jq -Sc '.data.data' 2>/dev/null) || dst="NOT_FOUND"

      if [ "$dst" = "NOT_FOUND" ]; then
        echo "MISSING:  $full"
        (( MISSING++ )) || true
      elif [ "$src" = "$dst" ]; then
        echo "MATCH:    $full"
        (( MATCH++ )) || true
      else
        echo "MISMATCH: $full"
        (( MISMATCH++ )) || true
      fi
    fi
  done
}

echo "=== Vault Migration Validation ==="
validate_path ""

echo ""
echo "=================================="
echo "Matched:  $MATCH"
echo "Mismatch: $MISMATCH"
echo "Missing:  $MISSING"

if [ "$MISMATCH" -eq 0 ] && [ "$MISSING" -eq 0 ]; then
  echo "Validation PASSED"
else
  echo "Validation FAILED — review mismatches above"
  exit 1
fi
Tip: Run the validation script immediately after migration, and again 24 hours later to catch any secrets that may have been updated on the source after the migration window.

10. Security Best Practices

Migrating secrets is one of the most sensitive operations you can perform. Follow every practice below to minimize the risk of exposure, unauthorized access, and compliance violations.

TLS Everywhere

Both Vault instances must use valid TLS certificates signed by a trusted Certificate Authority. Never use -tls-skip-verify in production — it disables certificate validation and opens the door to man-in-the-middle attacks.

Verify TLS is active and valid on both endpoints
# Check TLS certificate validity
curl -s -o /dev/null -w "TLS verify: %{ssl_verify_result}\n" \
  $SOURCE_VAULT_ADDR/v1/sys/health
# Expected output: TLS verify: 0  (0 means success)

curl -s -o /dev/null -w "TLS verify: %{ssl_verify_result}\n" \
  $DEST_VAULT_ADDR/v1/sys/health
# Expected output: TLS verify: 0

Use Short-Lived, Scoped Tokens

Create dedicated tokens for the migration with a TTL just long enough to complete the work. Scope them to the minimum required permissions.

Create migration-specific tokens with limited TTL
# Create a read-only token on the source (2-hour TTL)
VAULT_ADDR=$SOURCE_VAULT_ADDR vault token create \
  -policy="migration-read-only" \
  -ttl="2h" \
  -display-name="migration-azure-to-aws" \
  -no-default-policy=true

# Create a write-only token on the destination (2-hour TTL)
VAULT_ADDR=$DEST_VAULT_ADDR vault token create \
  -policy="migration-write-only" \
  -ttl="2h" \
  -display-name="migration-azure-to-aws" \
  -no-default-policy=true

Audit Logging

Confirm that audit devices are active on both Vaults before starting. Every kv/get on the source and every kv/put on the destination will be logged with timestamps, client tokens, and request payloads (HMAC-hashed by default).

Verify audit devices are enabled
VAULT_ADDR=$SOURCE_VAULT_ADDR VAULT_TOKEN=$SOURCE_VAULT_TOKEN \
  vault audit list -detailed

VAULT_ADDR=$DEST_VAULT_ADDR VAULT_TOKEN=$DEST_VAULT_TOKEN \
  vault audit list -detailed

Securely Clean Up Temporary Files

Any JSON, HCL, or encrypted files created during the migration must be securely deleted. Standard rm does not overwrite the data on disk — use shred instead.

Securely delete all temporary migration files
# Overwrite and delete all migration artifacts
shred -vfz -n 3 /tmp/policy-*.hcl 2>/dev/null || true
shred -vfz -n 3 /tmp/secret-*.json 2>/dev/null || true
shred -vfz -n 3 /tmp/approle-*.json 2>/dev/null || true
shred -vfz -n 3 /tmp/token-role-*.json 2>/dev/null || true
shred -vfz -n 3 /tmp/*-encrypted.dat 2>/dev/null || true

# Clear shell history to remove any tokens from the session
history -c && history -w

Rotate Credentials Post-Migration

Once the migration is validated and applications are pointing to the new Vault on AWS, perform these post-migration security steps:

  • Revoke migration tokens on both Vaults immediately.
  • Rotate database passwords and API keys that were migrated. The act of reading them during migration increases their exposure risk.
  • Generate new AppRole secret_id values on the destination and update your CI/CD pipelines and application configurations.
  • Review audit logs on both Vaults for any unexpected access patterns during the migration window.
  • Disable or delete the transit encryption key used for the migration if you used Method 3.
Revoke migration tokens and clean up the transit key
# Revoke the source migration token
VAULT_ADDR=$SOURCE_VAULT_ADDR vault token revoke $SOURCE_VAULT_TOKEN

# Revoke the destination migration token
VAULT_ADDR=$DEST_VAULT_ADDR vault token revoke $DEST_VAULT_TOKEN

# Delete the transit migration key (if used)
VAULT_ADDR=$SOURCE_VAULT_ADDR vault delete transit/keys/migration-key \
  deletion_allowed=true
Final Reminder: Do not decommission the source Vault on Azure until you have fully validated the destination, updated all application configurations, and confirmed that no workloads are still reading from the old instance. Keep the source running in read-only mode for at least one full release cycle as a safety net. Monitor its audit log — if any application still hits it, you have a missed dependency.
