Building a GitOps Pipeline with ArgoCD & GitHub Actions

How I implemented a fully automated GitOps workflow — from code commit to production deployment — using ArgoCD for continuous delivery and GitHub Actions for CI.

What is GitOps?

GitOps is a paradigm where Git serves as the single source of truth for both application code and infrastructure. Instead of pushing deployments imperatively (CI triggers kubectl apply), GitOps uses a pull-based model where an agent running inside the cluster continuously reconciles the actual state with the desired state defined in Git.

The key principles are: declarative configuration stored in Git, automated reconciliation, and drift detection. If someone manually changes a resource in the cluster, the GitOps agent will revert it to match what's in the repository.

Architecture Overview

Our pipeline separates concerns between CI and CD:

  • GitHub Actions handles CI — building, testing, scanning, and pushing container images
  • ArgoCD handles CD — deploying to Kubernetes by syncing from the Git manifests repository

The flow works like this: developer pushes code → GitHub Actions builds and pushes a Docker image → CI updates the image tag in the Kubernetes manifests repo → ArgoCD detects the change and deploys it.

GitHub Actions CI Pipeline

Here's the GitHub Actions workflow that builds, scans, and pushes the image, then updates the manifests repository:

name: CI Pipeline
on:
  push:
    branches: [main]

env:
  IMAGE: ghcr.io/myorg/api-server

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    - name: Run tests
      run: go test ./... -v -race -coverprofile=coverage.out

    - name: Build Docker image
      run: |
        TAG=${{ github.sha }}
        docker build -t $IMAGE:$TAG .

    - name: Scan with Trivy
      uses: aquasecurity/trivy-action@master
      with:
        image-ref: ${{ env.IMAGE }}:${{ github.sha }}
        severity: CRITICAL,HIGH
        exit-code: "1"

    - name: Push to registry
      run: |
        echo ${{ secrets.GHCR_TOKEN }} | docker login ghcr.io -u $GITHUB_ACTOR --password-stdin
        docker push $IMAGE:${{ github.sha }}

    - name: Update manifests repo
      run: |
        git clone https://x-access-token:${{ secrets.MANIFEST_TOKEN }}@github.com/myorg/k8s-manifests.git
        cd k8s-manifests
        sed -i "s|image:.*|image: $IMAGE:${{ github.sha }}|" apps/api-server/deployment.yaml
        git commit -am "chore: update api-server to ${{ github.sha }}"
        git pushYAML
Pro Tip

Never put Kubernetes manifests in the same repo as your application code. Separating them means ArgoCD only watches the manifests repo, and a CI build doesn't accidentally trigger a deployment loop.

Setting Up ArgoCD

Install ArgoCD into your cluster and create an Application resource that points to your manifests repository:

# Install ArgoCD
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Get initial admin password
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -dShell

ArgoCD Application Manifest

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-server
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/myorg/k8s-manifests.git
    targetRevision: main
    path: apps/api-server
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
    - CreateNamespace=trueYAML

With selfHeal: true, ArgoCD will automatically revert any manual changes made directly to the cluster. This ensures Git remains the single source of truth.

Canary Deployments

Using Argo Rollouts alongside ArgoCD, we can implement canary deployments that gradually shift traffic to the new version:

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: api-server
spec:
  strategy:
    canary:
      steps:
      - setWeight: 10
      - pause: {duration: 5m}
      - setWeight: 30
      - pause: {duration: 5m}
      - setWeight: 60
      - pause: {duration: 5m}
      analysis:
        templates:
        - templateName: success-rate
        startingStep: 1YAML

Automated Rollbacks

If the canary analysis detects an increase in error rates, Argo Rollouts automatically rolls back to the previous stable version. The analysis template queries Prometheus:

apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
  - name: success-rate
    interval: 60s
    successCondition: result[0] >= 0.95
    provider:
      prometheus:
        address: http://prometheus.monitoring:9090
        query: |
          sum(rate(http_requests_total{status=~"2.."}[5m])) /
          sum(rate(http_requests_total[5m]))YAML

Lessons Learned

  • Separate CI from CD repositories. This prevents circular triggers and makes rollbacks as simple as reverting a Git commit in the manifests repo.
  • Use App of Apps pattern for managing multiple ArgoCD applications. One parent Application points to a directory containing child Application manifests.
  • Seal your secrets. Never store plain secrets in Git. Use Sealed Secrets or External Secrets Operator to safely store encrypted secrets in the manifests repo.
  • Start without auto-sync. Enable manual sync first to build confidence, then enable auto-sync with selfHeal once the team is comfortable.
  • Monitor sync status. Set up Slack/PagerDuty alerts for ArgoCD sync failures using the built-in notifications engine.

GitOps isn't just a deployment strategy — it's an operational model. The real power is in auditability: every change to production is a Git commit with an author, timestamp, and review trail.
