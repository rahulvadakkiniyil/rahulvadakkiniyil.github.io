Migrating from NGINX Ingress Controller to Istio: A Production Playbook

How we replaced NGINX Ingress with Istio's service mesh across 200+ microservices — covering the architecture shift, traffic migration strategy, mTLS rollout, and the production gotchas that caught us off guard.

Why We Migrated

NGINX Ingress Controller served us well for two years. It handled TLS termination, path-based routing, and rate limiting across our EKS clusters. But as we scaled to 200+ microservices, we kept running into limitations:

  • No service-to-service traffic control. NGINX only manages north-south traffic (external to cluster). East-west traffic between microservices was completely unmanaged — no retries, no circuit breaking, no traffic splitting.
  • No mutual TLS. Services talked to each other over plain HTTP inside the cluster. Our security team flagged this as a compliance risk — we needed encryption in transit for all internal communication.
  • Limited observability. NGINX gave us request-level metrics at the ingress layer, but we had zero visibility into inter-service latency, error rates, or dependency graphs without instrumenting every application.
  • Canary deployments were fragile. We had hacked together a canary system using NGINX annotations and custom Lua scripts. It worked, but was brittle, hard to debug, and impossible for other teams to use without our help.

Istio solved all of these problems at the infrastructure layer, without requiring application code changes. The decision wasn't "NGINX is bad" — it was "we've outgrown what an ingress controller alone can provide."

NGINX Ingress vs Istio: Key Differences

Understanding the fundamental difference is critical before migrating. These are not the same category of tool.

Capability NGINX Ingress Istio
Traffic scope North-south only North-south + east-west
mTLS Manual cert management Automatic, zero-config
Traffic splitting Annotation-based (limited) VirtualService (fine-grained)
Circuit breaking Not supported DestinationRule
Observability Ingress metrics only Full mesh telemetry
Resource overhead Low (~50MB per pod) Higher (~100MB sidecar per pod)
Complexity Simple, well-understood Steep learning curve

NGINX Ingress is an ingress controller — it routes external traffic into your cluster. Istio is a service mesh — it manages all traffic between every service, including ingress. Istio uses Envoy proxy sidecars injected into every pod, giving it full visibility and control over the entire communication graph.

Istio Architecture Overview

Before diving into the migration, it's important to understand what Istio deploys into your cluster:

  • istiod (Control Plane) — The single binary that handles service discovery, certificate management, and pushing Envoy configurations to all sidecars. It replaces the older Pilot, Citadel, and Galley components.
  • Envoy Sidecar Proxies (Data Plane) — Automatically injected into every pod. All inbound and outbound traffic flows through this proxy, which enforces routing rules, mTLS, retries, and collects telemetry.
  • Istio Ingress Gateway — Replaces NGINX Ingress. A standalone Envoy deployment at the edge of the mesh that handles external traffic. Configured via Gateway and VirtualService resources.
Note

Istio's ambient mode (available since Istio 1.22) removes the need for sidecar proxies by using a per-node ztunnel proxy. This significantly reduces resource overhead. However, for full L7 traffic management features, sidecar mode is still required as of early 2026.

Installing Istio on EKS

We used istioctl for installation rather than the Helm chart, as it gives better control over the installation profile and makes upgrades more predictable:

# Download istioctl
curl -L https://istio.io/downloadIstio | ISTIO_VERSION=1.23.0 sh -
cd istio-1.23.0
export PATH=$PWD/bin:$PATH

# Install with production profile
istioctl install --set profile=default \
  --set meshConfig.accessLogFile="/dev/stdout" \
  --set meshConfig.enableTracing=true \
  --set meshConfig.defaultConfig.holdApplicationUntilProxyStarts=true \
  --set values.pilot.resources.requests.cpu=500m \
  --set values.pilot.resources.requests.memory=2Gi \
  --set values.pilot.resources.limits.cpu=1000m \
  --set values.pilot.resources.limits.memory=4Gi \
  -y

# Verify installation
istioctl verify-install
kubectl get pods -n istio-systemShell
Pro Tip

Always set holdApplicationUntilProxyStarts: true in production. Without this, your application container can start before the Envoy sidecar is ready, causing connection failures during startup. This is the single most common issue teams hit when adopting Istio.

Istio Ingress Gateway with AWS NLB

The Istio Ingress Gateway needs a LoadBalancer service. On EKS, we use an AWS Network Load Balancer for better performance and static IP support:

apiVersion: v1
kind: Service
metadata:
  name: istio-ingressgateway
  namespace: istio-system
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"
    service.beta.kubernetes.io/aws-load-balancer-cross-zone-load-balancing-enabled: "true"
    service.beta.kubernetes.io/aws-load-balancer-backend-protocol: "tcp"
spec:
  type: LoadBalancer
  selector:
    istio: ingressgateway
  ports:
  - name: http
    port: 80
    targetPort: 8080
  - name: https
    port: 443
    targetPort: 8443YAML

Sidecar Injection Strategy

Don't enable sidecar injection cluster-wide on day one. We used a phased approach, namespace by namespace:

# Phase 1: Enable injection for a single non-critical namespace
kubectl label namespace staging istio-injection=enabled --overwrite

# Restart pods to inject sidecars
kubectl rollout restart deployment -n staging

# Verify sidecars are running (each pod should show 2/2 containers)
kubectl get pods -n staging

# Phase 2: After validation, enable for production namespaces one at a time
kubectl label namespace production-api istio-injection=enabled --overwrite
kubectl rollout restart deployment -n production-api

# To exclude specific pods from injection (e.g., Jobs, CronJobs)
# Add this annotation to the pod spec:
# sidecar.istio.io/inject: "false"Shell
Warning

CronJobs and one-shot Jobs should have sidecar injection disabled. The Envoy sidecar never terminates on its own, so your Job will stay in Running state forever even after the main container completes. Use the annotation sidecar.istio.io/inject: "false" on these workloads.

Converting Ingress to VirtualService

This is the core of the migration — translating every NGINX Ingress resource into Istio's Gateway + VirtualService model. Here's a real before/after example:

Before: NGINX Ingress

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-server
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/rate-limit-rps: "100"
    nginx.ingress.kubernetes.io/cors-allow-origin: "https://app.example.com"
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /api(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: api-server
            port:
              number: 8080
      - path: /auth(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: auth-service
            port:
              number: 8080YAML

After: Istio Gateway + VirtualService

# Gateway — shared across multiple VirtualServices
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: api-gateway
  namespace: istio-system
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 443
      name: https
      protocol: HTTPS
    tls:
      mode: SIMPLE
      credentialName: api-tls
    hosts:
    - api.example.com
  - port:
      number: 80
      name: http
      protocol: HTTP
    tls:
      httpsRedirect: true
    hosts:
    - api.example.com
---
# VirtualService — routing rules
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api-routes
  namespace: production
spec:
  hosts:
  - api.example.com
  gateways:
  - istio-system/api-gateway
  http:
  - match:
    - uri:
        prefix: /api
    rewrite:
      uri: /
    route:
    - destination:
        host: api-server.production.svc.cluster.local
        port:
          number: 8080
    timeout: 30s
    retries:
      attempts: 3
      perTryTimeout: 10s
      retryOn: gateway-error,connect-failure,refused-stream
  - match:
    - uri:
        prefix: /auth
    rewrite:
      uri: /
    route:
    - destination:
        host: auth-service.production.svc.cluster.local
        port:
          number: 8080YAML

Notice how Istio gives us built-in retries and timeouts that would have required custom NGINX configuration snippets. The VirtualService also works for internal service-to-service routing — not just ingress traffic.

Pro Tip

Use fully qualified service names (service.namespace.svc.cluster.local) in VirtualService destinations. Short names can cause ambiguous resolution issues when services exist in multiple namespaces.

Advanced Traffic Management

This is where Istio truly shines compared to NGINX Ingress. Here are the patterns we use daily:

Canary Deployments with Traffic Splitting

apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api-server-canary
spec:
  hosts:
  - api-server
  http:
  - route:
    - destination:
        host: api-server
        subset: stable
      weight: 90
    - destination:
        host: api-server
        subset: canary
      weight: 10
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api-server
spec:
  host: api-server
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100
      http:
        h2UpgradePolicy: DEFAULT
        maxRequestsPerConnection: 10
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 30s
      baseEjectionTime: 60s
      maxEjectionPercent: 50
  subsets:
  - name: stable
    labels:
      version: v1
  - name: canary
    labels:
      version: v2YAML

Header-Based Routing for Testing

Route internal testers to the canary version without affecting real users:

http:
- match:
  - headers:
      x-canary:
        exact: "true"
  route:
  - destination:
      host: api-server
      subset: canary
- route:
  - destination:
      host: api-server
      subset: stableYAML

With NGINX Ingress, this required custom Lua scripts and ConfigMap hacks. In Istio, it's a few lines of YAML.

mTLS Rollout

One of the biggest wins of moving to Istio is automatic mutual TLS between all services. But rolling it out in production requires a careful phased approach:

Phase 1: Permissive Mode (Accept Both)

apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: PERMISSIVE  # Accepts both mTLS and plaintextYAML

Start here. This allows services with sidecars to communicate via mTLS while still accepting plaintext from services that haven't been injected yet.

Phase 2: Validate with Kiali

# Check which connections are using mTLS
istioctl x describe pod $POD_NAME -n production

# Look for "mTLS" in the output. Any plaintext connections
# indicate services that still need sidecar injection.Shell

Phase 3: Strict Mode (Enforce mTLS)

# Only enable strict AFTER all services in the namespace have sidecars
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: production
spec:
  mtls:
    mode: STRICT  # Rejects all plaintext trafficYAML
Warning

Don't jump straight to STRICT mode mesh-wide. If any service doesn't have a sidecar (monitoring agents, legacy services, external integrations), it will be blocked from communicating. Enable STRICT per-namespace only after verifying 100% sidecar coverage with istioctl analyze.

Observability with Istio

Istio generates detailed telemetry for every request that flows through the mesh — without any application instrumentation. We integrated it with our existing Prometheus and Grafana stack:

Key Metrics Available Out of the Box

# Request rate by service
sum(rate(istio_requests_total{reporter="destination"}[5m])) by (destination_service_name)

# P99 latency by service
histogram_quantile(0.99,
  sum(rate(istio_request_duration_milliseconds_bucket{reporter="destination"}[5m]))
  by (destination_service_name, le)
)

# Error rate (5xx responses)
sum(rate(istio_requests_total{response_code=~"5..",reporter="destination"}[5m]))
/
sum(rate(istio_requests_total{reporter="destination"}[5m]))

# TCP connections by service
sum(istio_tcp_connections_opened_total) by (destination_service_name)PromQL

Distributed Tracing

Istio automatically generates trace spans for every request. We configured it to export to Jaeger:

apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  meshConfig:
    enableTracing: true
    extensionProviders:
    - name: jaeger
      opentelemetry:
        service: jaeger-collector.observability.svc.cluster.local
        port: 4317
    defaultConfig:
      tracing:
        sampling: 10  # Sample 10% of requests in productionYAML

The biggest observability improvement was being able to see the full dependency graph of our 200+ services — something that was completely invisible with NGINX Ingress.

Zero-Downtime Migration Strategy

We ran NGINX Ingress and Istio Ingress Gateway in parallel for 4 weeks before fully cutting over. Here's the strategy:

  1. Week 1: Install Istio, enable sidecar injection in staging namespaces. Run all integration tests. Validate that existing NGINX routing still works with sidecars present.
  2. Week 2: Create Istio Gateway + VirtualService equivalents for all NGINX Ingress resources. Deploy Istio Ingress Gateway with its own NLB. Route internal test traffic to Istio using a separate DNS entry (e.g., api-istio.example.com).
  3. Week 3: Use Route 53 weighted routing to send 10% of real traffic through Istio, 90% through NGINX. Monitor error rates and latency on both paths. Gradually increase Istio's weight: 10% → 30% → 50% → 80%.
  4. Week 4: Switch DNS to 100% Istio. Keep NGINX running but receiving no traffic for one week as a rollback safety net. Once stable, remove NGINX Ingress Controller entirely.
# Route 53 weighted routing — gradual cutover
# NGINX record (weight reduces over time)
api.example.com  A  ALIAS  nginx-nlb-xxxx.elb.amazonaws.com  weight: 0
# Istio record (weight increases over time)
api.example.com  A  ALIAS  istio-nlb-yyyy.elb.amazonaws.com  weight: 100DNS
Pro Tip

During the parallel-run phase, tag your Prometheus metrics with a gateway=nginx|istio label so you can compare latency, error rates, and throughput side-by-side in Grafana. This gives you hard data for go/no-go decisions.

Production Gotchas

After running Istio in production for 6 months across multiple EKS clusters, these are the issues that caught us off guard:

  • Memory overhead is real. Each Envoy sidecar consumes ~50-100MB of memory. With 200+ services running 3+ replicas each, that's an additional 30-60GB of memory cluster-wide. Budget for this before migrating.
  • Startup ordering matters. Without holdApplicationUntilProxyStarts, apps that make network calls during initialization will fail because the sidecar isn't ready yet. We lost 2 hours debugging this on day one.
  • 503 errors on HPA scale-up. When HPA rapidly creates new pods, there's a brief window where the pod is receiving traffic but the sidecar hasn't finished configuring routes. Fix this with proper readiness probes on the sidecar: sidecar.istio.io/rewriteAppHTTPProbers: "true".
  • Headless services need special handling. Istio doesn't manage traffic for headless services (like StatefulSets with clusterIP: None) the same way. You may need to add traffic.sidecar.istio.io/excludeOutboundIPRanges for databases and message brokers.
  • AWS ALB Ingress doesn't work with sidecars. If you use the AWS Load Balancer Controller for ALB-based ingress, the health checks will fail once sidecars are injected. Switch to NLB or use Istio's gateway instead.
  • Upgrade istiod carefully. Istio control plane upgrades are non-disruptive, but the data plane (sidecars) needs a rolling restart. Use canary upgrades with revision-based installations to avoid restarting all pods simultaneously.
  • External services need ServiceEntry. Any external API your services call (Stripe, Twilio, etc.) must be registered as a ServiceEntry or it will be blocked by Istio's default outbound traffic policy. We forgot about this and broke payment processing on our first deploy.

ServiceEntry for External APIs

apiVersion: networking.istio.io/v1beta1
kind: ServiceEntry
metadata:
  name: stripe-api
spec:
  hosts:
  - api.stripe.com
  ports:
  - number: 443
    name: https
    protocol: TLS
  resolution: DNS
  location: MESH_EXTERNALYAML

Results & Lessons Learned

After completing the migration and running Istio in production for 6 months:

  • mTLS coverage: 100%. All inter-service communication is now encrypted in transit. Security audit passed without findings.
  • Canary deployment time: 5 minutes (down from 30+ minutes with our hacky NGINX Lua scripts). Any team can run a canary by editing a VirtualService.
  • MTTR reduced by 40%. With full mesh telemetry and distributed tracing, we can pinpoint failing services in seconds instead of grepping logs across 200 services.
  • Zero customer-facing outages during the 4-week migration, thanks to the parallel-run strategy.
  • Cluster memory usage increased by ~18% due to sidecar overhead. This was expected and budgeted for.

The migration from NGINX Ingress to Istio isn't just swapping one proxy for another — it's a fundamental shift from managing edge traffic to managing all traffic. The operational complexity is higher, but the capabilities you gain in traffic control, security, and observability are transformative. Start with a clear "why", run in parallel, and migrate namespace by namespace.
