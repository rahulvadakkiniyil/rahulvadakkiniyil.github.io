How to Use AWS Secrets & Configuration Provider with Your Kubernetes Secrets Store CSI Driver

Mount AWS Secrets Manager and SSM Parameter Store values directly into your pods as files — no more base64-encoded Kubernetes Secrets or sidecar hacks.

The Problem with Kubernetes Secrets

Kubernetes Secrets are just base64-encoded data stored in etcd. They're not encrypted by default, they're visible to anyone with RBAC access to the namespace, and managing them at scale across multiple clusters is painful. You end up with secrets scattered across Helm values, sealed-secrets CRDs, and external-secrets operators — each adding complexity.

The Secrets Store CSI Driver takes a different approach. Instead of syncing secrets into Kubernetes, it mounts them directly from an external secrets manager (like AWS Secrets Manager or SSM Parameter Store) as volumes in your pods. The secret never lives in etcd — it's fetched at pod startup and mounted as a file.

How It Works — Architecture Overview

The setup involves three components working together:

  • Secrets Store CSI Driver — A DaemonSet that implements the CSI interface. When a pod with a CSI volume is scheduled, the driver calls the provider to fetch secrets and mounts them as a tmpfs volume.
  • AWS Secrets & Configuration Provider (ASCP) — A plugin that the CSI driver calls to retrieve secrets from AWS Secrets Manager and SSM Parameter Store. It authenticates using IAM Roles for Service Accounts (IRSA).
  • SecretProviderClass — A custom resource that tells the driver which secrets to fetch and how to map them into files.

The flow is: Pod scheduled → kubelet calls CSI driver → CSI driver calls ASCP → ASCP assumes IAM role via IRSA → fetches secret from AWS → mounts as file in pod.

Prerequisites

  • An EKS cluster (v1.24+) with OIDC provider configured
  • kubectl and helm installed
  • AWS CLI configured with sufficient permissions
  • eksctl (for easy IRSA setup)

Step 1: Install the Secrets Store CSI Driver

Install the CSI driver using Helm. The driver runs as a DaemonSet on every node:

helm repo add secrets-store-csi-driver \
  https://kubernetes-sigs.github.io/secrets-store-csi-driver/charts

helm install csi-secrets-store \
  secrets-store-csi-driver/secrets-store-csi-driver \
  --namespace kube-system \
  --set syncSecret.enabled=true \
  --set enableSecretRotation=true \
  --set rotationPollInterval=3600sShell
Note

syncSecret.enabled=true lets you optionally sync mounted secrets as native Kubernetes Secrets (useful for environment variables). enableSecretRotation=true enables automatic rotation polling.

Verify the driver pods are running:

kubectl get pods -n kube-system -l app=secrets-store-csi-driver

NAME                                 READY   STATUS    RESTARTS   AGE
csi-secrets-store-xxxxx              3/3     Running   0          45s
csi-secrets-store-yyyyy              3/3     Running   0          45sShell

Step 2: Install the AWS Provider (ASCP)

The ASCP is the bridge between the CSI driver and AWS. Install it using kubectl:

kubectl apply -f https://raw.githubusercontent.com/aws/secrets-store-csi-driver-provider-aws/main/deployment/aws-provider-installer.yamlShell

This deploys the ASCP as a DaemonSet in kube-system. Verify it's running:

kubectl get daemonset -n kube-system -l app=csi-secrets-store-provider-aws

NAME                                  DESIRED   CURRENT   READY   AGE
csi-secrets-store-provider-aws        3         3         3       30sShell

Step 3: Configure IAM Roles for Service Accounts (IRSA)

ASCP needs an IAM role to read secrets from AWS. The cleanest way to do this is IRSA — it maps a Kubernetes ServiceAccount to an IAM role without needing access keys.

Create the IAM Policy

cat <<'EOF' > secretsmanager-policy.json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "secretsmanager:GetSecretValue",
        "secretsmanager:DescribeSecret"
      ],
      "Resource": "arn:aws:secretsmanager:us-east-1:123456789012:secret:myapp/*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "ssm:GetParameter",
        "ssm:GetParameters"
      ],
      "Resource": "arn:aws:ssm:us-east-1:123456789012:parameter/myapp/*"
    }
  ]
}
EOF

aws iam create-policy \
  --policy-name EKSSecretsManagerPolicy \
  --policy-document file://secretsmanager-policy.jsonShell
Warning

Scope the IAM policy to specific secret ARNs — never use * as the resource. Each application's ServiceAccount should only have access to the secrets it needs.

Create the Service Account with IRSA

eksctl create iamserviceaccount \
  --name myapp-secrets-sa \
  --namespace production \
  --cluster my-production-cluster \
  --attach-policy-arn arn:aws:iam::123456789012:policy/EKSSecretsManagerPolicy \
  --approve \
  --override-existing-serviceaccountsShell

This creates a Kubernetes ServiceAccount annotated with the IAM role ARN. Any pod using this ServiceAccount will automatically assume the role via the EKS OIDC provider.

Step 4: Create a Secret in AWS Secrets Manager

If you don't already have a secret, create one for testing:

aws secretsmanager create-secret \
  --name myapp/database-credentials \
  --secret-string '{"username":"admin","password":"S3cureP@ss!","host":"mydb.cluster-abc123.us-east-1.rds.amazonaws.com","port":"5432"}'Shell

You can also create an SSM parameter for non-sensitive configuration:

aws ssm put-parameter \
  --name "/myapp/config/api-endpoint" \
  --value "https://api.example.com/v2" \
  --type StringShell

Step 5: Create a SecretProviderClass

The SecretProviderClass is the heart of the configuration. It tells the CSI driver which secrets to fetch from AWS and how to mount them:

apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: myapp-aws-secrets
  namespace: production
spec:
  provider: aws
  parameters:
    objects: |
      - objectName: "myapp/database-credentials"
        objectType: "secretsmanager"
        jmesPath:
          - path: username
            objectAlias: db-username
          - path: password
            objectAlias: db-password
          - path: host
            objectAlias: db-host
          - path: port
            objectAlias: db-port
      - objectName: "/myapp/config/api-endpoint"
        objectType: "ssmparameter"YAML
Pro Tip

Use jmesPath to extract individual keys from a JSON secret. This lets you store related credentials as a single Secrets Manager secret (saving costs) while mounting each field as a separate file in the pod.

Step 6: Mount Secrets into Your Pod

Now reference the SecretProviderClass as a CSI volume in your Deployment:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      serviceAccountName: myapp-secrets-sa
      containers:
      - name: myapp
        image: myapp:latest
        volumeMounts:
        - name: secrets-volume
          mountPath: "/mnt/secrets"
          readOnly: true
      volumes:
      - name: secrets-volume
        csi:
          driver: secrets-store.csi.k8s.io
          readOnly: true
          volumeAttributes:
            secretProviderClass: "myapp-aws-secrets"YAML

After deploying, you can verify the secrets are mounted:

kubectl exec -n production deploy/myapp -- ls /mnt/secrets/

db-username
db-password
db-host
db-port
/myapp/config/api-endpoint

kubectl exec -n production deploy/myapp -- cat /mnt/secrets/db-username

adminShell

Step 7: Sync as Kubernetes Secrets (Optional)

Some applications read config from environment variables, not files. You can tell the CSI driver to also create a native Kubernetes Secret that mirrors the mounted data:

apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: myapp-aws-secrets
  namespace: production
spec:
  provider: aws
  parameters:
    objects: |
      - objectName: "myapp/database-credentials"
        objectType: "secretsmanager"
        jmesPath:
          - path: username
            objectAlias: db-username
          - path: password
            objectAlias: db-password
  secretObjects:
  - secretName: myapp-db-creds
    type: Opaque
    data:
    - objectName: db-username
      key: DB_USERNAME
    - objectName: db-password
      key: DB_PASSWORDYAML

Then reference the synced Secret in your Deployment as environment variables:

containers:
- name: myapp
  image: myapp:latest
  envFrom:
  - secretRef:
      name: myapp-db-creds
  volumeMounts:
  - name: secrets-volume
    mountPath: "/mnt/secrets"
    readOnly: trueYAML
Warning

The synced Kubernetes Secret is only created when a pod mounts the volume. If no pods are using the SecretProviderClass, the K8s Secret won't exist. This means you can't reference it in other pods that don't mount the CSI volume.

Secret Rotation

When you enabled enableSecretRotation=true during installation, the CSI driver will periodically re-fetch secrets from AWS. The rotation cycle works like this:

  • The driver polls AWS every rotationPollInterval (we set it to 3600s)
  • If the secret value has changed, the mounted file is updated in-place
  • If secretObjects is configured, the synced K8s Secret is also updated
  • Your application needs to watch for file changes or periodically re-read the mounted files
# Rotate the secret in AWS
aws secretsmanager update-secret \
  --secret-id myapp/database-credentials \
  --secret-string '{"username":"admin","password":"N3wS3cureP@ss!","host":"mydb.cluster-abc123.us-east-1.rds.amazonaws.com","port":"5432"}'

# Wait for the rotation interval, then verify the pod has the new value
kubectl exec -n production deploy/myapp -- cat /mnt/secrets/db-password

N3wS3cureP@ss!Shell
Pro Tip

For zero-downtime password rotation with RDS, use AWS Secrets Manager's native rotation with a Lambda function. This rotates the credential in both RDS and Secrets Manager atomically, then the CSI driver picks up the new value on its next poll.

Production Gotchas

Lessons from running ASCP in production across multiple EKS clusters:

  • Pod startup latency. The CSI driver fetches secrets during pod init, adding 1-3 seconds to startup time. This matters for fast-scaling workloads — factor it into HPA response time calculations.
  • IRSA token expiration. IRSA tokens expire after 12 hours by default. Long-running pods won't have issues (tokens are auto-refreshed), but if the OIDC provider is misconfigured, pods will fail to fetch secrets silently after token expiry.
  • DaemonSet dependency. Both the CSI driver and ASCP run as DaemonSets. If either is not running on a node, pods scheduled there will hang in ContainerCreating. Set proper priorityClasses and monitor DaemonSet health.
  • Secret size limits. AWS Secrets Manager has a 64KB limit per secret. If you hit this, split your secret into multiple entries and mount them separately.
  • Cost awareness. Each GetSecretValue API call costs $0.05 per 10,000 calls. With rotation enabled across many pods, costs can add up. Tune rotationPollInterval based on how frequently your secrets actually change.
  • Failover behavior. If the CSI driver can't reach AWS during pod startup, the pod will fail to start. There's no cached fallback. Ensure your VPC has reliable connectivity to AWS APIs (use VPC endpoints for Secrets Manager).
  • Namespace isolation. Create separate SecretProviderClass resources per namespace. Never share a single SPC across namespaces — it couples their IAM permissions and blast radius.

Recommended VPC Endpoints

To avoid secrets traffic going over the public internet, create VPC endpoints for the services ASCP calls:

# Create VPC endpoints for private connectivity
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-abc123 \
  --service-name com.amazonaws.us-east-1.secretsmanager \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-111 subnet-222 \
  --security-group-ids sg-secrets-endpoint

aws ec2 create-vpc-endpoint \
  --vpc-id vpc-abc123 \
  --service-name com.amazonaws.us-east-1.ssm \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-111 subnet-222 \
  --security-group-ids sg-ssm-endpointShell

The Secrets Store CSI Driver with ASCP is the cleanest way to bridge AWS secrets into Kubernetes. It eliminates the need to store sensitive data in etcd, works natively with IAM, and keeps your secrets management centralized in AWS where you already have audit trails, rotation policies, and encryption at rest.
