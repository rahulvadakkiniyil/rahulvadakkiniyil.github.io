Jenkins Shared Libraries: Standardizing Pipelines Across Teams

How I built a shared library to enforce consistent pipeline stages across 20+ microservices

The Problem: Duplicated Pipeline Logic

When I joined the platform engineering team, we had over 20 microservices, each with its own Jenkinsfile. Every team had independently crafted their CI/CD pipelines, and the results were predictable: wildly inconsistent build stages, scattered deployment logic, and zero standardization. Some teams had security scanning, others didn't. Some ran integration tests, others skipped them entirely. Updating a common pattern — like switching Docker registries — meant opening pull requests against every single repository.

The maintenance burden was crushing. A simple change to our artifact publishing process required coordinating across six different teams. Onboarding a new microservice took days of copying and tweaking Jenkinsfile snippets from existing projects. We needed a single source of truth for our pipeline logic, and that's exactly what Jenkins Shared Libraries gave us.

The duplication wasn't just an inconvenience — it was a real operational risk. When a critical vulnerability was discovered in our container base images, it took nearly two weeks to update all pipelines to include the new scanning step. That timeline was unacceptable, and it became the catalyst for building a shared library.

What Are Shared Libraries?

Jenkins Shared Libraries are a mechanism for extracting reusable pipeline code into a standalone Git repository that can be loaded by any Jenkinsfile across your organization. Instead of duplicating Groovy code in every project, you define common steps, stages, and utilities in one place.

The library follows a specific directory structure:

vars/           // Global variables and custom pipeline steps
  buildApp.groovy
  deployService.groovy
  notifySlack.groovy
src/            // Helper classes (standard Groovy/Java)
  org/company/
    Config.groovy
    DockerUtils.groovy
resources/      // Non-Groovy files (configs, templates)
  deploy-template.yaml
  sonar-config.propertiesDirectory Structure

The vars/ directory is where most of the magic happens. Each .groovy file in this directory becomes a globally available step in your pipelines. The src/ directory holds traditional Groovy classes for more complex logic, and resources/ stores static files like configuration templates that can be loaded at runtime using the libraryResource step.

Note

Shared Libraries must be configured in Jenkins under Manage Jenkins → Configure System → Global Pipeline Libraries. You specify the library name, Git repository URL, and default branch. Libraries can also be configured at the folder level for team-specific customizations.

Writing Your First Shared Step

Let's start with a practical example. One of the most common duplicated patterns was building and pushing Docker images. Every team had slight variations of the same logic scattered across their Jenkinsfiles. Here's how we consolidated it into a shared step:

// vars/buildApp.groovy
def call(Map config = [:]) {
    def appName = config.get('appName', env.JOB_BASE_NAME)
    def registry = config.get('registry', 'registry.company.com')
    def tag = config.get('tag', env.BUILD_NUMBER)
    def dockerfile = config.get('dockerfile', 'Dockerfile')

    stage('Build Docker Image') {
        steps {
            sh """
                docker build -t ${registry}/${appName}:${tag} \
                    -f ${dockerfile} \
                    --build-arg BUILD_NUMBER=${tag} .
            """
        }
    }

    stage('Push to Registry') {
        steps {
            withCredentials([usernamePassword(
                credentialsId: 'docker-registry-creds',
                usernameVariable: 'DOCKER_USER',
                passwordVariable: 'DOCKER_PASS'
            )]) {
                sh """
                    echo \$DOCKER_PASS | docker login ${registry} -u \$DOCKER_USER --password-stdin
                    docker push ${registry}/${appName}:${tag}
                """
            }
        }
    }

    return "${registry}/${appName}:${tag}"
}Groovy

The def call() pattern is the key convention. When Jenkins encounters buildApp(appName: 'my-service') in a Jenkinsfile, it looks for vars/buildApp.groovy and invokes its call method. The Map parameter allows flexible configuration with sensible defaults, so teams only override what they need.

Pro Tip

Always provide default values for your shared step parameters. This keeps the consuming Jenkinsfile clean and reduces the barrier to adoption. Teams should be able to call buildApp() with zero arguments and get a working build for the common case.

Creating Standardized Stages

Individual steps are useful, but the real power comes from composing them into a full standardized pipeline template. We created a standardPipeline step that enforces a consistent set of stages across all services:

// vars/standardPipeline.groovy
def call(Map config) {
    pipeline {
        agent { label config.get('agent', 'docker') }

        stages {
            stage('Checkout') {
                steps { checkout scm }
            }

            stage('Build') {
                steps {
                    buildApp(
                        appName: config.appName,
                        registry: config.get('registry')
                    )
                }
            }

            stage('Unit Tests') {
                steps {
                    sh './gradlew test'
                    junit '**/build/test-results/**/*.xml'
                }
            }

            stage('Security Scan') {
                steps {
                    sh "trivy image ${config.appName}:${env.BUILD_NUMBER}"
                }
            }

            stage('Deploy') {
                when { branch 'main' }
                steps {
                    deployService(
                        appName: config.appName,
                        environment: 'production',
                        namespace: config.get('namespace', 'default')
                    )
                }
            }
        }

        post {
            success { notifySlack(status: 'SUCCESS') }
            failure { notifySlack(status: 'FAILURE') }
        }
    }
}Groovy

This template enforces that every service goes through build, test, security scan, and deploy stages in the correct order. The security scan stage was the biggest win — before the shared library, only 4 out of 22 services had any form of container scanning. After rolling out the template, coverage hit 100% overnight.

Consuming in a Jenkinsfile

With the shared library in place, individual service Jenkinsfiles become remarkably simple. The @Library annotation loads the library, and teams only need to specify their service-specific configuration:

// Jenkinsfile for my-payment-service
@Library('platform-pipeline-lib') _

standardPipeline(
    appName: 'payment-service',
    registry: 'registry.company.com/payments',
    namespace: 'payments',
    agent: 'docker-large'
)Jenkinsfile

That's it. Five lines replace what used to be a 120-line Jenkinsfile. The underscore after the @Library annotation is required — it imports the library into the script scope. Teams can still add custom stages by wrapping the standardPipeline call or by using individual steps like buildApp() and deployService() directly for more control.

For teams that need to deviate slightly from the standard, we support overriding specific stages while still benefiting from the shared infrastructure:

@Library('platform-pipeline-lib@v2.3.0') _

// Pin to a specific version for stability
standardPipeline(
    appName: 'auth-service',
    skipSecurityScan: false,
    customTestCommand: './gradlew integrationTest',
    deployTargets: ['staging', 'production']
)Jenkinsfile
Note

Version-pinning your library with @Library('lib-name@v2.3.0') is strongly recommended for production services. This prevents unexpected breakages when the shared library is updated. Teams can upgrade on their own schedule after testing.

Testing the Library

A shared library used by 20+ services is critical infrastructure — it must be tested. We use the JenkinsPipelineUnit framework to write unit tests for our shared steps without needing a running Jenkins instance:

// test/groovy/BuildAppTest.groovy
import com.lesfurets.jenkins.unit.BasePipelineTest
import org.junit.Before
import org.junit.Test
import static org.junit.Assert.*

class BuildAppTest extends BasePipelineTest {

    @Before
    void setUp() {
        super.setUp()
        binding.setVariable('env', [
            JOB_BASE_NAME: 'test-app',
            BUILD_NUMBER: '42'
        ])
        helper.registerAllowedMethod('sh', [String], { cmd ->
            // Mock shell commands
        })
    }

    @Test
    void testBuildAppWithDefaults() {
        def script = loadScript('vars/buildApp.groovy')
        def result = script.call([:])

        assertEquals('registry.company.com/test-app:42', result)
        assertJobStatusSuccess()
    }

    @Test
    void testBuildAppWithCustomRegistry() {
        def script = loadScript('vars/buildApp.groovy')
        def result = script.call(registry: 'custom.registry.io')

        assertEquals('custom.registry.io/test-app:42', result)
    }
}Groovy

We also run the library's own CI pipeline that executes all unit tests on every commit. The test suite catches regressions before they reach any consuming service. Combined with semantic versioning, this gives teams confidence that library updates won't break their builds.

Results & Impact

After rolling out the shared library across all 22 microservices, the results exceeded our expectations:

  • 80% reduction in pipeline code. The average Jenkinsfile shrank from 120 lines to under 10 lines. Less code means fewer bugs and less maintenance.
  • Faster onboarding. New microservices go from repository creation to full CI/CD in under 30 minutes. Previously, it took 2-3 days of pipeline setup and debugging.
  • 100% security scan coverage. Every service now runs Trivy container scanning and SonarQube code analysis — enforced by the template, not by team discipline.
  • Single-point updates. Changing the Docker registry, updating the deployment strategy, or adding a new compliance step requires one PR to the shared library instead of 22 separate changes.
  • Consistent observability. All pipelines now report build metrics to Prometheus and send notifications to Slack using the same format, making it easy to build dashboards and track build health across the organization.

The shared library transformed our CI/CD from a collection of snowflake pipelines into a standardized, maintainable platform. The investment in building and testing it paid for itself within the first month.
