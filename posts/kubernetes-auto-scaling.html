Kubernetes Auto-Scaling: HPA, VPA & Cluster Autoscaler Explained

A comprehensive guide to scaling workloads in Kubernetes. Learn when to use each autoscaler, how to configure them, and the production gotchas nobody tells you about.

Why Auto-Scaling Matters

In a production Kubernetes environment, traffic patterns are rarely constant. You might see 10x spikes during peak hours, followed by near-zero activity at night. Without auto-scaling, you're either over-provisioning (wasting money) or under-provisioning (risking outages).

Kubernetes provides three complementary autoscaling mechanisms, each operating at a different level of the stack. Understanding when and how to use each one is critical for running cost-effective, reliable workloads.

Horizontal Pod Autoscaler (HPA)

The HPA automatically adjusts the number of pod replicas based on observed metrics. It's the most commonly used autoscaler and works by periodically querying the metrics API (default: every 15 seconds) and comparing current values against your defined targets.

How It Works

The HPA controller uses a simple formula to calculate desired replicas:

desiredReplicas = ceil(currentReplicas * (currentMetric / desiredMetric))

For example, if you have 3 replicas running at 80% CPU and your target is 50%, the HPA would scale to ceil(3 * 80/50) = 5 replicas.

Basic CPU-Based HPA

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: api-server-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 70
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Percent
        value: 10
        periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15YAML
Pro Tip

Always set behavior.scaleDown.stabilizationWindowSeconds to at least 300 seconds. This prevents the HPA from thrashing during brief traffic dips, which can cause cascading failures as pods are killed and restarted.

Custom Metrics with Prometheus

CPU and memory are often poor indicators of actual load. For HTTP services, requests per second (RPS) is usually a better metric. Using the Prometheus Adapter, you can scale on any custom metric:

metrics:
- type: Pods
  pods:
    metric:
      name: http_requests_per_second
    target:
      type: AverageValue
      averageValue: "100"YAML

Vertical Pod Autoscaler (VPA)

While HPA scales horizontally (more pods), VPA scales vertically (bigger pods). It automatically adjusts CPU and memory requests and limits for your containers based on actual usage patterns. This is particularly useful for workloads that can't be horizontally scaled, like databases or stateful applications.

VPA Modes

  • Off — VPA only provides recommendations, no automatic changes
  • Initial — VPA sets resources only at pod creation time
  • Auto — VPA evicts and recreates pods with updated resources (use with caution)
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: api-server-vpa
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api-server
  updatePolicy:
    updateMode: "Off"  # Start with recommendations only
  resourcePolicy:
    containerPolicies:
    - containerName: "*"
      minAllowed:
        cpu: "100m"
        memory: "128Mi"
      maxAllowed:
        cpu: "2"
        memory: "4Gi"YAML
Warning

Never use VPA in Auto mode together with HPA on CPU or memory metrics. They will fight each other — HPA wants more pods while VPA wants bigger pods. Use VPA in Off mode to get recommendations, then apply them manually.

Cluster Autoscaler

The Cluster Autoscaler operates at the infrastructure level. When pods can't be scheduled due to insufficient node resources, it provisions new nodes. When nodes are underutilized, it drains and removes them.

How It Decides to Scale

  • Scale Up: A pod is unschedulable because no node has enough resources. The autoscaler simulates adding a node from each node group and picks the best fit.
  • Scale Down: A node's utilization drops below 50% (configurable) for 10 minutes. All pods on it can be rescheduled elsewhere. The node has no local storage or pods with restrictive PDBs.

EKS Cluster Autoscaler Configuration

# Install via Helm
helm install cluster-autoscaler autoscaler/cluster-autoscaler \
  --namespace kube-system \
  --set autoDiscovery.clusterName=my-production-cluster \
  --set awsRegion=us-east-1 \
  --set extraArgs.balance-similar-node-groups=true \
  --set extraArgs.skip-nodes-with-local-storage=false \
  --set extraArgs.scale-down-delay-after-add=10m \
  --set extraArgs.scale-down-unneeded-time=10mShell
Note

Consider using Karpenter as a modern alternative to Cluster Autoscaler on AWS. Karpenter provisions right-sized nodes in seconds (vs minutes), supports spot instances natively, and doesn't require pre-defined node groups.

Combining All Three

The three autoscalers complement each other when configured correctly:

  • HPA handles traffic spikes by adding more pod replicas
  • VPA (in Off/Initial mode) ensures each pod has the right resource requests
  • Cluster Autoscaler provisions new nodes when HPA creates pods that can't be scheduled

The scaling chain works like this: traffic increases → HPA creates new pods → pods are pending (no node capacity) → Cluster Autoscaler adds nodes → pods are scheduled → traffic is served.

Recommended Setup

# 1. Use HPA with custom metrics for application scaling
# 2. Use VPA in "Off" mode for resource recommendations
# 3. Use Cluster Autoscaler for node-level scaling
# 4. Set proper PodDisruptionBudgets

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-server-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: api-serverYAML

Production Gotchas

After running auto-scaling in production across multiple clusters, here are the hard-won lessons:

  • Always set resource requests. Without requests, HPA has nothing to calculate utilization against, and Cluster Autoscaler can't make scheduling decisions.
  • Tune the stabilization window. The default scale-down window is too aggressive for most workloads. Set it to 5-10 minutes minimum.
  • Watch for OOMKills. If VPA recommends higher memory but you don't apply it, your pods will get OOMKilled under load — right when you need them most.
  • Pre-scale for known events. Auto-scaling reacts to load, it doesn't predict it. For known traffic spikes (product launches, marketing campaigns), pre-scale your replicas with a CronJob or scheduled scaling.
  • Monitor scaling events. Set up alerts for HPA hitting maxReplicas and Cluster Autoscaler failing to provision nodes. These are early warning signs of capacity issues.
  • Use Pod Topology Spread Constraints to ensure scaled pods are distributed across availability zones, not all packed onto one node.

Auto-scaling is not a set-it-and-forget-it feature. It requires continuous tuning based on your application's behavior. Start conservative, monitor closely, and adjust iteratively.
