VPC Fundamentals

An Amazon Virtual Private Cloud (VPC) is a logically isolated section of the AWS cloud where you launch resources in a virtual network that you define. Think of it as your own private data center inside AWS, complete with full control over IP addressing, subnets, routing, and network gateways.

Every VPC is defined by a CIDR block — a range of IP addresses expressed in Classless Inter-Domain Routing notation. For example, 10.0.0.0/16 gives you 65,536 IP addresses (10.0.0.0 through 10.0.255.255). Choosing the right CIDR is critical because you cannot change it after creation, and it must not overlap with other VPCs you plan to peer or connect via Transit Gateway.

VPCs are regional resources — they span all Availability Zones (AZs) in a region but do not cross region boundaries. Each AZ is a physically separate data center with independent power, cooling, and networking. By distributing resources across multiple AZs, you gain resilience against single-facility failures.

Pro Tip

Plan your CIDR blocks with future growth in mind. Use a /16 for production VPCs (65K IPs) and /20 for dev/staging (4K IPs). Maintain a central IP address allocation spreadsheet to prevent overlaps across accounts and regions.

Public vs Private Subnets

The distinction between public and private subnets is the foundation of VPC security architecture. The difference comes down to routing — specifically, whether a subnet's route table has a route to an Internet Gateway.

  • Public subnets have a route to an Internet Gateway (IGW), allowing resources with public IPs to communicate directly with the internet. Use these for load balancers, bastion hosts, and NAT gateways.
  • Private subnets have no direct internet route. Resources here can only reach the internet through a NAT gateway sitting in a public subnet. This is where your application servers, databases, and internal services should live.
# View route tables to distinguish public from private subnets
aws ec2 describe-route-tables \
  --filters "Name=vpc-id,Values=vpc-0abc123def456" \
  --query "RouteTables[*].{ID:RouteTableId,Routes:Routes[*].{Dest:DestinationCidrBlock,Target:GatewayId}}" \
  --output table

# Public subnet route table will show:
#   0.0.0.0/0 -> igw-xxxxxxxx (Internet Gateway)
# Private subnet route table will show:
#   0.0.0.0/0 -> nat-xxxxxxxx (NAT Gateway)Shell

A common pattern for multi-tier applications is three subnet tiers: public (load balancers), private-app (application containers), and private-data (RDS, ElastiCache). Each tier gets its own set of subnets across all AZs and its own route table, enabling fine-grained network segmentation.

NAT Gateway Patterns

NAT (Network Address Translation) gateways allow private subnet resources to initiate outbound internet connections — for pulling container images, downloading patches, or calling external APIs — without exposing them to inbound traffic from the internet.

There are two common deployment patterns:

  • Single NAT Gateway: One NAT gateway in one AZ, used by all private subnets. Cost-effective but creates a single point of failure and cross-AZ data transfer charges. Suitable for development and staging environments.
  • Per-AZ NAT Gateway: One NAT gateway per Availability Zone. Each private subnet routes through the NAT gateway in its own AZ. Higher cost but eliminates cross-AZ traffic charges and provides AZ-level fault isolation. Required for production workloads.
Warning

NAT gateways are one of the most expensive networking components in AWS. At $0.045/hour plus $0.045/GB of data processed, a busy production environment can easily accumulate $500-1,000/month in NAT costs alone. Use VPC endpoints for AWS service traffic to reduce this significantly.

Multi-AZ Design

For production workloads, distributing resources across a minimum of three Availability Zones is the gold standard for high availability. Three AZs give you the ability to lose an entire AZ while still maintaining quorum for consensus-based systems (etcd, ZooKeeper, Consul) and sufficient capacity for your application tier.

The typical multi-AZ layout for a /16 VPC looks like this:

# VPC: 10.0.0.0/16 (65,536 IPs)
# Spread across 3 AZs with public + private subnets

# Public subnets (for ALB, NAT GW):
#   10.0.0.0/24   -> us-east-1a  (256 IPs)
#   10.0.1.0/24   -> us-east-1b  (256 IPs)
#   10.0.2.0/24   -> us-east-1c  (256 IPs)

# Private app subnets (for ECS/EKS workloads):
#   10.0.10.0/22  -> us-east-1a  (1,024 IPs)
#   10.0.14.0/22  -> us-east-1b  (1,024 IPs)
#   10.0.18.0/22  -> us-east-1c  (1,024 IPs)

# Private data subnets (for RDS, ElastiCache):
#   10.0.100.0/24 -> us-east-1a  (256 IPs)
#   10.0.101.0/24 -> us-east-1b  (256 IPs)
#   10.0.102.0/24 -> us-east-1c  (256 IPs)Text

Notice that private app subnets use /22 blocks (1,024 IPs each) while public and data subnets use /24 (256 IPs). Application subnets need more addresses because Kubernetes pods and ECS tasks each consume an IP address from the subnet via the AWS VPC CNI plugin.

VPC Peering vs Transit Gateway

As your AWS footprint grows, you will inevitably need to connect multiple VPCs — perhaps a shared-services VPC with a production VPC, or cross-account connectivity between teams. AWS provides two primary options, each with distinct trade-offs:

  • VPC Peering: A point-to-point connection between two VPCs. Simple, free (no hourly charge), and low-latency. But it does not support transitive routing — if VPC-A peers with VPC-B, and VPC-B peers with VPC-C, VPC-A cannot reach VPC-C through VPC-B. This means the number of peering connections grows quadratically: 10 VPCs require 45 peering connections for full mesh.
  • Transit Gateway (TGW): A regional hub that connects VPCs, VPN, and Direct Connect in a hub-and-spoke model. Supports transitive routing, route tables, and cross-account sharing. Costs $0.05/hour plus $0.02/GB, but scales linearly — 100 VPCs need only 100 attachments instead of 4,950 peering connections.
Note

Use VPC Peering when you have 2-3 VPCs with simple connectivity needs. Switch to Transit Gateway when you have 4+ VPCs, need centralized routing control, or require connectivity to on-premises networks. The operational simplicity of TGW pays for itself quickly at scale.

Security Layers

AWS provides two complementary network security mechanisms. Using both in a defense-in-depth strategy is a best practice, even though Security Groups alone cover most use cases.

  • Security Groups are stateful firewalls attached to individual resources (EC2 instances, RDS, ALBs). Because they are stateful, if you allow inbound traffic on port 443, the response traffic is automatically allowed. Security Groups only support allow rules — there are no deny rules. They operate at the instance level.
  • Network ACLs (NACLs) are stateless firewalls attached to subnets. They process rules in order (lowest number first) and support both allow and deny rules. Because they are stateless, you must explicitly allow both inbound and outbound traffic, including ephemeral port ranges for return traffic.
# Example: Block a specific IP range at the NACL level
aws ec2 create-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --rule-number 50 \
  --protocol "-1" \
  --rule-action deny \
  --cidr-block "203.0.113.0/24" \
  --ingressShell

The practical approach: use Security Groups for all standard access control (they are easier to manage and more flexible). Use NACLs as a coarse-grained safety net — for example, blocking known malicious IP ranges or restricting traffic between subnet tiers as an extra layer of protection.

Terraform Example

Here is a complete Terraform configuration that creates a production VPC with public and private subnets across three AZs, NAT gateways, and proper route tables:

variable "vpc_cidr" {
  default = "10.0.0.0/16"
}

variable "azs" {
  default = ["us-east-1a", "us-east-1b", "us-east-1c"]
}

variable "public_cidrs" {
  default = ["10.0.0.0/24", "10.0.1.0/24", "10.0.2.0/24"]
}

variable "private_cidrs" {
  default = ["10.0.10.0/22", "10.0.14.0/22", "10.0.18.0/22"]
}

# ---- VPC ----
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "production-vpc"
  }
}

# ---- Internet Gateway ----
resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "production-igw" }
}

# ---- Public Subnets ----
resource "aws_subnet" "public" {
  count                   = length(var.public_cidrs)
  vpc_id                  = aws_vpc.main.id
  cidr_block              = var.public_cidrs[count.index]
  availability_zone       = var.azs[count.index]
  map_public_ip_on_launch = true

  tags = {
    Name = "public-${var.azs[count.index]}"
  }
}

# ---- Private Subnets ----
resource "aws_subnet" "private" {
  count             = length(var.private_cidrs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.private_cidrs[count.index]
  availability_zone = var.azs[count.index]

  tags = {
    Name = "private-${var.azs[count.index]}"
  }
}

# ---- NAT Gateways (one per AZ) ----
resource "aws_eip" "nat" {
  count  = length(var.azs)
  domain = "vpc"
  tags   = { Name = "nat-eip-${var.azs[count.index]}" }
}

resource "aws_nat_gateway" "nat" {
  count         = length(var.azs)
  allocation_id = aws_eip.nat[count.index].id
  subnet_id     = aws_subnet.public[count.index].id
  tags          = { Name = "nat-${var.azs[count.index]}" }
}

# ---- Route Tables ----
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.igw.id
  }

  tags = { Name = "public-rt" }
}

resource "aws_route_table" "private" {
  count  = length(var.azs)
  vpc_id = aws_vpc.main.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.nat[count.index].id
  }

  tags = { Name = "private-rt-${var.azs[count.index]}" }
}

resource "aws_route_table_association" "public" {
  count          = length(var.public_cidrs)
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

resource "aws_route_table_association" "private" {
  count          = length(var.private_cidrs)
  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[count.index].id
}HCL

Cost Optimization

VPC infrastructure can be surprisingly expensive if you are not paying attention. The resources themselves (VPCs, subnets, route tables) are free, but the networking components that make them useful are not. Here are the key cost levers:

  • NAT Gateway costs: At $0.045/hour ($32/month) per gateway plus $0.045/GB processed, three per-AZ NAT gateways cost $97/month before any data transfer. For dev environments, use a single NAT gateway or even a NAT instance (t3.micro) to save 80%.
  • VPC Endpoints: Every API call to S3, DynamoDB, ECR, CloudWatch, and other AWS services from a private subnet goes through the NAT gateway by default. A Gateway endpoint (S3, DynamoDB) is free and routes traffic over the AWS backbone. Interface endpoints cost $0.01/hour per AZ but eliminate NAT data processing charges for high-volume services like ECR pulls.
  • Cross-AZ data transfer: Traffic between AZs costs $0.01/GB in each direction ($0.02/GB round trip). In a chatty microservices architecture, this can add up. Consider placing tightly coupled services in the same AZ or using service mesh locality-aware routing.
  • Transit Gateway data charges: At $0.02/GB, Transit Gateway adds a per-gigabyte tax on all inter-VPC traffic. For high-bandwidth connections between two specific VPCs, a direct VPC peering connection (free data transfer) may be more economical.
# Create a free Gateway endpoint for S3
resource "aws_vpc_endpoint" "s3" {
  vpc_id       = aws_vpc.main.id
  service_name = "com.amazonaws.us-east-1.s3"

  route_table_ids = concat(
    [aws_route_table.public.id],
    aws_route_table.private[*].id
  )

  tags = { Name = "s3-gateway-endpoint" }
}

# Create an Interface endpoint for ECR (saves NAT costs for image pulls)
resource "aws_vpc_endpoint" "ecr_api" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.us-east-1.ecr.api"
  vpc_endpoint_type   = "Interface"
  private_dns_enabled = true
  subnet_ids          = aws_subnet.private[*].id

  tags = { Name = "ecr-api-endpoint" }
}HCL

The best VPC design balances security, availability, and cost. Over-engineering with every possible endpoint and three NAT gateways in a dev environment wastes money. Under-engineering in production risks outages and security incidents. Know your environment's tier and design accordingly.
