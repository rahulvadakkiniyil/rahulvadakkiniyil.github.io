How to Create a Transit Secrets Engine in HashiCorp Vault

A hands-on walkthrough of Vault's encryption-as-a-service engine — enable the mount, create a key, encrypt and decrypt data, rotate keys, rewrap ciphertext, and generate data keys for envelope encryption, all from the command line.

1. What Is the Transit Secrets Engine

The Transit secrets engine is HashiCorp Vault's encryption-as-a-service offering. Applications send plaintext to Vault and get ciphertext back; they send ciphertext and get plaintext back. The encryption keys never leave Vault, and the engine itself does not store any of the data being encrypted.

This is a fundamentally different mental model from KV secrets. In KV, Vault is the database — it holds the secret. In Transit, Vault is the cryptographic provider — it holds the key, and your application keeps the data wherever it normally would (Postgres, S3, a config file). You hand Vault the bytes, Vault hands back ciphertext, and you store the ciphertext.

When to Reach for It

  • Encrypting columns in a database — store encrypted values for PII, payment tokens, or API keys without putting key material on the application servers.
  • Envelope encryption for large payloads — generate a per-object data key with datakey/plaintext, encrypt the payload locally, store the wrapped key alongside the ciphertext.
  • Signing and HMAC — produce signatures and message authentication codes for webhooks, JWTs, or audit records using keys you never have to handle.
  • Centralized key rotation — rotate the underlying key in Vault on a schedule; old ciphertext keeps decrypting, new ciphertext uses the new version.
Note: Transit does not persist any plaintext or ciphertext. It is stateless from a data perspective — only the key material and key configuration live in Vault's storage backend. Lose the storage backend, and every ciphertext encrypted under those keys becomes unrecoverable. Back up the storage as carefully as you would back up a KMS.

2. Prerequisites

You need very little to follow along, but every item below should be in place before you run the first command.

  • A running, unsealed Vault — server v1.12 or newer is recommended. A dev-mode Vault works for experimentation; production should be a properly initialized cluster.
  • Vault CLI on your workstation — matching or newer than the server version.
  • An admin or root token for the initial setup. Day-to-day work should use a scoped policy, covered in section 10.
  • Environment variables exported — VAULT_ADDR pointing at the server and VAULT_TOKEN set to a valid token.
Confirm the CLI can talk to the server and you are authenticated
export VAULT_ADDR="https://vault.example.com:8200"
export VAULT_TOKEN="hvs.CAESI..."

vault status
# Sealed should be false

vault token lookup
# Confirms the token, its TTL, and policies
Tip: If you just want to try this out, run vault server -dev in a second terminal. It boots an in-memory Vault, prints the root token to stdout, and stays unsealed for as long as the process runs. Never use dev mode for anything you care about — it loses all data on exit.

3. Enable the Transit Engine

Like every secrets engine in Vault, Transit is mounted at a path. The conventional path is simply transit/, but you can mount it anywhere — and you can mount it more than once if different teams need isolated keyspaces.

Enable the engine at the default path
vault secrets enable transit
# Success! Enabled the transit secrets engine at: transit/
Or mount it at a custom path for a specific team or environment
vault secrets enable -path="transit-payments" transit

# List all mounted engines to confirm
vault secrets list

Custom mounts are useful when you want strict separation between, say, the payments team's keys and the analytics team's keys. Each mount is its own isolated keyspace; a token with access to transit-payments/ cannot touch keys under transit/.

Note: The mount path becomes part of every API call (vault write transit-payments/encrypt/...). Pick a name you are willing to live with — renaming a mount means migrating every ciphertext that was encrypted under it.

4. Create an Encryption Key

With the engine mounted, the next step is to create a named encryption key. The name is how your applications will refer to it, so choose something descriptive — orders-pii, jwt-signing, billing-api — rather than key1.

Create a default AES-256-GCM key
vault write -f transit/keys/orders-pii
# Success! Data written to: transit/keys/orders-pii

The -f flag (force) tells Vault to create the key with all defaults: aes256-gcm96 as the cipher, exportable disabled, deletion not allowed, and version 1 as the active version. For most encryption use cases, the defaults are correct and you should not change them.

Create a key with explicit type — useful for signing or asymmetric work
# RSA-4096 key for signing JWTs or large payloads
vault write transit/keys/jwt-signing type="rsa-4096"

# Ed25519 key — fast asymmetric signing
vault write transit/keys/audit-signing type="ed25519"

# ChaCha20-Poly1305 — alternative symmetric AEAD cipher
vault write transit/keys/stream-data type="chacha20-poly1305"
Inspect the key configuration
vault read transit/keys/orders-pii

# Key                       Value
# ---                       -----
# allow_plaintext_backup    false
# auto_rotate_period        0s
# deletion_allowed          false
# derived                   false
# exportable                false
# keys                      map[1:1714652400]
# latest_version            1
# min_available_version     0
# min_decryption_version    1
# min_encryption_version    0
# name                      orders-pii
# supports_decryption       true
# supports_derivation       false
# supports_encryption       true
# supports_signing          false
# type                      aes256-gcm96

Common Key Types and What They Are For

  • aes256-gcm96 (default) — symmetric AEAD, best general-purpose choice for encrypt/decrypt.
  • chacha20-poly1305 — symmetric AEAD, faster than AES on platforms without AES-NI.
  • rsa-2048 / rsa-3072 / rsa-4096 — asymmetric, for signing or for envelope encryption when consumers only need the public key.
  • ecdsa-p256 / ecdsa-p384 / ecdsa-p521 — asymmetric signing with elliptic curves.
  • ed25519 — modern signature scheme; fast, small signatures.
  • hmac — for generating message authentication codes only.

5. Encrypt and Decrypt Data

Transit expects plaintext to be base64-encoded on the way in. The ciphertext it returns is a Vault-formatted string that begins with vault:v1: — the v1 indicates which version of the key was used to produce it. Store this string verbatim; do not try to strip the prefix.

Encrypt a piece of plaintext
vault write transit/encrypt/orders-pii \
  plaintext="$(echo -n 'cardholder@example.com' | base64)"

# Key            Value
# ---            -----
# ciphertext     vault:v1:abcd1234...XYZ=
# key_version    1
Decrypt the same ciphertext
vault write transit/decrypt/orders-pii \
  ciphertext="vault:v1:abcd1234...XYZ="

# Key          Value
# ---          -----
# plaintext    Y2FyZGhvbGRlckBleGFtcGxlLmNvbQ==

# Decode the base64 to recover the original
echo "Y2FyZGhvbGRlckBleGFtcGxlLmNvbQ==" | base64 --decode
# cardholder@example.com

This round-trip is the entire core of Transit. Everything else — rotation, rewrap, data keys, signing — is a variation on the same pattern: vault write transit/<operation>/<key-name> with the operation-specific parameters.

Encrypt with associated context (required for derived keys)
# First, create a derived key
vault write transit/keys/per-tenant derived="true"

# Now every encrypt call must supply a context — typically the tenant ID
vault write transit/encrypt/per-tenant \
  plaintext="$(echo -n 'tenant-secret' | base64)" \
  context="$(echo -n 'tenant-42' | base64)"
Tip: Derived keys give you per-tenant or per-user encryption without managing one key per tenant. The context becomes part of the encryption — same plaintext, different context, different ciphertext.

6. Rotate the Encryption Key

Rotating a Transit key generates a new version. The new version becomes the default for all subsequent encrypt operations. Critically, old ciphertext keeps decrypting just fine — Vault retains every previous version of the key until you explicitly drop them.

Rotate the key on demand
vault write -f transit/keys/orders-pii/rotate
# Success! Data written to: transit/keys/orders-pii/rotate

# Confirm the new version
vault read transit/keys/orders-pii
# latest_version    2
# keys              map[1:1714652400 2:1714738800]
Configure automatic rotation on a schedule
# Rotate every 30 days, automatically
vault write transit/keys/orders-pii/config \
  auto_rotate_period="720h"

After rotation, every new encrypt call returns ciphertext prefixed with vault:v2:. Ciphertext from before the rotation still starts with vault:v1: and decrypts using key version 1. The version is embedded in the ciphertext itself — Vault knows which key to use without you telling it.

Important: Do not delete or disable old key versions until every ciphertext that was encrypted under them has been rewrapped. Doing so makes that ciphertext permanently unrecoverable. Section 7 shows how to rewrap so old versions can be retired safely.

7. Rewrap Existing Ciphertext

Rewrapping takes ciphertext encrypted under an older key version and re-encrypts it under the latest version, without ever exposing the plaintext. The decrypt and re-encrypt happen entirely inside Vault. After rewrapping, you can safely raise min_decryption_version and retire old key material.

Rewrap a single ciphertext
vault write transit/rewrap/orders-pii \
  ciphertext="vault:v1:abcd1234...XYZ="

# Key            Value
# ---            -----
# ciphertext     vault:v2:wxyz5678...ABC=
# key_version    2

Update your storage with the new ciphertext. Once every record has been rewrapped, you can raise the minimum decryption version so the old key version is no longer used.

After rewrapping everything, retire the old version
# Refuse to decrypt anything older than version 2
vault write transit/keys/orders-pii/config \
  min_decryption_version="2"

# Optionally, also raise the minimum available version
# (drops the actual key material for v1 — irreversible)
vault write transit/keys/orders-pii/trim \
  min_available_version="2"
Note: For databases with millions of rows, rewrap one row at a time as part of a background job. Rewrap is cheap (each call is a single Vault round-trip and costs no plaintext exposure), but doing it in a single transaction will hold locks far too long. Stream the work through a queue.

8. Generate Data Keys for Envelope Encryption

For large payloads — files, full database rows, message blobs — calling encrypt on every byte is wasteful and slow. The standard pattern is envelope encryption: ask Vault for a per-object data key, encrypt the payload locally with that key, and store the wrapped key alongside the ciphertext. Vault never sees the payload.

Get a plaintext data key plus its wrapped form
vault write transit/datakey/plaintext/orders-pii

# Key            Value
# ---            -----
# ciphertext     vault:v2:dGVzdF9rZXk...=
# key_version    2
# plaintext      WnRzVnA5MlpQQXNxRzZNbWdQR0lLNWJpZE...=

The application uses plaintext (a fresh 256-bit AES key, base64-encoded) to encrypt the payload locally with any standard AEAD library. It then discards the plaintext key from memory and stores only the ciphertext (the wrapped form) alongside the encrypted payload. To decrypt later, the application sends the wrapped form to transit/decrypt/orders-pii to recover the data key, decrypts the payload, and discards the key again.

Get only the wrapped form — for write-only services
# Useful for log shippers or producers that only need to encrypt,
# never decrypt. The plaintext key is never returned over the wire.
vault write transit/datakey/wrapped/orders-pii
Tip: Envelope encryption is the right default for anything larger than a few kilobytes. It keeps the cryptographic boundary inside Vault (the data key is wrapped with a key Vault holds) while letting your application do the heavy lifting locally. AWS KMS, GCP KMS, and Azure Key Vault all use the same pattern.

9. Sign, Verify, and HMAC

Transit also handles signing and message authentication. The shape of the API is identical — write to sign/<key> or hmac/<key> with input bytes, get a signature back, and write to verify/<key> to check it.

Sign and verify with an asymmetric key
# Sign a payload with the JWT signing key created earlier
vault write transit/sign/jwt-signing \
  input="$(echo -n 'header.payload' | base64)"

# Key            Value
# ---            -----
# key_version    1
# signature      vault:v1:MEUCIQDH...=

# Verify the signature
vault write transit/verify/jwt-signing \
  input="$(echo -n 'header.payload' | base64)" \
  signature="vault:v1:MEUCIQDH...="

# Key      Value
# ---      -----
# valid    true
HMAC for symmetric message authentication
vault write transit/hmac/orders-pii \
  input="$(echo -n 'webhook-payload' | base64)"

# Key      Value
# ---      -----
# hmac     vault:v2:F8x9aZqL...

Signing keys can be exported as public keys for verification by external systems that do not have Vault access — useful for issuing JWTs to clients who verify them locally.

Export the public key from an asymmetric signing key
vault read transit/keys/jwt-signing \
  | grep -A 20 "public_key"

10. Wire It Up With a Policy

Never let production applications use a root token. Create a policy that grants exactly the operations a given service needs — encrypt-only, decrypt-only, or both — and bind that policy to an AppRole, Kubernetes service account, or whatever auth method fits your environment.

A least-privilege policy for the orders service
# File: orders-service-policy.hcl

# Allow encrypt and decrypt for the orders-pii key
path "transit/encrypt/orders-pii" {
  capabilities = ["update"]
}

path "transit/decrypt/orders-pii" {
  capabilities = ["update"]
}

# Allow rewrap so background jobs can re-encrypt under the latest version
path "transit/rewrap/orders-pii" {
  capabilities = ["update"]
}

# Read-only access to key metadata (latest_version, etc.) — no key material
path "transit/keys/orders-pii" {
  capabilities = ["read"]
}
Apply the policy and verify it works
vault policy write orders-service orders-service-policy.hcl

# Issue a token bound to the policy and test it
vault token create -policy="orders-service" -ttl="1h"

VAULT_TOKEN="<new-token>" \
  vault write transit/encrypt/orders-pii \
  plaintext="$(echo -n 'test' | base64)"
Important: The update capability on transit/encrypt/<key> only allows encryption — it cannot read or modify the key itself. This is the correct level of access for almost every workload. Avoid granting create, delete, or wildcard paths like transit/* outside of a small number of admin policies.

11. Best Practices

The Transit engine is one of the simpler parts of Vault to operate, but a handful of choices made early will save you significant pain later. The list below is what I have seen actually matter in production.

  • One key per data domain, not per record. Create separate keys for distinct trust boundaries (orders PII, billing data, internal audit signatures), but not one per row. Use derived keys with context if you need per-tenant isolation under a single key.
  • Rotate on a schedule, rewrap on a schedule. Set auto_rotate_period to something like 90 days and run a background rewrap job. Rotation alone does nothing for old ciphertext — pair it with rewrap.
  • Never enable exportable unless you truly need it. An exportable key can be pulled out of Vault with the right permissions, defeating the entire point of the engine. The default is false; leave it that way.
  • Treat min_available_version bumps as one-way doors. Trimming key versions deletes the key material. Once it is gone, ciphertext under that version is gone too. Always rewrap first, then trim.
  • Audit every operation. Enable an audit device before you mount Transit, so every encrypt/decrypt/sign call is recorded. The payloads are HMAC-hashed by default, so audit logs do not contain plaintext.
  • Back up the storage backend like a KMS. The keys live in Vault's storage (Raft, Consul, etc.). If you lose that storage and have no snapshot, every byte of ciphertext encrypted by Transit becomes shredded data.
  • Use envelope encryption for anything over a few KB. Round-tripping multi-megabyte payloads through Vault is slow and unnecessary. Generate a data key, encrypt locally, store the wrapped key.
  • Bind tokens to short TTLs and narrow policies. A leaked token with encrypt-only on a single key is a contained incident; a leaked token with transit/* is a key-rotation event.
Wrap-up: The Transit engine is the answer to “how do I encrypt this column without putting a master key on every app server?” Mount it once, create a key per data domain, give each service the narrowest policy that lets it do its job, and lean on rotation and rewrap to keep things healthy. Once the pattern is in place, adding a new encrypted field is a one-line policy change and a single vault write.
