Why Modules Matter

If you have been working with Terraform for any length of time, you have likely encountered the pain of copy-pasting resource blocks between projects. A VPC here, a security group there, an RDS instance somewhere else — all slightly different, all diverging over time. This is the infrastructure equivalent of spaghetti code, and it leads to exactly the same problems: inconsistency, drift, and fear of making changes.

Terraform modules solve this by letting you encapsulate a set of resources into a reusable, versioned unit. Think of them as functions for your infrastructure. Instead of duplicating 200 lines of VPC configuration across ten projects, you write it once as a module and call it with a few parameters. When you need to update the VPC pattern — say, adding flow logs or changing the subnet layout — you update the module in one place and roll it out everywhere.

The benefits go beyond just DRY (Don't Repeat Yourself) principles. Modules enforce team consistency by ensuring that every VPC, every EKS cluster, every RDS instance follows the same architectural patterns and security baselines. New team members don't need to understand every resource type — they just need to know which modules to use and what inputs to provide.

Module Structure

A well-structured Terraform module follows a consistent file convention that makes it immediately understandable to anyone familiar with Terraform. While Terraform itself doesn't enforce filenames, the community has settled on a standard layout:

# Standard module directory structure
modules/
  vpc/
    main.tf           # Primary resource definitions
    variables.tf      # Input variable declarations
    outputs.tf        # Output value declarations
    versions.tf       # Provider and Terraform version constraints
    locals.tf         # Local value computations
    data.tf           # Data source lookups
    README.md         # Module documentationHCL

The versions.tf file is often overlooked but critically important. It pins the minimum Terraform and provider versions your module supports, preventing obscure errors when someone runs it with an incompatible version:

terraform {
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = ">= 5.0, < 6.0"
    }
  }
}HCL

Building a VPC Module

Let's build a production-ready VPC module step by step. This module will create a VPC with public and private subnets across multiple availability zones, complete with NAT gateways and proper route tables.

Start with variables.tf to define the module's interface:

variable "vpc_name" {
  description = "Name tag for the VPC and related resources"
  type        = string
}

variable "vpc_cidr" {
  description = "CIDR block for the VPC (e.g., 10.0.0.0/16)"
  type        = string
  default     = "10.0.0.0/16"
}

variable "azs" {
  description = "List of availability zones to deploy subnets into"
  type        = list(string)
  default     = ["us-east-1a", "us-east-1b", "us-east-1c"]
}

variable "private_subnet_cidrs" {
  description = "CIDR blocks for private subnets"
  type        = list(string)
  default     = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
}

variable "public_subnet_cidrs" {
  description = "CIDR blocks for public subnets"
  type        = list(string)
  default     = ["10.0.101.0/24", "10.0.102.0/24", "10.0.103.0/24"]
}

variable "enable_nat_gateway" {
  description = "Whether to create NAT gateways for private subnets"
  type        = bool
  default     = true
}

variable "single_nat_gateway" {
  description = "Use a single NAT gateway instead of one per AZ (saves cost)"
  type        = bool
  default     = false
}

variable "tags" {
  description = "Map of tags to apply to all resources"
  type        = map(string)
  default     = {}
}HCL

Now the main.tf with the core resources:

resource "aws_vpc" "this" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = merge(var.tags, {
    Name = var.vpc_name
  })
}

resource "aws_subnet" "private" {
  count             = length(var.private_subnet_cidrs)
  vpc_id            = aws_vpc.this.id
  cidr_block        = var.private_subnet_cidrs[count.index]
  availability_zone = var.azs[count.index]

  tags = merge(var.tags, {
    Name = "${var.vpc_name}-private-${var.azs[count.index]}"
    Tier = "private"
  })
}

resource "aws_subnet" "public" {
  count                   = length(var.public_subnet_cidrs)
  vpc_id                  = aws_vpc.this.id
  cidr_block              = var.public_subnet_cidrs[count.index]
  availability_zone       = var.azs[count.index]
  map_public_ip_on_launch = true

  tags = merge(var.tags, {
    Name = "${var.vpc_name}-public-${var.azs[count.index]}"
    Tier = "public"
  })
}

resource "aws_internet_gateway" "this" {
  vpc_id = aws_vpc.this.id

  tags = merge(var.tags, {
    Name = "${var.vpc_name}-igw"
  })
}HCL

Input Validation

Terraform 1.x introduced variable validation blocks, which let you catch configuration errors before terraform plan even runs. This is essential for modules consumed by other teams — clear error messages are far better than cryptic AWS API failures.

variable "vpc_cidr" {
  description = "CIDR block for the VPC"
  type        = string

  validation {
    condition     = can(cidrhost(var.vpc_cidr, 0))
    error_message = "The vpc_cidr must be a valid CIDR block (e.g., 10.0.0.0/16)."
  }

  validation {
    condition     = tonumber(split("/", var.vpc_cidr)[1]) <= 20
    error_message = "The VPC CIDR prefix must be /20 or larger to accommodate subnets."
  }
}

variable "environment" {
  description = "Deployment environment"
  type        = string

  validation {
    condition     = contains(["dev", "staging", "production"], var.environment)
    error_message = "Environment must be one of: dev, staging, production."
  }
}HCL
Pro Tip

Use multiple validation blocks on the same variable to check different conditions. Each block produces its own error message, making it easy for consumers to understand exactly what went wrong.

Output Composition

Module outputs are the API surface that downstream modules and root configurations consume. Well-designed outputs expose the identifiers and ARNs that other resources commonly need, without leaking unnecessary implementation details.

output "vpc_id" {
  description = "The ID of the VPC"
  value       = aws_vpc.this.id
}

output "vpc_arn" {
  description = "The ARN of the VPC"
  value       = aws_vpc.this.arn
}

output "private_subnet_ids" {
  description = "List of private subnet IDs"
  value       = aws_subnet.private[*].id
}

output "public_subnet_ids" {
  description = "List of public subnet IDs"
  value       = aws_subnet.public[*].id
}

output "private_subnet_arns" {
  description = "List of private subnet ARNs"
  value       = aws_subnet.private[*].arn
}

output "nat_gateway_ips" {
  description = "Elastic IPs associated with NAT gateways"
  value       = aws_eip.nat[*].public_ip
}HCL

A downstream module can then reference these outputs cleanly:

module "vpc" {
  source  = "git::https://github.com/myorg/terraform-modules.git//vpc?ref=v2.1.0"
  vpc_name = "production"
  vpc_cidr = "10.0.0.0/16"
}

module "eks" {
  source     = "git::https://github.com/myorg/terraform-modules.git//eks?ref=v1.4.0"
  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnet_ids
}HCL

Versioning with Git Tags

Versioning modules is essential for safe, predictable infrastructure changes. Without pinned versions, a module update could unexpectedly alter resources across every project that references it — potentially destroying production infrastructure.

Use semantic versioning (SemVer) to communicate the impact of changes:

  • Patch (v1.0.1): Bug fixes, documentation updates. No resource changes.
  • Minor (v1.1.0): New optional features, new variables with defaults. Backward compatible.
  • Major (v2.0.0): Breaking changes — renamed variables, removed resources, changed defaults.
# Tag a release in your module repository
git tag -a v2.1.0 -m "Add VPC flow logs support, new enable_flow_logs variable"
git push origin v2.1.0

# Pin the version in your root module
module "vpc" {
  source = "git::https://github.com/myorg/terraform-modules.git//vpc?ref=v2.1.0"
}Shell
Warning

Never reference a module by branch name (e.g., ref=main) in production. Branches are mutable — someone could push a breaking change and your next terraform apply would pick it up automatically. Always pin to a specific tag or commit SHA.

Testing with Terratest

Terratest is a Go library that lets you write automated tests for your Terraform modules. It runs terraform init, plan, and apply against real cloud infrastructure, validates the results, and then runs destroy to clean up. This gives you confidence that your module actually works, not just that it parses correctly.

package test

import (
    "testing"

    "github.com/gruntwork-io/terratest/modules/terraform"
    "github.com/stretchr/testify/assert"
)

func TestVpcModule(t *testing.T) {
    t.Parallel()

    terraformOptions := &terraform.Options{
        TerraformDir: "../modules/vpc",
        Vars: map[string]interface{}{
            "vpc_name":    "test-vpc",
            "vpc_cidr":    "10.99.0.0/16",
            "environment": "dev",
        },
    }

    // Clean up resources after the test
    defer terraform.Destroy(t, terraformOptions)

    // Run terraform init and apply
    terraform.InitAndApply(t, terraformOptions)

    // Validate outputs
    vpcId := terraform.Output(t, terraformOptions, "vpc_id")
    assert.NotEmpty(t, vpcId)

    privateSubnets := terraform.OutputList(t, terraformOptions, "private_subnet_ids")
    assert.Equal(t, 3, len(privateSubnets))
}Go

Run the test with go test -v -timeout 30m ./test/. The timeout is important because cloud resource creation can take several minutes. Integrate this into your CI pipeline so every pull request against the module repository is validated before merging.

Best Practices Summary

After building and maintaining dozens of Terraform modules across multiple organizations, these are the principles that consistently lead to maintainable, reliable infrastructure code:

  • Keep modules focused. A module should do one thing well. A VPC module creates a VPC. An EKS module creates a cluster. Don't create a "kitchen sink" module that provisions an entire environment.
  • Document every variable and output. Use the description field religiously. Your future self and your teammates will thank you when they need to understand what enable_cross_zone_lb actually does.
  • Provide sensible defaults. Required variables should be limited to things that are genuinely unique per deployment (like names and CIDR blocks). Everything else should have a reasonable default.
  • Use consistent naming. Adopt a naming convention and stick to it. If your VPC module uses vpc_name, your EKS module should use cluster_name, not name or eks_cluster_name_tag.
  • Version everything. Use Git tags with semantic versioning. Never reference main or HEAD in production module sources.
  • Test with real infrastructure. Unit tests that only check plan output miss a whole class of bugs. Use Terratest to verify that resources are actually created correctly.
  • Use a private module registry. Whether it's Terraform Cloud, Artifactory, or a simple Git repository with tags, a central registry makes modules discoverable and versioning transparent.
  • Pin provider versions. Always specify both minimum and maximum provider versions in versions.tf to prevent unexpected breaking changes from provider updates.

Good Terraform modules are like good APIs: they have a clear contract, handle edge cases gracefully, and are versioned so consumers can upgrade on their own schedule.
