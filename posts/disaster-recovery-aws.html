Understanding RTO and RPO

Recovery Time Objective (RTO) is the maximum acceptable time your application can be offline after a disaster. If your RTO is 1 hour, your systems must be fully operational within 60 minutes of an outage. Recovery Point Objective (RPO) is the maximum acceptable amount of data loss measured in time. An RPO of 15 minutes means you can afford to lose at most 15 minutes of data.

These two metrics drive every architectural decision in your DR plan. A tighter RTO means more infrastructure running in standby (higher cost). A tighter RPO means more frequent data replication (higher complexity and cost). The business impact analysis should guide these targets: a payment processing system demands sub-minute RTO/RPO, while an internal reporting dashboard might tolerate hours of downtime.

To determine your targets, start by classifying workloads into tiers. Tier 1 (mission-critical) applications like customer-facing APIs and transaction databases need aggressive targets. Tier 2 (business-important) systems like internal tools can tolerate moderate downtime. Tier 3 (non-essential) services like dev environments can be rebuilt from scratch with minimal urgency.

Four DR Strategies

AWS documentation defines four distinct DR strategies, each representing a different tradeoff between cost and recovery speed. Understanding all four lets you match the right strategy to each workload tier.

1. Backup & Restore

The simplest and cheapest strategy. You take regular backups (EBS snapshots, RDS automated backups, S3 cross-region replication) and restore them in a new region when disaster strikes. RTO is typically 4-24 hours depending on data volume. RPO equals your backup frequency.

2. Pilot Light

A minimal version of your environment runs in the DR region at all times. Core data services (like RDS read replicas) stay synchronized, but application servers are stopped. During failover, you start the application tier and scale up. RTO is typically 1-2 hours.

3. Warm Standby

A scaled-down but fully functional copy of your production environment runs continuously in the DR region. All components are live but at reduced capacity (e.g., minimum instance counts). During failover, you scale up to full production capacity. RTO is typically 15-30 minutes.

4. Multi-Region Active-Active

Your application runs at full capacity in two or more regions simultaneously, serving traffic from all regions. Data is replicated bidirectionally using DynamoDB Global Tables or Aurora Global Database. Failover is nearly instantaneous since all regions are already handling traffic. RTO is near-zero, but cost is roughly 2x or more.

Cost Comparison

Here is a realistic monthly cost comparison for a mid-size web application (assuming ~$5,000/month primary region cost):

  • Backup & Restore — DR cost: ~$200-500/month (S3 storage, snapshot storage). RTO: 4-24 hrs. RPO: 1-24 hrs.
  • Pilot Light — DR cost: ~$500-1,200/month (RDS replica, minimal infra). RTO: 1-2 hrs. RPO: minutes.
  • Warm Standby — DR cost: ~$2,000-3,500/month (scaled-down full stack). RTO: 15-30 min. RPO: seconds-minutes.
  • Multi-Region Active-Active — DR cost: ~$5,000-7,000/month (full duplicate + replication overhead). RTO: near-zero. RPO: near-zero.

Most organizations use a hybrid approach: Active-Active for Tier 1 workloads, Warm Standby for Tier 2, and Backup & Restore for Tier 3.

Pilot Light Implementation

Pilot Light is the most popular DR strategy because it provides reasonable recovery times at a fraction of active-active costs. Here is a Terraform configuration for the essential DR infrastructure:

# Pilot Light DR infrastructure in us-west-2

resource "aws_db_instance" "dr_replica" {
  replicate_source_db    = "arn:aws:rds:us-east-1:123456789:db:production-db"
  instance_class         = "db.r6g.large"
  availability_zone      = "us-west-2a"
  storage_encrypted      = true
  multi_az               = false  # Keep costs low in DR
  skip_final_snapshot    = false

  tags = {
    Environment = "disaster-recovery"
    Tier        = "pilot-light"
  }
}

# AMI copy for quick EC2 launch in DR region
resource "aws_ami_copy" "dr_app_ami" {
  name              = "dr-app-server-ami"
  source_ami_id     = "ami-0abcdef1234567890"
  source_ami_region = "us-east-1"
  encrypted         = true
}

# Launch template ready to go but no instances running
resource "aws_launch_template" "dr_app" {
  name          = "dr-app-server"
  image_id      = aws_ami_copy.dr_app_ami.id
  instance_type = "c6i.xlarge"

  user_data = base64encode(templatefile("scripts/app-init.sh", {
    db_endpoint = aws_db_instance.dr_replica.endpoint
    region      = "us-west-2"
  }))
}Terraform

Route 53 Health Checks & Failover

Route 53 is the backbone of automated DNS failover. You configure health checks against your primary region, and Route 53 automatically routes traffic to the DR region when the primary becomes unhealthy.

# Create health check for primary region
aws route53 create-health-check \
  --caller-reference "primary-health-$(date +%s)" \
  --health-check-config '{
    "IPAddress": "203.0.113.10",
    "Port": 443,
    "Type": "HTTPS",
    "ResourcePath": "/health",
    "RequestInterval": 10,
    "FailureThreshold": 3,
    "EnableSNI": true
  }'

# Create failover DNS records
aws route53 change-resource-record-sets \
  --hosted-zone-id Z1234567890 \
  --change-batch '{
    "Changes": [
      {
        "Action": "CREATE",
        "ResourceRecordSet": {
          "Name": "api.example.com",
          "Type": "A",
          "SetIdentifier": "primary",
          "Failover": "PRIMARY",
          "TTL": 60,
          "ResourceRecords": [{ "Value": "203.0.113.10" }],
          "HealthCheckId": "health-check-id-here"
        }
      },
      {
        "Action": "CREATE",
        "ResourceRecordSet": {
          "Name": "api.example.com",
          "Type": "A",
          "SetIdentifier": "secondary",
          "Failover": "SECONDARY",
          "TTL": 60,
          "ResourceRecords": [{ "Value": "198.51.100.20" }]
        }
      }
    ]
  }'Shell
Pro Tip

Set your DNS TTL to 60 seconds or less for failover records. A high TTL means clients will cache the old (failed) IP address and continue sending traffic to the downed region long after Route 53 has updated.

Cross-Region S3 Replication

S3 Cross-Region Replication (CRR) ensures your object data is continuously copied to the DR region. This is essential for static assets, configuration files, backups, and any data stored in S3.

# Enable versioning (required for replication)
aws s3api put-bucket-versioning \
  --bucket my-app-assets-us-east-1 \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-versioning \
  --bucket my-app-assets-us-west-2 \
  --versioning-configuration Status=Enabled

# Configure replication
aws s3api put-bucket-replication \
  --bucket my-app-assets-us-east-1 \
  --replication-configuration '{
    "Role": "arn:aws:iam::123456789:role/s3-replication-role",
    "Rules": [
      {
        "ID": "ReplicateAll",
        "Status": "Enabled",
        "Priority": 1,
        "Filter": { "Prefix": "" },
        "Destination": {
          "Bucket": "arn:aws:s3:::my-app-assets-us-west-2",
          "StorageClass": "STANDARD",
          "ReplicationTime": {
            "Status": "Enabled",
            "Time": { "Minutes": 15 }
          },
          "Metrics": {
            "Status": "Enabled",
            "EventThreshold": { "Minutes": 15 }
          }
        },
        "DeleteMarkerReplication": { "Status": "Enabled" }
      }
    ]
  }'Shell

Lambda Health Monitoring

While Route 53 health checks cover basic HTTP endpoint monitoring, you often need custom health checks that validate business logic, database connectivity, and downstream dependencies. A Lambda function running on a schedule can perform deep health checks and trigger failover actions.

import boto3
import json
import requests
from datetime import datetime

route53 = boto3.client('route53')
sns = boto3.client('sns')
cloudwatch = boto3.client('cloudwatch')

HEALTH_ENDPOINTS = [
    {'name': 'api', 'url': 'https://api.example.com/health', 'timeout': 5},
    {'name': 'auth', 'url': 'https://auth.example.com/health', 'timeout': 5},
    {'name': 'payments', 'url': 'https://payments.example.com/health', 'timeout': 3},
]

SNS_TOPIC_ARN = 'arn:aws:sns:us-east-1:123456789:dr-alerts'
FAILURE_THRESHOLD = 3

def lambda_handler(event, context):
    results = []
    failures = []

    for endpoint in HEALTH_ENDPOINTS:
        try:
            resp = requests.get(
                endpoint['url'],
                timeout=endpoint['timeout']
            )
            healthy = resp.status_code == 200
            latency = resp.elapsed.total_seconds() * 1000
        except Exception as e:
            healthy = False
            latency = 0
            failures.append({'endpoint': endpoint['name'], 'error': str(e)})

        # Publish metric to CloudWatch
        cloudwatch.put_metric_data(
            Namespace='DR/HealthChecks',
            MetricData=[{
                'MetricName': 'EndpointHealth',
                'Dimensions': [{'Name': 'Service', 'Value': endpoint['name']}],
                'Value': 1 if healthy else 0,
                'Unit': 'Count'
            }]
        )
        results.append({'service': endpoint['name'], 'healthy': healthy, 'latency_ms': latency})

    # Alert if any critical service is down
    if failures:
        sns.publish(
            TopicArn=SNS_TOPIC_ARN,
            Subject=f'DR ALERT: {len(failures)} endpoint(s) unhealthy',
            Message=json.dumps({
                'timestamp': datetime.utcnow().isoformat(),
                'failures': failures,
                'action': 'Investigate immediately. Failover may be required.'
            }, indent=2)
        )

    return {'statusCode': 200, 'results': results}Python

Testing Your DR Plan

Warning

A DR plan that hasn't been tested is not a DR plan. It is a collection of assumptions waiting to fail at the worst possible moment.

Testing must be regular, documented, and progressively more realistic. Here is a phased approach:

  • Tabletop exercises (monthly): Walk through the runbook with your team. Identify gaps in documentation, unclear ownership, and missing contact info. These cost nothing and surface problems quickly.
  • Component failover tests (quarterly): Promote an RDS read replica, verify data integrity, switch a single service to the DR region. Test each component in isolation before testing the full stack.
  • Full DR simulation (bi-annually): Simulate a complete regional outage. Route all traffic to the DR region and run production workloads for several hours. Measure actual RTO and RPO against your targets.
  • Chaos engineering (ongoing): Use AWS Fault Injection Simulator to inject controlled failures: terminate instances, throttle API calls, introduce network latency. Build confidence that your systems degrade gracefully.

Automated Runbook Example

#!/bin/bash
# DR Failover Runbook - Automated Steps
# Run with: ./failover.sh --region us-west-2 --confirm

set -euo pipefail

DR_REGION="us-west-2"
ASG_NAME="dr-app-server-asg"
DB_INSTANCE="dr-replica-db"
HOSTED_ZONE="Z1234567890"

echo "[1/4] Promoting RDS read replica..."
aws rds promote-read-replica \
  --db-instance-identifier $DB_INSTANCE \
  --region $DR_REGION

echo "[2/4] Scaling up application tier..."
aws autoscaling update-auto-scaling-group \
  --auto-scaling-group-name $ASG_NAME \
  --min-size 4 \
  --desired-capacity 8 \
  --max-size 16 \
  --region $DR_REGION

echo "[3/4] Waiting for instances to become healthy..."
aws autoscaling wait group-in-service \
  --auto-scaling-group-name $ASG_NAME \
  --region $DR_REGION

echo "[4/4] Updating DNS failover weight..."
aws route53 change-resource-record-sets \
  --hosted-zone-id $HOSTED_ZONE \
  --change-batch '{"Changes":[{"Action":"UPSERT","ResourceRecordSet":{"Name":"api.example.com","Type":"A","SetIdentifier":"secondary","Failover":"PRIMARY","TTL":60,"ResourceRecords":[{"Value":"198.51.100.20"}]}}]}'

echo "Failover complete. Verify at https://api.example.com/health"Shell

Lessons from Real Incidents

After managing DR for production systems across three organizations, these are the lessons that only come from real outages:

  • DNS caching will betray you. During a us-east-1 outage, our Route 53 failover worked perfectly, but some clients cached the old IP for 30+ minutes because we had a 300-second TTL. Always use a low TTL for failover records.
  • Read replicas are not instant promotions. Promoting an RDS read replica can take 5-15 minutes. Factor this into your RTO calculations and consider Aurora Global Database for faster failover.
  • Secrets and config drift silently. Your DR region may have stale API keys, expired certificates, or outdated environment variables. Include config synchronization in your replication strategy.
  • IAM is global, but service quotas are regional. We once failed over and immediately hit EC2 instance limits in the DR region because nobody had requested quota increases. Check service quotas in your DR region proactively.
  • People are the biggest bottleneck. During a 2 AM outage, the person with the failover runbook knowledge was unreachable. Automate everything possible and ensure at least three people can execute the plan independently.

The best DR strategy is the one your team has practiced until it becomes muscle memory. Cost and architecture matter, but human readiness determines whether you meet your RTO when it counts.
