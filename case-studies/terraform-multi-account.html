Managing 8+ AWS Accounts with Terraform

How I architected a scalable Terraform codebase using AWS Organizations, shared modules, cross-account IAM roles, and CI-driven plan/apply workflows to manage infrastructure across production, staging, dev, security, logging, and shared-services accounts.

Project Overview

The company was scaling fast. Engineering had tripled in eighteen months and the cloud footprint was growing with it. When I joined the platform team, there were three AWS accounts—production, staging, and a catch-all dev account—all managed manually through the AWS Console. IAM policies were copy-pasted between accounts, VPC CIDRs overlapped, and nobody could say with certainty what infrastructure existed where.

The mandate was clear: scale to eight or more accounts with proper governance, auditability, and automation. Every resource had to be codified in Terraform, every change had to go through a pull request, and the entire estate had to be manageable by a two-person platform team without heroics.

Target accounts: Production, Staging, Development, Security, Logging, Shared Services, Sandbox, and a Network (transit) account. All governed under a single AWS Organization with strict service control policies.

The project took roughly ten weeks from design to full rollout. This case study walks through every major decision—the organization structure, the Terraform repository layout, IAM strategy, CI/CD pipeline, and the compliance guardrails that keep everything in check.

AWS Organizations Setup

The foundation of any multi-account strategy is AWS Organizations. I designed a four-tier organizational unit (OU) hierarchy that balances isolation with operational simplicity.

OU Structure

Root
├── Security OU
│   ├── security-account       (GuardDuty, Security Hub, IAM Identity Center)
│   └── logging-account        (CloudTrail, Config, centralized S3 logs)
├── Infrastructure OU
│   ├── shared-services        (ECR, Route 53 zones, shared AMIs)
│   └── network-account        (Transit Gateway, VPN, Direct Connect)
├── Workloads OU
│   ├── production-account
│   ├── staging-account
│   └── development-account
└── Sandbox OU
    └── sandbox-account        (experimentation, auto-nuke after 7 days)

Service Control Policies

SCPs act as guardrails at the OU level. I applied three key policies:

  • DenyRootAccount — Prevents use of the root user in all accounts except the management account.
  • RestrictRegions — Limits resource creation to us-east-1 and eu-west-1, reducing blast radius and cost sprawl.
  • DenyLeaveOrganization — No account can remove itself from the Organization.
Lesson learned: Always test SCPs in a sandbox OU first. I accidentally blocked sts:AssumeRole across the Workloads OU during initial rollout, which broke every cross-account pipeline for about 40 minutes.

Account Factory

New accounts are provisioned via a Terraform module that wraps aws_organizations_account. It automatically applies baseline resources: a Terraform execution role, CloudTrail forwarding, VPC flow log configuration, and default tagging. Spinning up a new account takes a single PR.

Each environment directory is a self-contained Terraform root module. It calls shared modules with environment-specific variables. The global/ directory manages Organization-level resources that exist only in the management account.

Cross-Account IAM Roles

Terraform runs from a central CI pipeline in the shared-services account but needs to provision resources in every other account. The solution is an assume-role chain: the CI runner authenticates via OIDC, assumes a role in shared-services, then assumes an execution role in the target account.

Provider Configuration with Assume Role

environments/production/main.tf
provider "aws" {
  alias  = "production"
  region = "us-east-1"

  assume_role {
    role_arn     = "arn:aws:iam::111122223333:role/TerraformExecution"
    session_name = "terraform-ci-production"
    external_id  = var.external_id
  }

  default_tags {
    tags = {
      Environment = "production"
      ManagedBy   = "terraform"
      Team        = "platform"
    }
  }
}

provider "aws" {
  alias  = "logging"
  region = "us-east-1"

  assume_role {
    role_arn     = "arn:aws:iam::444455556666:role/TerraformExecution"
    session_name = "terraform-ci-logging"
  }
}

IAM Role Trust Policy

modules/iam/terraform-execution-role.tf
resource "aws_iam_role" "terraform_execution" {
  name = "TerraformExecution"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Principal = {
          AWS = "arn:aws:iam::999988887777:role/GitHubActionsOIDC"
        }
        Action = "sts:AssumeRole"
        Condition = {
          StringEquals = {
            "sts:ExternalId" = var.external_id
          }
        }
      }
    ]
  })

  max_session_duration = 3600
}
Best practice: Use OIDC federation for CI runners instead of long-lived access keys. GitHub Actions has native support for AWS OIDC, eliminating the need to store AWS_SECRET_ACCESS_KEY in repository secrets.

Shared Modules

The power of a multi-account Terraform setup lies in reusable modules. Every module enforces input validation, produces consistent outputs, and includes sensible defaults. Here is the VPC module as an example.

VPC Module

modules/vpc/variables.tf
variable "vpc_cidr" {
  description = "CIDR block for the VPC"
  type        = string

  validation {
    condition     = can(cidrhost(var.vpc_cidr, 0))
    error_message = "Must be a valid CIDR block (e.g., 10.0.0.0/16)."
  }
}

variable "environment" {
  description = "Environment name"
  type        = string

  validation {
    condition     = contains(["production", "staging", "dev", "shared"], var.environment)
    error_message = "Environment must be one of: production, staging, dev, shared."
  }
}

variable "availability_zones" {
  description = "List of AZs to deploy subnets into"
  type        = list(string)
  default     = ["us-east-1a", "us-east-1b", "us-east-1c"]
}

variable "enable_nat_gateway" {
  description = "Enable NAT Gateway for private subnets"
  type        = bool
  default     = true
}

variable "single_nat_gateway" {
  description = "Use a single NAT Gateway (cost saving for non-prod)"
  type        = bool
  default     = false
}
modules/vpc/main.tf
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name        = "vpc-${var.environment}"
    Environment = var.environment
  }
}

resource "aws_subnet" "private" {
  count             = length(var.availability_zones)
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 4, count.index)
  availability_zone = var.availability_zones[count.index]

  tags = {
    Name = "private-${var.environment}-${var.availability_zones[count.index]}"
    Tier = "private"
  }
}

resource "aws_subnet" "public" {
  count                   = length(var.availability_zones)
  vpc_id                  = aws_vpc.main.id
  cidr_block              = cidrsubnet(var.vpc_cidr, 4, count.index + 8)
  availability_zone       = var.availability_zones[count.index]
  map_public_ip_on_launch = true

  tags = {
    Name = "public-${var.environment}-${var.availability_zones[count.index]}"
    Tier = "public"
  }
}
modules/vpc/outputs.tf
output "vpc_id" {
  description = "ID of the VPC"
  value       = aws_vpc.main.id
}

output "private_subnet_ids" {
  description = "List of private subnet IDs"
  value       = aws_subnet.private[*].id
}

output "public_subnet_ids" {
  description = "List of public subnet IDs"
  value       = aws_subnet.public[*].id
}

The EKS and RDS modules follow the same pattern: strict input validation, opinionated defaults for security (encryption at rest enabled, public access disabled), and clean outputs that downstream modules consume. Each module is versioned via Git tags, and environments pin to specific versions to prevent unexpected changes.

Remote State Management

State isolation is critical in a multi-account setup. Each environment writes to its own state file within a centralized S3 bucket in the shared-services account. DynamoDB provides locking to prevent concurrent modifications.

environments/production/backend.tf
terraform {
  backend "s3" {
    bucket         = "company-terraform-state-central"
    key            = "production/us-east-1/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-state-locks"
    role_arn       = "arn:aws:iam::999988887777:role/TerraformStateAccess"
  }
}

State File Naming Convention

# Pattern: {account-name}/{region}/terraform.tfstate
production/us-east-1/terraform.tfstate
staging/us-east-1/terraform.tfstate
dev/us-east-1/terraform.tfstate
security/us-east-1/terraform.tfstate
logging/us-east-1/terraform.tfstate
shared-services/us-east-1/terraform.tfstate
global/organizations/terraform.tfstate
State bucket security: The S3 bucket has versioning enabled, server-side encryption with a KMS CMK, and a bucket policy that restricts access to only the Terraform execution roles. MFA delete is enabled for an additional layer of protection.

Cross-environment data sharing uses terraform_remote_state data sources. For example, the production environment reads the VPC ID from the network account's state to peer VPCs or attach to Transit Gateway route tables.

CI/CD Pipeline

The pipeline follows a strict plan-on-PR, apply-on-merge workflow. No one runs terraform apply locally. Every change goes through code review with the plan output attached to the pull request as a comment.

.github/workflows/terraform.yml
name: Terraform Multi-Account

on:
  pull_request:
    paths:
      - 'environments/**'
      - 'modules/**'
  push:
    branches: [main]
    paths:
      - 'environments/**'
      - 'modules/**'

permissions:
  id-token: write
  contents: read
  pull-requests: write

jobs:
  detect-changes:
    runs-on: ubuntu-latest
    outputs:
      environments: ${{ steps.filter.outputs.environments }}
    steps:
      - uses: actions/checkout@v4
      - id: filter
        run: |
          # Detect which environment directories changed
          ENVS=$(git diff --name-only HEAD~1 | grep ^environments/ | cut -d/ -f2 | sort -u | jq -R -s -c 'split("\n")[:-1]')
          echo "environments=$ENVS" >> $GITHUB_OUTPUT

  plan:
    needs: detect-changes
    runs-on: ubuntu-latest
    strategy:
      matrix:
        environment: ${{ fromJson(needs.detect-changes.outputs.environments) }}
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::999988887777:role/GitHubActionsOIDC
          aws-region: us-east-1
      - uses: hashicorp/setup-terraform@v3
      - name: Terraform Init
        run: terraform init
        working-directory: environments/${{ matrix.environment }}
      - name: Terraform Plan
        id: plan
        run: terraform plan -no-color -out=tfplan
        working-directory: environments/${{ matrix.environment }}
      - name: Comment PR with Plan
        if: github.event_name == 'pull_request'
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
              body: `### Plan: ${{ matrix.environment }}\n\`\`\`\n${{ steps.plan.outputs.stdout }}\n\`\`\``
            })

  apply:
    needs: [detect-changes, plan]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: ${{ matrix.environment }} # Requires manual approval for prod
    strategy:
      matrix:
        environment: ${{ fromJson(needs.detect-changes.outputs.environments) }}
      max-parallel: 1
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::999988887777:role/GitHubActionsOIDC
          aws-region: us-east-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
        working-directory: environments/${{ matrix.environment }}
      - run: terraform apply -auto-approve
        working-directory: environments/${{ matrix.environment }}
Environment protection rules: The production and security environments in GitHub require manual approval from a designated reviewer before the apply job runs. This adds a human gate for high-risk changes.

Drift Detection & Compliance

Automated drift detection runs on a daily cron schedule. A GitHub Actions workflow executes terraform plan against every environment and posts alerts to Slack if drift is detected. This catches manual console changes before they become entrenched.

OPA Policy Checks

Before any plan is approved, the Terraform plan JSON output is evaluated against Open Policy Agent (OPA) policies. These policies enforce organizational standards at the code level.

policies/tagging.rego
package terraform.tagging

import input as tfplan

required_tags := {"Environment", "ManagedBy", "Team", "CostCenter"}

# Deny resources missing required tags
deny[msg] {
  resource := tfplan.resource_changes[_]
  resource.change.actions[_] == "create"

  tags := resource.change.after.tags
  missing := required_tags - {tag | tags[tag]}
  count(missing) > 0

  msg := sprintf(
    "Resource %s (%s) is missing required tags: %v",
    [resource.address, resource.type, missing]
  )
}

# Deny if ManagedBy tag is not "terraform"
deny[msg] {
  resource := tfplan.resource_changes[_]
  resource.change.actions[_] == "create"
  resource.change.after.tags.ManagedBy != "terraform"

  msg := sprintf(
    "Resource %s must have ManagedBy=terraform tag",
    [resource.address]
  )
}
Enforcement, not just detection: OPA policy failures block the pipeline. The plan job exits with a non-zero code, preventing the PR from being merged. This is not advisory—it is a hard gate.

Additional policies enforce security baselines: S3 buckets must have encryption enabled, RDS instances cannot be publicly accessible, and security groups cannot have 0.0.0.0/0 ingress on port 22.

Results & Impact

After ten weeks of implementation and migration, the transformation was substantial. Here are the numbers that mattered to leadership:

  • Provisioning time: Dropped from 2-3 days of manual setup to under 20 minutes for a fully configured account with VPC, IAM baselines, logging, and monitoring.
  • Manual console changes: Zero. Every change goes through a pull request. The Terraform execution roles are the only principals with write access, and they are only assumable by the CI pipeline.
  • Audit trail: 100% of infrastructure changes are tracked in Git history with full context—who approved it, what the plan output showed, and when it was applied.
  • Team size: Eight AWS accounts managed by a two-person platform team. Before this project, three accounts required three engineers plus ad-hoc help from application teams.
  • Drift incidents: Reduced from ~12 per month (untracked console changes) to fewer than 1 per quarter, typically caused by AWS-initiated changes (e.g., default security group rule updates).
  • Cost visibility: Mandatory CostCenter tagging enabled accurate per-team cost allocation for the first time, revealing that one team accounted for 40% of the staging bill due to orphaned resources.
Ongoing maintenance: The repository averages 15-20 PRs per week. Module updates propagate across environments in a controlled rollout—dev first, then staging, then production—with each step requiring a separate PR and approval.

Key Takeaways

Building a multi-account Terraform setup is not just about writing HCL. The hardest parts are organizational: agreeing on naming conventions, defining ownership boundaries between teams, and building trust in automation so that engineers stop reaching for the console. The technical implementation is the straightforward part once those decisions are made.

If I were starting this project again, the one thing I would do differently is adopt Terragrunt from the start to reduce backend configuration boilerplate. The DRY wrapper it provides for backend configs and provider blocks would have saved several hundred lines of repetitive code across eight environments. That said, the vanilla Terraform approach we chose is easier to onboard new team members to, and that trade-off was worth it for our team.
