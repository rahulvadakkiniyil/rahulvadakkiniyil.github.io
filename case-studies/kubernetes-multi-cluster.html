Kubernetes Multi-Cluster Platform on AWS EKS

How I designed and deployed a multi-region Kubernetes platform serving 150+ microservices across two AWS regions with Istio service mesh, automated failover, and centralized observability.

Project Overview

Our organization operated a monolithic deployment model where all services ran in a single AWS region. After two major outages in Q3 caused by region-level AWS issues, leadership mandated a multi-region strategy. The goals were clear: eliminate single points of failure, meet data residency requirements for our expanding European customer base, and reduce the blast radius of any single deployment gone wrong.

The platform needed to support 150+ microservices owned by 18 engineering teams, handle 45,000 requests per second at peak, and provide seamless failover with less than 30 seconds of downtime during a regional incident. I led the infrastructure design and implementation from proof-of-concept through production rollout over a six-month engagement.

Key Constraints: The migration had to be zero-downtime. Teams could not be blocked during the transition. All existing CI/CD pipelines had to work with the new multi-cluster topology without requiring application code changes.

The previous single-cluster setup had several pain points beyond availability: cluster upgrades required extended maintenance windows, namespace sprawl made resource accounting difficult, and the lack of service mesh meant no mTLS between services. This project addressed all of these concerns simultaneously.

Architecture

The platform runs two AWS EKS clusters across us-east-1 (primary) and us-west-2 (secondary). Each cluster mirrors the other in terms of installed operators, namespace structure, and deployed workloads, but they operate independently for day-to-day traffic.

Cluster Topology

Each cluster runs Kubernetes 1.29 on EKS with three distinct managed node groups:

  • System Node Group — 3x m6i.xlarge instances reserved for cluster-critical components: CoreDNS, Istio control plane, monitoring agents, and ingress controllers. These nodes carry a taint node-role=system:NoSchedule to prevent workload pods from landing here.
  • Workload Node Group — 6-20x m6i.2xlarge On-Demand instances for production workloads requiring guaranteed capacity. Karpenter handles scaling within defined limits.
  • Spot Node Group — 0-30x mixed instance types (m6i.2xlarge, m5.2xlarge, r6i.2xlarge) for non-critical workloads, batch jobs, and development namespaces. This group alone delivered a 40% cost reduction compared to running everything on-demand.

Networking

Cross-region connectivity uses AWS Transit Gateway with inter-region peering. Each cluster's VPC uses non-overlapping CIDR ranges (10.10.0.0/16 for us-east-1, 10.20.0.0/16 for us-west-2) to enable direct pod-to-pod communication across regions. The Amazon VPC CNI plugin runs in custom networking mode to conserve IP addresses and to place pods in dedicated subnets separate from the node ENIs.

Design Decision: We chose Transit Gateway over VPC Peering because it gave us centralized route management and the ability to add future regions without exponential peering connections. The marginal cost increase was negligible at our traffic volume.

Cluster Bootstrap with Terraform

All infrastructure is defined in Terraform with a modular structure. Each region has its own state file stored in S3 with DynamoDB locking. The EKS module wraps the official terraform-aws-modules/eks module with our organizational defaults baked in.

modules/eks-cluster/main.tf
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"

  cluster_name    = "platform-${var.region_alias}"
  cluster_version = "1.29"
  vpc_id          = var.vpc_id
  subnet_ids      = var.private_subnet_ids

  cluster_endpoint_public_access  = false
  cluster_endpoint_private_access = true

  cluster_addons = {
    coredns    = { most_recent = true }
    kube-proxy = { most_recent = true }
    vpc-cni    = {
      most_recent    = true
      configuration_values = jsonencode({
        env = {
          AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG = "true"
          ENI_CONFIG_LABEL_DEF              = "topology.kubernetes.io/zone"
        }
      })
    }
  }

  eks_managed_node_groups = {
    system = {
      instance_types = ["m6i.xlarge"]
      min_size       = 3
      max_size       = 3
      desired_size   = 3
      labels         = { "node-role" = "system" }
      taints = [{
        key    = "node-role"
        value  = "system"
        effect = "NO_SCHEDULE"
      }]
    }

    workload = {
      instance_types = ["m6i.2xlarge"]
      min_size       = 6
      max_size       = 20
      desired_size   = 8
      labels         = { "node-role" = "workload" }
    }

    spot = {
      instance_types = ["m6i.2xlarge", "m5.2xlarge", "r6i.2xlarge"]
      capacity_type  = "SPOT"
      min_size       = 0
      max_size       = 30
      desired_size   = 5
      labels         = { "node-role" = "spot" }
      taints = [{
        key    = "capacity"
        value  = "spot"
        effect = "NO_SCHEDULE"
      }]
    }
  }
}

IRSA (IAM Roles for Service Accounts)

Every workload that needs AWS API access uses IRSA instead of node-level IAM roles. This follows the principle of least privilege and eliminates the risk of one pod assuming permissions meant for another.

modules/irsa/main.tf
module "irsa_fluentbit" {
  source  = "terraform-aws-modules/iam/aws//modules/iam-role-for-service-accounts-eks"
  version = "~> 5.0"

  role_name = "fluentbit-${var.cluster_name}"

  oidc_providers = {
    main = {
      provider_arn               = var.oidc_provider_arn
      namespace_service_accounts = ["logging:fluent-bit"]
    }
  }

  role_policy_arns = {
    cloudwatch = "arn:aws:iam::policy/CloudWatchLogsFullAccess"
    s3_logs    = aws_iam_policy.fluentbit_s3.arn
  }
}

Service Mesh with Istio

We deployed Istio 1.21 in a primary-remote model. The us-east-1 cluster hosts the primary Istio control plane (istiod), while us-west-2 runs a remote configuration that connects back to the primary's control plane over the Transit Gateway link. This model simplifies certificate management and policy distribution while still allowing each cluster to handle its own data plane traffic independently.

Lesson Learned: In our initial rollout, we attempted a multi-primary Istio setup. The operational overhead of managing two independent certificate authorities and synchronizing authorization policies across both control planes was significant. Switching to primary-remote cut our Istio-related incident tickets by 60%.

Cross-Cluster Service Discovery

Istio's multi-cluster service discovery allows a pod in us-east-1 to transparently call a service in us-west-2 using the same Kubernetes service name. We configure this by creating remote secrets that grant each cluster read access to the other's API server.

Istio Gateway & Traffic Routing

istio/gateway.yaml
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: platform-gateway
  namespace: istio-system
spec:
  selector:
    istio: ingressgateway
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
      tls:
        mode: SIMPLE
        credentialName: platform-tls-cert
      hosts:
        - "*.platform.internal.company.com"
    - port:
        number: 80
        name: http
        protocol: HTTP
      tls:
        httpsRedirect: true
      hosts:
        - "*.platform.internal.company.com"
istio/virtualservice-api.yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: api-gateway-vs
  namespace: production
spec:
  hosts:
    - "api.platform.internal.company.com"
  gateways:
    - istio-system/platform-gateway
  http:
    - match:
        - uri:
            prefix: "/v2/"
      route:
        - destination:
            host: api-gateway.production.svc.cluster.local
            port:
              number: 8080
            subset: stable
          weight: 90
        - destination:
            host: api-gateway.production.svc.cluster.local
            port:
              number: 8080
            subset: canary
          weight: 10
      retries:
        attempts: 3
        perTryTimeout: 2s
        retryOn: 5xx,reset,connect-failure
istio/destination-rule.yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: api-gateway-dr
  namespace: production
spec:
  host: api-gateway.production.svc.cluster.local
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 1000
      http:
        h2UpgradePolicy: UPGRADE
        maxRequestsPerConnection: 100
    outlierDetection:
      consecutive5xxErrors: 5
      interval: 30s
      baseEjectionTime: 60s
      maxEjectionPercent: 50
    tls:
      mode: ISTIO_MUTUAL
  subsets:
    - name: stable
      labels:
        version: stable
    - name: canary
      labels:
        version: canary

The ISTIO_MUTUAL TLS mode enforces mTLS for all inter-service communication. Combined with Istio's PeerAuthentication policy set to STRICT across the mesh, this ensures that no plaintext traffic flows between any two services, even within the same namespace.

Centralized Logging & Monitoring

Observability across two clusters is non-negotiable. We built a centralized stack where both clusters ship telemetry to a shared observability plane hosted in us-east-1.

Logging with Fluent Bit

Each cluster runs Fluent Bit as a DaemonSet that collects container logs, enriches them with Kubernetes metadata (namespace, pod, labels), and ships them to a centralized Grafana Loki instance backed by S3. We chose Loki over Elasticsearch for its dramatically lower resource footprint and native label-based querying that maps well to Kubernetes concepts.

logging/fluent-bit-values.yaml
config:
  inputs: |
    [INPUT]
        Name              tail
        Tag               kube.*
        Path              /var/log/containers/*.log
        Parser            cri
        DB                /var/log/flb_kube.db
        Mem_Buf_Limit     50MB
        Skip_Long_Lines   On
        Refresh_Interval  5

  filters: |
    [FILTER]
        Name                kubernetes
        Match               kube.*
        Kube_URL            https://kubernetes.default.svc:443
        Kube_Tag_Prefix     kube.var.log.containers.
        Merge_Log           On
        Keep_Log            Off
        K8S-Logging.Parser  On
        Labels              On
        Annotations         Off

    [FILTER]
        Name    modify
        Match   kube.*
        Add     cluster_name platform-${CLUSTER_REGION}
        Add     environment  production

  outputs: |
    [OUTPUT]
        Name         loki
        Match        kube.*
        Host         loki.observability.svc.cluster.local
        Port         3100
        Labels       job=fluentbit, cluster=${CLUSTER_REGION}
        Auto_Kubernetes_Labels On

Metrics with Prometheus Federation

Each cluster runs its own Prometheus instance that scrapes local targets. A central Thanos deployment in us-east-1 provides a global query view by federating metrics from both clusters through Thanos Sidecar running alongside each Prometheus. Long-term storage goes to an S3 bucket with lifecycle policies for cost management.

Dashboard Strategy: We maintain 12 standard Grafana dashboards provisioned via ConfigMaps: cluster health, node utilization, namespace resource consumption, Istio mesh traffic, pod restart rates, and per-team cost allocation. Every dashboard includes a cluster selector dropdown so engineers can compare behavior across regions.

Namespace Strategy & Resource Quotas

Multi-tenancy is enforced at the namespace level. Each team owns one or more namespaces, and all namespaces are created through Terraform with mandatory ResourceQuota and LimitRange objects attached. No team can create namespaces ad-hoc.

Namespace Structure

We follow a naming convention of {team}-{environment}. For example, payments-production, payments-staging, search-production. Platform-level namespaces like istio-system, logging, and monitoring are managed exclusively by the platform team.

namespaces/resource-quota.yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: payments-production
spec:
  hard:
    requests.cpu: "20"
    requests.memory: "40Gi"
    limits.cpu: "40"
    limits.memory: "80Gi"
    pods: "100"
    services: "30"
    persistentvolumeclaims: "20"
    secrets: "50"
    configmaps: "50"
namespaces/limit-range.yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: payments-production
spec:
  limits:
    - type: Container
      default:
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"
      max:
        cpu: "4"
        memory: "8Gi"
      min:
        cpu: "50m"
        memory: "64Mi"
    - type: Pod
      max:
        cpu: "8"
        memory: "16Gi"

The LimitRange ensures that even if a developer forgets to set resource requests in their pod spec, sensible defaults are applied. The hard caps prevent any single container from consuming excessive resources and impacting neighbors in the same node.

Automated Failover

Failover is the cornerstone of the multi-cluster value proposition. We use a combination of Route 53 health checks, DNS-based failover, and ArgoCD for deployment consistency to achieve sub-30-second failover times.

Route 53 Health Checks

Each cluster exposes a /healthz endpoint through its NLB. Route 53 health checks poll these endpoints every 10 seconds from multiple AWS edge locations. The DNS records use a failover routing policy where us-east-1 is the primary and us-west-2 is the secondary.

terraform/route53-failover.tf
resource "aws_route53_health_check" "east_cluster" {
  fqdn              = "ingress-east.platform.company.com"
  port              = 443
  type              = "HTTPS"
  resource_path     = "/healthz"
  failure_threshold = "3"
  request_interval  = "10"

  tags = {
    Name = "platform-east-health"
  }
}

resource "aws_route53_record" "primary" {
  zone_id = var.hosted_zone_id
  name    = "api.platform.company.com"
  type    = "A"

  failover_routing_policy {
    type = "PRIMARY"
  }

  alias {
    name                   = module.eks_east.nlb_dns_name
    zone_id                = module.eks_east.nlb_zone_id
    evaluate_target_health = true
  }

  set_identifier  = "primary"
  health_check_id = aws_route53_health_check.east_cluster.id
}

resource "aws_route53_record" "secondary" {
  zone_id = var.hosted_zone_id
  name    = "api.platform.company.com"
  type    = "A"

  failover_routing_policy {
    type = "SECONDARY"
  }

  alias {
    name                   = module.eks_west.nlb_dns_name
    zone_id                = module.eks_west.nlb_zone_id
    evaluate_target_health = true
  }

  set_identifier = "secondary"
}

ArgoCD App-of-Apps

Both clusters are registered as targets in a single ArgoCD instance. We use the app-of-apps pattern where a root Application resource generates child Application resources for every microservice. Each child app targets both clusters, ensuring that any manifest change committed to Git is automatically synced to both regions within minutes.

argocd/app-of-apps.yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: platform-services
  namespace: argocd
spec:
  generators:
    - matrix:
        generators:
          - git:
              repoURL: https://github.com/company/platform-manifests.git
              revision: main
              directories:
                - path: "services/*"
          - list:
              elements:
                - cluster: platform-east
                  url: https://eks-east.company.internal
                - cluster: platform-west
                  url: https://eks-west.company.internal
  template:
    metadata:
      name: "{{path.basename}}-{{cluster}}"
    spec:
      project: default
      source:
        repoURL: https://github.com/company/platform-manifests.git
        targetRevision: main
        path: "{{path}}"
      destination:
        server: "{{url}}"
        namespace: production
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
          - PruneLast=true
Failover Test Protocol: We run monthly chaos engineering exercises where we simulate a full regional failure by scaling down all workload nodes in us-east-1 to zero. The platform consistently recovers traffic to us-west-2 within 22-28 seconds, well under our 30-second SLA.

Results & Impact

After six months of design, implementation, and gradual migration, the multi-cluster platform went fully live. Here are the measurable outcomes:

  • 99.99% uptime achieved over the first 12 months of operation, up from 99.9% on the single-cluster setup. The additional nine translates to roughly 52 fewer minutes of downtime per year.
  • 40% infrastructure cost reduction by running non-critical and batch workloads on Spot instances. The diversified instance type pool across three families ensures that Spot interruptions are rare and well-handled by Karpenter's consolidation logic.
  • Sub-30-second failover consistently measured during monthly chaos drills. DNS TTL is set to 15 seconds, and Route 53 health checks detect failures within 10 seconds, making the theoretical minimum around 25 seconds.
  • 150+ microservices migrated to the platform without application code changes. Teams only needed to update their Helm chart values to include node affinity rules and resource requests.
  • 18 teams onboarded with self-service namespace provisioning through Terraform modules. Average onboarding time for a new team dropped from 2 weeks to under 1 day.
  • Zero-downtime cluster upgrades became possible by draining one cluster at a time. Kubernetes version upgrades that previously required 4-hour maintenance windows now happen transparently during business hours.
What I Would Do Differently: If starting fresh, I would evaluate Cilium as the CNI and service mesh replacement for both VPC CNI and Istio. Cilium's eBPF-based approach eliminates sidecar overhead and provides native multi-cluster connectivity through ClusterMesh, which would reduce the operational surface area significantly. I would also adopt Crossplane earlier for managing AWS resources declaratively from within Kubernetes rather than maintaining a separate Terraform workflow.

This project demonstrated that a well-designed multi-cluster Kubernetes platform is not just about redundancy. It is an enabler for faster, safer deployments, better resource utilization, and a foundation that scales with the organization. The investment in automation and GitOps from day one meant that the platform essentially runs itself, with the team shifting focus from operational firefighting to building internal developer tooling on top of the platform.
