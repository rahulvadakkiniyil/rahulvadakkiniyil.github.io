Production Observability Stack for 200+ Microservices

Building a unified observability platform with Prometheus, Grafana, Loki, and Alertmanager — covering metrics, logs, traces, and intelligent alerting at scale.

Project Overview

Our platform had grown to over 200 microservices deployed across multiple Kubernetes clusters, yet there was no unified monitoring solution in place. Each team had cobbled together its own approach — some used basic log files, others relied on ad-hoc shell scripts, and a handful had standalone Prometheus instances with no cross-cluster visibility. The result was a landscape of blind spots where production incidents went undetected for far too long.

The mean time to resolution (MTTR) had climbed to 45+ minutes, largely because engineers spent the first 20 minutes just figuring out where the problem was. There was no correlation between metrics, logs, and traces. Alert fatigue was rampant — teams had either too many noisy alerts or, worse, none at all. On-call rotations were dreaded, and customer-facing SLAs were at risk.

Business Drivers: The VP of Engineering mandated a single observability platform that every team could adopt within one quarter, with clearly defined SLOs and a centralized alerting pipeline that integrated with existing PagerDuty and Slack workflows.

The project goals were clear: unify metrics collection across all clusters, implement structured log aggregation, introduce distributed tracing, build a library of standardized dashboards, and establish an intelligent alerting pipeline that reduced noise while catching real incidents faster. The target was to bring MTTR below 10 minutes and achieve 99.95% SLO across all customer-facing services.

Architecture Design

The observability platform was built on three pillars, each handled by a purpose-built open-source tool, with Grafana serving as the unified visualization layer:

  • Metrics — Prometheus with Thanos sidecar for long-term storage and cross-cluster federation
  • Logs — Grafana Loki with FluentBit as the log collector on every node
  • Traces — Grafana Tempo with OpenTelemetry SDK instrumentation across services
  • Dashboards & Visualization — Grafana as the single pane of glass with provisioned data sources
  • Alerting — Alertmanager with routing trees for PagerDuty, Slack, and email escalation
Architecture Overview: Each Kubernetes cluster runs its own Prometheus, Loki, and Tempo instances. Thanos Query federates metrics from all clusters into a global view. Grafana connects to Thanos Query for metrics, Loki for logs, and Tempo for traces — enabling seamless correlation across all three pillars from a single dashboard.

The architecture was designed with multi-tenancy in mind. Each team's namespace received its own set of ServiceMonitors, log labels, and trace service names, ensuring that dashboards and alerts could be scoped per team while still allowing platform-wide rollups for SRE leadership.

Prometheus Setup

Prometheus was deployed using the kube-prometheus-stack Helm chart, which bundles Prometheus Operator, Alertmanager, Grafana, and a comprehensive set of recording rules and dashboards for Kubernetes cluster monitoring out of the box. We customized the Helm values extensively to support our scale and multi-cluster requirements.

kube-prometheus-stack Helm Values (values.yaml)
prometheus:
  prometheusSpec:
    replicas: 2
    retention: 15d
    retentionSize: 45GB
    resources:
      requests:
        cpu: 2000m
        memory: 8Gi
      limits:
        cpu: 4000m
        memory: 16Gi
    storageSpec:
      volumeClaimTemplate:
        spec:
          storageClassName: gp3-encrypted
          resources:
            requests:
              storage: 100Gi
    serviceMonitorSelectorNilUsesHelmValues: false
    podMonitorSelectorNilUsesHelmValues: false
    # Thanos sidecar for cross-cluster federation
    thanos:
      objectStorageConfig:
        secret:
          type: S3
          name: thanos-objstore-secret
          key: objstore.yml

alertmanager:
  alertmanagerSpec:
    replicas: 3
    retention: 120h

grafana:
  enabled: true
  replicas: 2
  persistence:
    enabled: true
    size: 10Gi

Every service that needed monitoring defined a ServiceMonitor CRD, which instructed Prometheus Operator to automatically discover and scrape the service's metrics endpoint. We standardized the metrics path as /metrics and required every service to expose RED metrics (Rate, Errors, Duration) using a shared middleware library.

ServiceMonitor CRD (servicemonitor.yaml)
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: payment-service-monitor
  namespace: payments
  labels:
    team: payments
    release: kube-prometheus-stack
spec:
  selector:
    matchLabels:
      app: payment-service
  endpoints:
    - port: http-metrics
      path: /metrics
      interval: 15s
      scrapeTimeout: 10s
  namespaceSelector:
    matchNames:
      - payments

Grafana Dashboards

All dashboards were managed as code, provisioned through Kubernetes ConfigMaps that Grafana's sidecar container automatically picked up. This ensured dashboards were version-controlled, reproducible across environments, and immune to manual drift. We built a library of standardized dashboards covering cluster health, namespace resource usage, service-level SLO tracking, and per-service latency breakdowns.

Grafana Dashboard Provisioning ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: grafana-dashboard-slo-overview
  namespace: monitoring
  labels:
    grafana_dashboard: "1"
data:
  slo-overview.json: |-
    {
      "dashboard": {
        "title": "SLO Overview - All Services",
        "uid": "slo-overview-v1",
        "panels": [
          {
            "title": "Availability SLO (30d rolling)",
            "type": "gauge",
            "targets": [{
              "expr": "1 - (sum(rate(http_requests_total{code=~\"5..\"}[30d])) / sum(rate(http_requests_total[30d])))"
            }]
          },
          {
            "title": "P99 Latency by Service",
            "type": "timeseries",
            "targets": [{
              "expr": "histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le, service))"
            }]
          }
        ]
      }
    }

Key dashboards included a Cluster Health overview (node CPU, memory, disk, and pod status), a Service Latency dashboard with RED metrics breakdown, an SLO burn rate tracker showing remaining error budgets, and a Cost Attribution dashboard that tied resource usage back to teams and services.

Dashboard Standards: Every team was required to have at least three dashboards: a service overview (golden signals), a dependency health check (downstream latency and error rates), and a custom business metrics board. Templates were provided as Helm chart values.

Log Aggregation with Loki

Grafana Loki was chosen over Elasticsearch for log aggregation due to its significantly lower resource footprint. Loki indexes only metadata labels rather than full-text content, which reduced storage costs by approximately 60% compared to our previous ELK stack estimates. FluentBit ran as a DaemonSet on every node, collecting container logs and forwarding them to Loki with enriched Kubernetes metadata.

FluentBit Configuration (fluent-bit.conf)
[SERVICE]
    Flush        1
    Log_Level    info
    Daemon       off
    Parsers_File parsers.conf

[INPUT]
    Name             tail
    Path             /var/log/containers/*.log
    Parser           docker
    Tag              kube.*
    Mem_Buf_Limit    5MB
    Skip_Long_Lines  On
    Refresh_Interval 10

[FILTER]
    Name                kubernetes
    Match               kube.*
    Merge_Log           On
    Keep_Log            Off
    K8S-Logging.Parser  On
    K8S-Logging.Exclude On
    Labels              On
    Annotations        Off

[OUTPUT]
    Name        loki
    Match       kube.*
    Host        loki-gateway.monitoring.svc
    Port        3100
    Labels      job=fluentbit, cluster=prod-us-east-1
    Label_Keys  $kubernetes['namespace_name'],$kubernetes['pod_name'],$kubernetes['container_name']
    Auto_Kubernetes_Labels Off

All services were required to emit structured JSON logs with standardized fields: level, msg, timestamp, trace_id, service, and request_id. The trace_id field enabled direct correlation between logs in Loki and traces in Tempo from within Grafana's Explore view.

LogQL Query Examples
# Find all errors in the payment service in the last hour
{namespace="payments", container="payment-service"}
  |= `"level":"error"`
  | json
  | line_format "{{.timestamp}} [{{.level}}] {{.msg}}"

# Count error rate per service over 5 minute windows
sum by (service) (
  count_over_time(
    {cluster="prod-us-east-1"}
    |= `"level":"error"`
    | json
    [5m]
  )
)

# Trace correlation — find logs for a specific trace
{namespace="payments"}
  | json
  | trace_id = "abc123def456"
Cardinality Warning: One of the biggest pitfalls with Loki is high-cardinality labels. We enforced a strict policy: only namespace, pod name, container name, and cluster were allowed as index labels. Any other filtering was done via LogQL's pipeline stages on the log content itself.

Alerting Pipeline

Alertmanager was configured with a multi-tier routing tree that directed alerts to the right channel based on severity and owning team. Critical alerts (P1) triggered PagerDuty incidents immediately, high-severity alerts (P2) went to a dedicated Slack channel with a 5-minute group wait, and warnings (P3) were batched into daily digest emails. This tiered approach was central to reducing alert fatigue.

Alertmanager Configuration (alertmanager.yml)
global:
  resolve_timeout: 5m
  pagerduty_url: "https://events.pagerduty.com/v2/enqueue"
  slack_api_url: "https://hooks.slack.com/services/T00/B00/XXXXX"

route:
  receiver: default-slack
  group_by: [alertname, namespace, service]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - match:
        severity: critical
      receiver: pagerduty-critical
      group_wait: 10s
      repeat_interval: 1h
    - match:
        severity: warning
      receiver: slack-warnings
      group_wait: 5m
      repeat_interval: 12h

receivers:
  - name: pagerduty-critical
    pagerduty_configs:
      - service_key_file: /etc/alertmanager/secrets/pagerduty-key
        severity: "{{ .CommonLabels.severity }}"
        description: "{{ .CommonAnnotations.summary }}"
  - name: slack-warnings
    slack_configs:
      - channel: "#alerts-warning"
        title: "[{{ .Status | toUpper }}] {{ .CommonLabels.alertname }}"
        text: "{{ .CommonAnnotations.description }}"
  - name: default-slack
    slack_configs:
      - channel: "#alerts-general"
PrometheusRule for High Error Rate (prometheusrule.yaml)
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: service-high-error-rate
  namespace: monitoring
spec:
  groups:
    - name: service.error.rules
      rules:
        - alert: HighErrorRate
          expr: |
            sum(rate(http_requests_total{code=~"5.."}[5m])) by (service, namespace)
            / sum(rate(http_requests_total[5m])) by (service, namespace)
            > 0.05
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "High 5xx error rate on {{ $labels.service }}"
            description: "Service {{ $labels.service }} in {{ $labels.namespace }} has an error rate above 5% for the last 5 minutes (current: {{ $value | humanizePercentage }})."
            runbook_url: "https://runbooks.internal/high-error-rate"
Alert Fatigue Reduction: We introduced three key strategies — (1) inhibition rules that suppressed downstream alerts when an upstream dependency was already firing, (2) mandatory for durations of at least 5 minutes on all alerts to avoid flapping, and (3) weekly alert review meetings where noisy or unactionable alerts were pruned.

SLO Tracking

Each customer-facing service defined explicit SLIs (Service Level Indicators) and SLOs (Service Level Objectives). The two primary SLIs were availability (percentage of non-5xx responses) and latency (percentage of requests completing within a target threshold). SLOs were set per service based on business criticality — for example, the payment service had a 99.99% availability SLO while internal tooling services had 99.9%.

Error budgets were calculated on a 30-day rolling window. When a service consumed more than 50% of its error budget, a warning alert fired. At 80% consumption, the team was required to halt feature releases and focus on reliability. Burn rate alerting detected when error budgets were being consumed too quickly, enabling proactive intervention before an SLO breach.

SLO Recording Rules (recording-rules.yaml)
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: slo-recording-rules
  namespace: monitoring
spec:
  groups:
    - name: slo.recording.rules
      interval: 30s
      rules:
        # Availability SLI — ratio of successful requests
        - record: sli:availability:ratio_rate5m
          expr: |
            1 - (
              sum(rate(http_requests_total{code=~"5.."}[5m])) by (service)
              / sum(rate(http_requests_total[5m])) by (service)
            )

        # Latency SLI — ratio of requests under 300ms
        - record: sli:latency:ratio_rate5m
          expr: |
            sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m])) by (service)
            / sum(rate(http_request_duration_seconds_count[5m])) by (service)

        # Error budget remaining (30-day window)
        - record: slo:error_budget:remaining
          expr: |
            1 - (
              (1 - sli:availability:ratio_rate5m)
              / (1 - 0.9995)
            )

        # Burn rate — fast burn (1h window, 14.4x budget)
        - record: slo:burn_rate:1h
          expr: |
            (
              sum(rate(http_requests_total{code=~"5.."}[1h])) by (service)
              / sum(rate(http_requests_total[1h])) by (service)
            ) / (1 - 0.9995)

        # Burn rate — slow burn (6h window, 6x budget)
        - record: slo:burn_rate:6h
          expr: |
            (
              sum(rate(http_requests_total{code=~"5.."}[6h])) by (service)
              / sum(rate(http_requests_total[6h])) by (service)
            ) / (1 - 0.9995)
Multi-Window Burn Rate: Following Google's SRE practices, we implemented multi-window burn rate alerting. A fast-burn alert fires when the 1-hour burn rate exceeds 14.4x AND the 5-minute burn rate also exceeds 14.4x. A slow-burn alert fires when the 6-hour burn rate exceeds 6x AND the 30-minute burn rate also exceeds 6x. This approach catches both sudden outages and slow degradations.

Results & Impact

The unified observability stack was rolled out incrementally over 10 weeks, starting with the three highest-traffic services and expanding team by team. By the end of the rollout, all 200+ microservices across four Kubernetes clusters were fully instrumented. The results were transformative:

  • MTTR reduced from 45 minutes to 8 minutes — Correlated metrics, logs, and traces in a single Grafana session eliminated the time engineers previously spent switching tools and contexts during incidents.
  • 99.95% SLO achievement — All customer-facing services met or exceeded their SLO targets for three consecutive quarters, up from an inconsistent and unmeasured baseline.
  • 70% reduction in alert noise — Inhibition rules, mandatory for durations, and weekly alert reviews brought the actionable alert ratio from roughly 30% to over 90%.
  • Single pane of glass for all teams — Grafana became the one place every engineer went during incidents. Standardized dashboards meant that on-call responders could investigate any service, even ones they had never worked on before.
  • 60% lower log storage costs — Migrating from the proposed Elasticsearch cluster to Loki's label-indexed architecture saved approximately $4,200/month in infrastructure costs.
  • Proactive incident detection — Burn rate alerting caught three major degradations before customers noticed, preventing potential SLO breaches and protecting error budgets.
Key Takeaway: The most impactful decision was not the choice of tools, but the investment in standardization. Requiring every service to expose RED metrics, emit structured JSON logs with trace IDs, and define explicit SLOs created a consistent observability contract that made the entire stack effective at scale.

Looking ahead, the team is exploring Grafana's Adaptive Metrics to automatically identify and drop unused metric series, OpenTelemetry Collector as a unified telemetry pipeline replacing FluentBit and direct SDK instrumentation, and Grafana Machine Learning for anomaly detection on key business metrics. The observability stack has shifted from being a reactive firefighting tool to a proactive platform that continuously validates system health against business objectives.
